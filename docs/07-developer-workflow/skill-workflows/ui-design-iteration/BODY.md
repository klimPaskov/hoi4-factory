# UI design iteration

## Trigger and inputs

Use this workflow whenever a page of the browser client is designed or redesigned: the UI design track (ADR-025), or a new page that a later stage adds. Inputs are the page or pages in scope, the approved design system if one exists, the current screens and the [instructions](../../../../CLAUDE.md).

## Procedure

1. Inventory the page: its route, every state (empty, loading, error, unavailable, success), the data it shows and the actions it offers. Screenshot the current version with the built-in browser.
2. Start from images. Generate the page's look with the image model (the `gptimage` MCP, billed to the maintainer's ChatGPT plan, allowed for page and UI mockups by D-52, while HOI4 game assets come only from hoi4-imagegen) before writing any code: mockups for each page and state, and every visual asset the page needs, such as icons, the logo or mascot poses. Use an approved mockup as the reference image so later images stay consistent, and give a character one master image that every pose references. Write prompts from the brief alone when the maintainer asks for fresh ideas, because earlier concepts in a prompt steer the result. Ask for opaque white backgrounds for mockups and transparent backgrounds for assets. Keep real national flags and political or military insignia out of every image. Store mockups as WebP under `docs/design/mockups/` and copy the ones the lab shows to `web/src/design-lab/mockups/`. Slice icon sheets into alpha masks so icons take the text color. Code then matches the chosen image. Generate one image at a time, never several calls in parallel, with at least 10 to 20 seconds between requests and a longer wait after an error (decision W5-5). Before each request check that no hoi4-imagegen job is generating on the machine, because both tools share one ChatGPT sign-in (D-52). When a page shows a game surface, such as a focus tree, pass a real render of it as a reference image so the mockup looks like the game. Parallel requests from several clients got the account's grants revoked on 2026-11-02, and the gptimage MCP has no lock shared with other processes, so pace by hand. If the server signs the account out, stop and tell the maintainer instead of retrying.
3. Build three or four variants as real React components in the development-only design lab (`/design-lab`, included only when `import.meta.env.DEV` is true). Use fixtures with realistic HOI4 modding data and show every important state. Make the variants differ in a way worth choosing between, such as layout, density or emphasis, not just color. When a design system is approved, every variant uses its tokens and components.
4. Check each variant yourself before showing it: open it at phone width (375 pixels) and desktop width, look for overflow, contrast and focus problems, and fix them.
5. Make the choice easy to review. The lab's front page (`/design-lab`) shows only the one open decision, set in `web/src/design-lab/decisions.ts`: a heading, the question, and the options as large lettered cards with a one-line summary each. Clicking a picture opens a full-screen viewer in the page, where the arrow keys switch options and Escape closes it. Never open pictures in a new tab, and never mix past and present images on one page. Move a decided question to the archive page (`/design-lab/history`) with its outcome.
6. Ask the maintainer to choose with one question: one option per variant, each with a one-line description, and the lab URL. Batch questions for several pages when they are independent. Never choose for the maintainer, and prepare the next round while waiting. The one exception is when the maintainer asks that work go on without waiting for approval. Then pick the option you recommend, build it, and mark it provisional in the lab's `PROVISIONAL` list with its alternatives. List the provisional pages in chat in the same order and with the same letters as the lab shows them. On 2026-11-06 the chat summary listed the pages in the reverse of the lab's order, so the maintainer's answer "A, C, B, B" could be read two ways.
7. Implement the choice in the real page. Keep strings in i18n, keep behavior and API calls, and update tests. Delete the variants that lost, so the lab holds only open choices and the approved components.
8. Run `web/scripts/docker-npm.sh run check`, take an after screenshot, record the choice in `docs/design/DESIGN-DECISIONS.md`, and commit.
9. Repeat for the next page. When the maintainer asks for changes rather than choosing, make a new round from the closest variant.

## Outputs and evidence

The redesigned pages, the design system tokens and components, `docs/design/DESIGN-DECISIONS.md` with each choice and its before and after screenshots, and a passing client check. Keep the interface minimal: the maintainer prefers as little on screen as possible. Screenshots are design evidence, not usability evidence. Usability is observed in the S08 pilot.

## Stop and error paths

If a design needs an API change, a new runtime dependency or a server change, ask the maintainer before building it. Before you send the maintainer to the lab, start the dev server yourself and confirm the page renders the round you mean. `web/scripts/docker-npm.sh` runs only from Git Bash or zsh. In a PowerShell terminal it returns at once and starts nothing. The maintainer's main checkout can also lag `origin/main` while other sessions hold unpushed commits on it, so it may not contain the pushed design work. Serve the lab from a worktree at `origin/main` instead of changing the shared branch. If the dev server cannot reach the API, check that the Compose stack is running and that Vite proxies `/api` to it. If the maintainer is unavailable, keep preparing variants and do not implement an unchosen design. If client tests fail with "Timeout waiting for worker to respond", the host is saturated (check CPU and free memory) rather than the code being wrong: the Docker bind mount on Windows slows module loading past Vitest's 60-second worker start limit. Run lint and typecheck, and rerun the tests when the machine is quieter.
