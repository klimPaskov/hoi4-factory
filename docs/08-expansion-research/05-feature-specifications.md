# Feature specifications

Status: **Proposed for approval**. Covers shared notes, the jobs board, the integrated Git experience, onboarding and graphics, and records why there is no Drift Bot. The research behind each choice is summarised in [open-source research](02-open-source-research.md). Requirement areas FR-1 to FR-4 are specified separately in [ecosystem requirements](06-ecosystem-requirements.md). Under D-13 these are product designs. They are built only when the HOI4 Factory stage that owns them is authorized.

## Shared notes

Decided in B1 ([decision record](00-decision-record.md)).

**Purpose.** One place where people and agents keep lore, mechanics, conventions and design decisions for a mod, readable outside HOI4 Factory.

**Format and storage.**
- Plain Markdown files in the project repository under `.factory/notes/`, compatible with Obsidian: YAML frontmatter, `[[wikilinks]]` (Markdown links also accepted), tags, aliases. Unknown Obsidian syntax and `.canvas` files are preserved untouched.
- PostgreSQL holds only a rebuildable index: full text, trigram and link graph. Deleting the index loses nothing.
- Git history gives version history and attribution. Agent commits carry the agent identity and the job ID, human commits the member's identity.
- `index.md` and `log.md` in the LLM-wiki style are generated by the server, never hand-appended, so parallel work cannot conflict on them.
- A project whose GitHub repository is public can keep notes in a separate private notes repository instead. The notes screen states which repository and visibility apply.
- Notes never ship in the mod. HOI4 Factory builds every download, push target and future Workshop payload from an allow-list of mod content. Whether the Paradox launcher would upload a stray `.factory/` folder is unverified, so the allow-list is the safeguard.

**Frontmatter.**

| Field | Values | Rule |
|---|---|---|
| `status` | `confirmed`, `proposal`, `assumption`, `outdated` | Only a human can set `confirmed`. A confirmed note that contradicts newer source is flagged, never silently edited |
| `kind` | `lore`, `mechanic`, `convention`, `decision`, `reference`, `log` | Drives retrieval and templates |
| `refs` | Paths, symbols (`focus:IRE_economy`, `event:chaosx.nr39.1`), asset paths | Resolved by the Rust engine. Broken references are findings |
| `jobs`, `specs` | Job IDs and spec item IDs | Links notes to work and to P13 spec items |
| `authors` | Derived from Git, never typed | Attribution |

**Agent behaviour.**
- Agents retrieve notes through the C-06 context bundle as labelled data with no authority. Confirmed notes rank first, outdated notes are excluded unless asked for.
- After a significant change, the agent proposes note updates in the same job: new mechanics notes, updated references, `outdated` marks. A note last edited by a human is changed only through a proposed diff that the human accepts.
- Approved canon (SPEC-004) stays separate. A confirmed lore note can be promoted to canon through the existing design-proposal path.

**Relation to ADR-022 memory.** Memory stays automatic, page-less and about agent behaviour. Notes are explicit project documents that people browse and edit. A lesson about how to work belongs in memory. A fact about the mod belongs in notes.

## Jobs board

Decided in B2: keep it simple. The board starts small and gains fields only when real use asks for them.

**One tracker.** A job is the existing SPEC-003 task with a few board fields. A job can link to a GitHub issue. For a linked job, the issue's title, text, comments and open or closed state stay on GitHub (ADR-018) and are mirrored. Nothing is stored twice.

**Fields in the first version.**

| Field | Purpose |
|---|---|
| Short ID per project | Stable, never renumbered |
| Title and description | What the job is |
| Column | To do, in progress, in review, done |
| Labels | Free labels, also used for priority if a project wants it |
| Parent job | Simple subtasks |
| Blocked by | One kind of dependency. A job is ready when every job it is blocked by is done. Cycles are refused |
| Acceptance checklist | Items the reviewer ticks, with the verification results the agent recorded |
| Assignee | A member or an agent |
| Links | Branch, pull request, spec items, notes |
| Handoff | Free text with a short required outline (goal, state, done and verified, next step, open questions) |

**Views.** One board with columns and one filtered list. Agents propose jobs into a "proposed" lane that a member accepts or dismisses.

**Behaviour reused from SPEC-003.** Claims, leases and fencing stay as designed. After repeated failed attempts the job is marked blocked with a reason.

**Not in the first version.** Milestones, priority fields, typed dependency kinds, roll-up progress, GitHub Projects sync. Each can be added later if projects need it.

## No Drift Bot

Decided in B3: rejected. HOI4 Factory does not build a Drift Bot. What remains from that research is already covered elsewhere:

- **P13:** stable spec item IDs with origin tags, cited by handoffs, and a gap audit that lists spec items without implementation and new content without a spec item.
- **Visual review:** approved layouts and decisions are stored with their checkpoints, so a reviewer can compare a later render with the approved one.
- **Reports:** the research on drift tools stays in the appendices in case the question returns.

## Integrated Git experience

Recommended default, recorded for approval in the consolidated plan.

**Engine.** The `git` command line through the existing workspace crate. Every Git operation in workspaces passes `-c core.autocrlf=false`.

**Beginner vocabulary.** "Save point" for a commit, "agent's draft" for an agent branch, "keep this draft" for merge, "undo" for restoring a recorded save point. Advanced Git names appear behind a switch.

**Capabilities.**

| Capability | How |
|---|---|
| Create, clone, import | Existing Setup and GitHub import, plus "create a GitHub repository for this mod" under its own grant (ADR-014) |
| Branches and agent worktrees | One worktree per job on a task branch. Base SHA recorded. Branches that existed before a job are never deleted. A task branch is deleted only when the merged head equals its tip |
| Inspect changes | Semantic diff (focus added, prerequisite changed, localisation key changed) beside the raw diff and the finding delta |
| Selective staging | Hunks and lines through `git apply --cached --unidiff-zero` |
| Commits | Agents group changes into logical commits that cite spec items and the job. Unrelated user changes are never staged by an agent |
| History and undo | Operation log built on restore-point refs, so any recorded state can be restored |
| Reviews and pull requests | In-app review with line comments, approvals and merges on GitHub (ADR-018) |
| Conflicts | Detection with `git merge-tree --write-tree`, a per-region conflict chooser, and a structural HOI4-aware merge later on the Rust engine |
| Validation and CI | GitHub check results beside the factory's own evidence |
| Visual comparison | Before and after renders of focus trees and events. Image diffs in two-up, swipe, onion skin and difference modes, with DDS and TGA converted to PNG on the server |

## Onboarding and guided tours

Recommended default, recorded for approval in the consolidated plan.

- **First-run tour**, short and skippable, never part of sign-up (no extra sign-up steps).
- **Guided project creation** and **existing-mod import** as the first real tasks, using the Setup wizard with plain-language explanations.
- **Task-based tutorials** completed on a sample mod: create a focus, view its render, ask the agent to change it, review the diff, save. Each step is verified from server state, not from clicks.
- **Explanations** of autonomy levels, checkpoints, the review queue, jobs, Git save points and MCP tools as contextual help next to the feature, written as docs-as-code.
- **Engine:** in-house, on the Popover API and CSS anchor positioning, with a centered-card fallback for older browsers. Tours are versioned data tied to feature flags with `data-tour` targets. Seen-state is stored on the server, every tour is replayable from a help menu, and a CI test fails when a target or translation key disappears. Driver.js is the fallback if the in-house engine proves costly.
- **Accessibility and i18n:** dialog roles, focus management, keyboard control, all strings in the i18n files, no inline styles.

## Graphics and assets

Recommended default, plus FR-2.

- **Generation** goes through `hoi4-imagegen-mcp` (FR-2) as a broker tool profile in HOI4 Factory, with per-user and per-task budgets. The monthly operator allowance may be spent on images too (D-11), and users can bring their own provider keys or ComfyUI endpoint.
- **Pipeline** in Rust: preprocessing, transparency, frames and shine sprites, resizing, DDS and TGA export with headers the game accepts, deterministic validation against asset profiles, naming and placement, `.gfx` sprite registration, preview and approval, versioned outputs with a provenance manifest.
- **One profile source.** Asset category profiles (dimensions, format, alpha, naming, placement) live in one project-configurable file that extends the kit's existing `.tools/gfx/profiles.json`, rather than a second specification.
- **Layered sources.** Master PNGs, a versioned recipe and a receipt in Git, with OpenRaster as the exchange format for Krita and GIMP.
- **Review.** Visual review checkpoints for significant graphics choices, image diffs in the Git view, and an in-game DDS acceptance test before any compressed format is trusted.
