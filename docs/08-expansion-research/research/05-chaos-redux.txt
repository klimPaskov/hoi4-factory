# 05 - Chaos Redux workflow audit

Audit of the maintainer's Chaos Redux HOI4 mod workflow, written so later work can compare it with Hagane Works and design HOI4 Factory. Inventory and description only, with file-level evidence. Obvious gaps are noted in section 10 without proposals.

## 0. Method, scope, conventions

- Date of audit: 2026-10-31. Chaos Redux (CR) checkout: `<hoi4-mod-folder>\chaos_redux`, branch `master`, HEAD `c8782e065e` (committed 2026-10-25 22:00 +0200), 8,034 commits since 2025-06-06 (526 commits since 2026-10-12). The tree has the maintainer's uncommitted edits (seven modified files under `docs/plans/repo_cleanup/`, `docs/specs/102_serial_killer_specs/` and `sound/`, plus many untracked files such as new achievement DDS triplets). ## 0.1 Key findings (summary)

1. CR runs on a very large instruction layer: `CLAUDE.md` (459 lines, 59,920 bytes, ceiling 60,000), 26 skills (860,960 bytes of SKILL.md, plus references), 23 subagents (128,239 bytes). Claude Code is canonical since 2026-10-10 (commit `2218155273`); Codex/Cursor/Qoder/OpenCode files are generated. `AGENTS.md` is generated from `CLAUDE.md` by `.tools/sync/sync_instructions.py` through six phrase replacements (verified in sync).
2. The kit's `hoi4-*` skills are NOT generated from or auto-synced with the CR skills. Evidence points to a manual, mostly one-way "generalise CR into the kit" process (one earlier step went the other way: commit `f1e57f6c3f`, 2026-10-10, "Turn the generic HOI4 system skills into Chaos Redux system skills"). The only mechanical sync is 32 byte-identical tool files listed in `KIT:scripts/shared_tools.json` with CR as upstream.
3. The lifecycle is paper-heavy and ID-centric: workbook row -> external planning chat producing a ZIP of spec parts and prompt files -> import into `docs/specs/<NNN>_<slug>_specs/` with import review and hash evidence -> implementation under strict naming (`chaosx.nr<ID>.<n>`, `<NNN>_<slug>_*.txt`) -> temporary asset workspace -> event doc -> workbook + CSV export. No tool validates the spec package structure itself.
4. The deterministic layer (`.tools/check.py`) is strong on localisation, asset wiring, forbidden syntax, GFX geometry, generator freshness and regression tests. It has no static check for "event fired but never defined", "scripted effect/trigger called but never defined", or duplicate event/effect IDs. Those are left to the HOI4 Agent Tools MCP (`hoi4.script_validate`, `hoi4.event_inspect`) and the game's `error.log` through live testing (CR docs/testing/live_qa/20261003_full_playtest/bugs.md B001).
5. Done-ness is defined by honesty rules, not by a single gate: CLAUDE.md section 5 (lines 346-389) forbids completion claims while anything is simplified, missing or stale; a passing check proves only what it checks (line 343); live game testing is user-owned unless the user explicitly invokes `chaos-redux-debug-playtest` (lines 319, 355). No catalog row is `Playable` (0 of 155).
6. The maintainer's design taste is encoded as hard rules: no timid effects, varied costs instead of political power, dynamic everything, at most four persistent player-facing values, difficult multi-condition achievements, prose without em dashes, semicolons, staccato or "thesis/antithesis" hedging.
7. Multi-agent concurrency is a first-class concern: shared-index commit procedure with compare-and-swap `update-ref`, asset "claims" files, a three-heavy-agent cap, `keep-dirty-file` dispositions.
8. A planned "guardrails against unrequested changes" handoff (docs/plans/handoffs_2026-10-13/13_guardrails_against_unrequested_changes.md) has no matching section in `CLAUDE.md` and no `docs/plans/guardrails_2026-10-13.md`; see section 10.

## 4. Catalog conventions

- Event IDs: integers in the workbook (155 rows, IDs 1-166, with gaps); entry event `chaosx.nr<ID>.1` (CLAUDE.md:395), sub-events `chaosx.nr<ID>.<n>`, news events `chaosx.news.<n>` (030 README mentions `chaosx.news.33`); namespace declared with `add_namespace = chaosx.nr<ID>` at the top of each file (`events/001_communism_spread.txt:1`; several files can share one namespace, e.g. the three `events/030_time_traveler*.txt`).
- Event files: `events/<NNN>_<slug>[_<theme>].txt`, three-digit padding; shared or non-numbered files use leading underscore or subsystem names (`_chaosx_news.txt`, `_chaosx_easter_eggs.txt`, `biological_*_events.txt`, `cbrn_*`).
- Event-owned `common/` files follow `common/<kind>/<NNN>_<slug>_<kind>.txt` (ideas, decisions, decision categories, on_actions, scripted_guis, opinion_modifiers, dynamic_modifiers, scripted_effects, scripted_triggers, script_constants, mtth) (events SKILL 272-314). Shared systems use `chaosx_*` file names (`chaosx_on_actions_system.txt`, `chaosx_logic_effects.txt`). CLAUDE.md:295 says do not add the `chaosx` prefix to variable/effect names unless the surrounding context does.
- Flags and variables: `<event_slug>_<thing>` (e.g. `time_traveler_pact_refused`, `global.time_traveler_status`, `time_traveler_credibility`); global variables use the `global.` prefix; world-end uses `world_end` plus a scenario flag (e.g. `world_end_zombies`, `world_end_wendigo`). Shared tuning: `common/script_constants/<NNN>_<slug>_constants.txt` accessed as `constant:category.key` (CLAUDE.md:248).
- Localisation: `localisation/english/<NNN>_<slug>_l_english.yml`; keys `<event id>.t`, `.d`, options `.a`...; event names in `chaosx_event_names_l_english.yml`; no `:0` suffix; UTF-8 with BOM.

## 8. Chaos-Redux-specific versus generic

### 8.1 Chaos-Redux-specific design rules and systems

- Tone and prose: no em dash or semicolons; no dialectical hedging or thesis/antithesis constructions; no staccato; no empty dramatic filler; no pasting instruction text into game text; player-facing escalation text never labels itself a warning or threat, built from fear, missing people, rumours and repeated consequences; avoid paperwork/diplomatic-evasion mystery; humour calibrated to stakes with irony not cheap comedy for atrocities (events SKILL 122-165; event-planning 123-131, 557-567; `references/player-facing-text-direction.md`).
- Chaos design: Chaos Meter feedback is a core contract (event-planning 360-363, 537; references/advanced-chaos-generation-design.md); chaos tiers 1-6 (Calm World ... World Collapse, thresholds such as 200/400/600/800/1000+ in the 030 README); baseline stages are distinct from evolutions, at most five evolutions, one per chaos tier (337); evolution state itself gives zero Chaos (events SKILL 212); world-end scenarios need chaos above 1000 and the `world_end` flag guard (228-233); special chaos countries may be deliberately overpowered (event-planning 498-500); no more than four persistent player-facing values (394); effects must be strong, not 2-3% dust (475-502); costs beyond political power (396-421).

- Event plumbing: event log, Event Details, evolution catalog, cluster arrays, world-end registry, triggerable scenarios (events reference files), CXT test country, CBRN, camps, civilian transfer ledgers, formable state puzzles.
- Asset policy: flags always generated flat from cited designs; historical leaders never generated; grounded polities get sourced portraits with a user-supplied HOI4-style final (RunPod user-run); super-event audio/quotes sourced and documented (events SKILL 103; super-events skill).
- Process: parent-owns-completion, user-owns-live-testing, "assume the game has been reloaded; do not ask for logs" (CLAUDE.md:319), no AI attribution in commits (457), project-specific MCP set (`.mcp.json`).
