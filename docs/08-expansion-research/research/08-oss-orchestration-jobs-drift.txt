# Research 08: Open-source orchestration, jobs, drift and worktree tooling for HOI4 Factory

Date accessed: 2026-10-31. Read-only research. Nothing was cloned, installed, built or run. All evidence came from `gh api` (file contents, metadata, compare), WebFetch and WebSearch. No paid model calls. Licenses were read from LICENSE files (or Cargo.toml / package metadata) where GitHub's detector said NOASSERTION.

Legend for "Depth" in the tables: Code = I read source files; Docs = I read project documentation pages; README = README only; Meta = repository metadata and license only.

---

## 0. Bottom line

1. No new runtime dependency is justified for jobs, orchestration, worktrees or drift. Every candidate is either a different runtime (Go + Dolt, Electron, tmux TUIs, Dagger), a different storage engine, a license problem, or abandoned. The useful content is invariants, field lists and UX patterns, which are cheap to build natively on PostgreSQL and the existing `git`-CLI workspace crate (`crates/workspace`, "git CLI only").
2. Beads is the best model for the task graph (typed edges, ready-work rule, atomic claim, lease/heartbeat/reclaim with a grace window). Adopt its invariants, not its code, CLI, Dolt backend, hash IDs or its last-write-wins tracker sync. The HOI4 Factory plan (lease + fencing generation) is already stronger than Beads' reclaim, which has no fencing of the old owner.
3. Gas Town and Gas City: nothing changed that alters the earlier verdict. Gas Town has had 7 commits since the pin and no release since 2026-06-06. Gas City's v1.5.1 notes (2026-10-24) fix the same hazard class the plan already guards against (releasing claims the controller cannot vouch for). Keep adapting invariants only.
4. Blacksmith is a one-author, 30-commit, Unix-only Rust CLI that requires `bd` and the `claude` CLI, last touched 2026-03-05. Reject as a dependency. Three small ideas are worth adapting: glob "affected sets" for conflict-aware scheduling (plus a post-hoc comparison against the real diff), single-flight integration with a bounded fix-attempt circuit breaker, and a periodic reconciliation run that flags the last N integrations.
5. Pane is an Electron desktop app (AGPL-3.0 plus extra UI-attribution and naming terms). Reject. Adapt its nine-section handoff note, its "agents ask through a notify tool" pattern and its status cues.
6. Of the orchestrators, the data models worth reading are vibe-kanban (Rust + Postgres issue schema, now sunsetting by the vendor but still committed to by a small group), Backlog.md (task file fields: acceptance criteria, Definition of Done, plan, notes), Plane (state groups, relation vocabulary) and agtx (Rust; shows autonomy modes as policy over one board, and two anti-patterns). Reject Claude Squad, Crystal, uzi, Sculptor, container-use, OpenHands, Task Master, Huly, Conductor as dependencies, each for a stated reason.
7. Drift Bot as documented is narrow: a PR/MR reviewer that compares changed code to Blueprints and Requirements, posts one summary comment plus a few inline comments, and sets a pass/fail `drift-bot` commit status. The docs say nothing about how detection works, severity, false positives, suppression or approval of intentional deviations. Plan the product's own version with: versioned requirement IDs and a "stale" state (Tracey), a findings table with categories and caps (spec-kit analyze), CRITICAL/WARNING/SUGGESTION plus "not applicable is not skipped is not failed" (OpenSpec verify), a baseline/budget with justified bumps for accepted deviations (ArchUnit freezing, Imbue ratchets), and a rule that only deterministic checks can fail a gate.
8. Git: keep the git CLI. gitoxide cannot yet do checkout/merge/rebase/push or move/remove/repair of linked worktrees; libgit2 (git2-rs) can add/lock/prune worktrees but diverges from CLI behavior; jj is a different VCS. Adopt cleanup invariants (never delete a pre-existing branch; delete a task branch only when its merged PR head equals the branch tip or merging adds nothing; record the base SHA; per-task target branch). Mergiraf (GPL-3.0-only, separate process) is an optional later add for JSON/YAML/TOML/Rust/TS conflicts. It has no Clausewitz support.

## 2. Beads and Gas Town: model, ready work, handoff, molecules, sync, and what to adopt

### 2.1 Beads issue model (docs/architecture/index.md, docs/core-concepts/*)
Fields on every issue: `id` (content-derived hash such as `bd-a1b2`, extended on collision), `title`, `description`, `design`, `acceptance_criteria`, `notes`, `status` (`open`, `in_progress`, `blocked`, `deferred`, `closed`, `pinned`, `hooked`, extendable), `priority` 0-4, `issue_type` (bug, feature, task, epic, chore, decision, message, molecule, gate, spike, story, milestone), `assignee`, `estimated_minutes`, timestamps, `created_by`, `closed_at` + `close_reason`, `external_ref` (for example `gh-9`), free `metadata` JSON, labels, typed dependencies, comments. Field groups for scheduling (`due_at`, `defer_until`), claim leasing (`lease_expires_at`, `heartbeat_at`), gates (`await_type`, `await_id`, `timeout`), and molecule/wisp state (`ephemeral`, `mol_type`, `bonded_from`). Internal-only: `content_hash` (SHA-256 of canonical content, for change detection).

### 2.2 Dependency edges and "ready work"
- Blocking edge types: `blocks` (default), `parent-child` (children blocked when the parent is blocked), `conditional-blocks` (runs only if the other fails), `waits-for` (waits for all or any children of a spawner; `gate` metadata `all-children` or `any-children`).
- Non-blocking, annotation only: `related`, `tracks`, `discovered-from`, `caused-by`, `validates`, `supersedes`; also graph-link types such as `duplicates`, `replies-to`.
- Ready work = claimable status (open plus any custom status whose category is "active") with no open blocking dependency, not deferred (`defer_until` in the future, including children of a deferred parent), and not held by a gate. Filters: priority, label, assignee, unassigned, type, parent descendants, sort.
- Cycles are rejected at write time by `bd dep add`; bulk wiring can skip per-edge checks but still runs one final whole-graph check before commit.
- `is_blocked` is a denormalized, recomputed column. blocked_state.go contains a comment about a case where one close took about 39 seconds to recompute on a 50k-issue / 100k-edge database until the correlated EXISTS queries were split per index. There is also a `recompute-blocked` command and a blocked-consistency checker. Lesson: derive readiness with indexed queries on demand, and only denormalize if measured, then in the same transaction plus a consistency check.
- Gates are issues: types `human` (closed only by explicit resolve), `timer`, `gh:run`, `gh:pr`, `bead`. A gate blocks its waiter through a normal dependency edge, so no polling by agents.

### 2.3 Claim, lease, reclaim (internal/storage/issueops/claim.go, lease.go; docs/cli-reference/reclaim.md)
- Claim is compare-and-swap inside a transaction: allowed when the issue is claimable and unassigned, already assigned to the same actor (idempotent re-claim), or assigned to a configured pool alias; otherwise a typed "already claimed" error. Every status/ownership mutation rewrites a random `row_lock` cell so concurrent reclaim and close collide instead of cell-merging (a Dolt-specific hazard; Postgres gets this from row locks / expected-version).
- Lease: default 5-minute TTL, kept alive by a heartbeat that does not touch the issue row (it lives in a separate ephemeral table to avoid commit bloat and merge conflicts). A dead worker's lease goes stale; `bd reclaim` reverts `in_progress` to `open` only after the lease expired by more than a grace window (the doc suggests about 2x the TTL), clears the assignee and records a recovery event. A lease is only meaningful on the replica that granted it; reclaim skips foreign leases unless forced.
- Gap relative to HOI4 Factory: reclaim does not fence the old owner's later writes. The plan's fencing generation and effect-boundary check is the stronger design; keep it.

### 2.4 Handoff fields
- Beads has no dedicated handoff object. Handoff-relevant fields are `design`, `acceptance_criteria`, `notes`, `metadata`, `close_reason`, `discovered-from` edges, and a `bd prime` context command.
- Gas Town models a handoff as a pinned bead titled "<role> Handoff" whose description holds the content, and `gt handoff --collect` gathers hooked work, inbox, ready beads and in-progress items. The rendered template carries role, current work, status, git branch, dirty flag, pending mail count, ordered next steps, notes. Any molecule on the hook auto-continues in the fresh session.
- Pane's note (section 5) is the more complete field list and is the one to copy.

### 2.5 Molecules and formulas
Formula (TOML or JSON: `formula`, `version`, `type`, `[vars.*]` with `required`, `[[steps]]` with `id`, `title`, `needs`, `type = "human"`) is cooked into a proto (template epic with `{{vars}}`), then poured into a molecule (persistent beads) or a wisp (ephemeral beads, purged later). Steps flow through ready-work like any other issues. Adoptable idea: a project-level "workflow template" is just a DAG of tasks with variables and human-approval steps; it needs no new engine, only a template table and an instantiate-in-one-transaction function. Defer until the plain task graph is stable.

### 2.6 Sync design
- Beads internal sync: Dolt push/pull with history under `refs/dolt/data` on the git remote. HOI4 Factory has PostgreSQL as the system of record, so none of this applies.
- External trackers (`bd github|gitlab|jira|linear|ado|notion`): bidirectional sync, conflict policy flags `--prefer-github`, `--prefer-local`, `--prefer-newer` (the default). Last-write-wins by timestamp is the opposite of "GitHub stays authoritative". Do not copy the default.
- GitHub REST now models what the mirror needs natively (docs.github.com, API version header shown as 2026-03-10): `blocked_by` / `blocking` issue dependencies (POST body takes an `issue_id`; GET lists in both directions, 100 per page max), sub-issues (same repository owner as the parent; reorder endpoint), `sub_issues_summary` and `issue_dependencies_summary` fields on issues. Write endpoints warn about secondary rate limiting when called quickly. Map `blocks` to blocked_by and `parent-child` to sub-issues; keep non-blocking edge kinds local-only or as labels.

### 2.7 Gas Town items worth adapting
- Convoy vs swarm: a persistent tracking unit versus the ephemeral set of workers currently assigned. HOI4 already separates task from attempt; keep the separation explicit in the UI as well.
- Mountain-Eater design note ("No Agent Holds the Thread"): state is derived from the graph on each check ("Discover, Don't Track"); after N failures on the same issue it is marked blocked, skipped, and the next ready work is fed; stranded convoys (ready work, no worker) are detected on a periodic scan. Stage-launch validates the DAG and computes waves with Kahn's algorithm.
- Refinery (internal/refinery/batch.go): batch-then-bisect merge queue; defaults max batch 5, wait 30 s, retry the whole batch once before bisecting to avoid blaming an innocent MR for a flaky test; MRs blocked by MRs outside the batch are excluded. Too large for hobbyist scale; record as a later option.
- Do not adopt: tmux role provisioning, role zoo (Mayor, Witness, Deacon, Dogs, Polecats), federation, Wasteland. CONTRIBUTING documents a refinery/fork-routing limitation, a reason not to import automatic merge policy wholesale.

### 2.8 Data-model invariants to adopt for Rust + PostgreSQL (consolidated, with source)

Task graph
1. Typed edges; only a small closed set affects readiness (`blocks`, `parent-child`; later `waits-for`, `conditional-blocks`). Informational kinds (related, discovered_from, validates, supersedes, duplicate) never block. [Beads]
2. Reject cycles in the same transaction as the edge insert (advisory lock per project plus recursive-CTE check; bulk import does one whole-graph check at commit). [Beads]
3. Ready = status category is claimable AND no open blocking edge AND no unresolved gate AND not deferred (own or ancestor) AND dependencies satisfied by the explicit rule below. A blocked parent blocks its children. [Beads]
4. Derive readiness from indexed queries or a view first; denormalize only after measurement, in the same transaction, with a consistency checker. [Beads blocked_state.go]
5. A dependency is satisfied only when the target is completed and accepted. A missing target fails closed (task stays blocked with `blocked_reason`). Do not copy agtx, where a dependency in Review counts as done and an unknown dependency id counts as satisfied (src/db/schema.rs `deps_satisfied`), and where dependencies are a comma-separated string.
6. Claim = compare-and-swap on expected task version; idempotent for the same owner; typed `already_claimed` error; a claim creates the attempt row and lease in one transaction. [Beads, matches SPEC-003]
7. Lease heartbeats live outside the hot task row; reaper acts only after TTL plus grace (about 2x TTL), writes a recovery event, and never re-queues work with an `unknown_effect` attempt. Fencing generation stays. [Beads + Gas City]
8. Status names are configurable but each maps to a fixed category (Plane: backlog, unstarted, started, completed, cancelled, triage; 8090 work orders use five of these) and all logic keys on category. [Plane, 8090]
9. Same-transaction event row for every transition (already in SPEC-003).
10. IDs: UUID primary key plus a human-readable sequential short ID allocated in the transaction by `UPDATE counter ... RETURNING`. Choose the counter scope once. vibe-kanban started with a per-project counter and later shipped a migration that renumbered every issue to a per-organization counter and backfilled denormalized notification payloads (crates/remote/migrations/20260313000000). Keep `external_source` + `external_id` (Plane) or `external_ref` (Beads) for the GitHub mapping; GitHub numbers are per repository. Hash IDs (Beads) solve offline multi-writer creation, which the hosted design does not need.
11. Task <-> PR is many-to-many, unique on (pr_url, project) (vibe-kanban 20260316 migration).
12. Sortable board order: floating `sort_order` per column (vibe-kanban `sort_order DOUBLE PRECISION` and `parent_issue_sort_order`; Plane `sort_order` float default 65535) with occasional rebalance.
13. Acceptance criteria as an ordered checklist (item text + checked flag), a separate reusable Definition-of-Done checklist, an implementation plan section and an implementation notes section, `references`, `documentation`, `modified_files`, `milestone`, `ordinal`, `type`, `parent_task_id`. [Backlog.md serializer.ts]
14. Verification results are rows with claim, command, exit code, revision tested and evidence reference, and a task cannot complete on an unproven claim ("phantom completion" check: file exists, diff present, symbol pattern, dead-code check, per spec-kit-verify-tasks). [verify-tasks, SPEC-003 completion policy]
15. Skip-after-N-failures and circuit breaker: after N failed attempts or integration fix attempts, mark `blocked` with a reason and escalate; work flows around it. [Gas Town witness/mountain-eater, Blacksmith CircuitBreaker]
16. Roll-ups (epic progress) are computed from the graph on read, not stored (GitHub's `sub_issues_summary` follows the same idea). [Gas Town, GitHub]
17. Waves: validate the DAG and compute launch waves (Kahn) for "run all ready tasks" and for the Kiro-style "independent tasks in parallel". [Gas Town, Kiro docs]
18. Handoff record (structured, required fields): goal and definition of done; current state; done and verified (command, result, commit); in progress (quote failures exactly); next steps (first one concrete); decisions and constraints (including approaches that failed); open questions; how to verify; git state (repo, branch, head SHA, pushed, uncommitted files that matter). Reject a handoff with a missing or empty field ("None" allowed). The host rewrites the git-state header at send time so it is never stale, and appends receiver instructions (check head commit, run verify, continue from next steps). [Pane note-template.md; Gas Town template]
19. Autonomy modes are a policy table on one state machine, not three machines: checkpoints such as `spec_approved`, `plan_approved`, `diff_reviewed`, `merge_approved`, each `auto | ask | skip` per mode and per project. Backlog.md names the same three review points (spec, plan, code). agtx ships a human-in-the-loop `void` plugin and an unattended `oneshot` skill over the same board. [Backlog.md, agtx]

## 3. Blacksmith (https://github.com/ozten/blacksmith)

Facts: SHA 6bb0015f1250709bee5214af7e6fb603048e6899, committed 2026-03-05. License MIT (LICENSE read, copyright Austin King). Rust, edition 2021, version 0.1.5. 1 star, 0 forks, 0 open issues; all 30 commits by one author over 2026-02-14 to 2026-03-05. Dependencies include tokio, axum (optional), rusqlite (bundled SQLite), clap, nix (Unix-only), fs2, zstd. The README says it depends on `bd` (Beads) for tasks and `claude` for `blacksmith init`, and that its API is unstable. It runs a supervised agent loop (watchdog for stale sessions, retry/backoff, STOP-file shutdown, metrics in SQLite), optionally with parallel workers in git worktrees. Docs index links to pages that are absent from the tree (only five doc files exist). Its companion `ozten/speck` (spec-driven planning, 0 stars) says "Not Ready for Use".

From code (Depth: Code):
- scheduler.rs: ready beads (open, all deps closed) are filtered by overlap of `affected:` globs declared in the bead's `design` field against in-progress work; overlap is a conservative literal-prefix test (empty set = "affects everything"); a bead without an affected set is allowed to run in parallel and conflicts are caught at integration. SPEC-v7 lists the three failure modes it wants to fix: missing, wrong, and stale-after-refactor affected sets.
- worktree.rs: directory `worker-{worker_id}-{bead_id}`, created with `git worktree add --detach <path> <base>` (no branch is created, so there is no branch to clean up), removed with `git worktree remove --force` plus temp-file cleanup.
- integrator.rs: one integration at a time. Merge main into the task branch (never push the branch to main), apply a task manifest for shared files, run compiler checks, on failure run an integration agent up to 3 attempts, then trip a per-bead circuit breaker and escalate to a human, then fast-forward main. A reconciliation tracker runs the full suite every N successful integrations and flags the last N beads for review if it fails. A rollback path exists.
- Architecture analysis (fan-in, god files, circular imports, boundary violations on `use crate::`) is a small regex/import-graph analogue to ArchUnit for Rust.

Overlap with HOI4 Factory: partial (scheduling, integration queue). Integration cost to depend: high (a CLI, SQLite per project, requires Beads and a CLI agent, Unix-only, unstable API, no library surface).

Recommendation: REJECT as dependency. ADAPT (a) affected-set scheduling, but invert the default for hobbyist mod repos: a task with no declared path set conflicts with everything, and after each attempt compare the declared set to the real diff and record "scope drift" as a finding; (b) the integration pipeline order and bounded fix attempts; (c) the every-N reconciliation run.

## 4. Pane (https://github.com/greenfield-inc/Pane)

Facts: SHA 212ea64a59652cec8f90d40ccd7d2beb2e25d282, committed 2026-10-31; latest release v2.4.212 (2026-10-31). 594 stars, 234 forks, 203 open issues, about 26 contributors but 87 of the last 100 commits are by one author. TypeScript (Electron `main/`, React `frontend/`, native module, mobile app, glasses client). GitHub detects NOASSERTION because the LICENSE is AGPL-3.0 with Section 7(b) additional terms: visible attribution to the owner in the application UI, and no use of the owner's name or logo (and the former name "foozol") for endorsement.

What it does: a terminal-first desktop manager for any CLI agent. Each "pane" is one worktree + branch + agent. Features: remote host daemon reachable from a phone browser, "workspaces" to run commands on other machines over Tailscale, `runpane handoff`, a notify MCP tool (agents ask questions through a tool; the answer is returned as the tool result), status cues (blocked on approval, working, done), "Loops" (cron-scheduled agent runs, each in a fresh worktree, at most hourly), per-pane isolated port ranges, `.env` mirroring.

Handoff (Depth: Code/skill docs): the nine required sections are Goal, Current state, Done and verified, In progress, Next steps, Decisions and constraints, Open questions, How to verify, Git state. The CLI rejects a note with a missing or empty section, rewrites the front matter (origin machine/pane/session, repository, branch, head SHA, remote, pushed) at send time, appends receiver instructions (verify the head commit, run "How to verify", continue from "Next steps", push without force, report back to the sender), and for same-agent handoff checks the receiver actually resumed the session (`continued`, `inconclusive`, `not-continued`, `fresh-agent`).

Overlap: UI patterns only. Integration cost: not integrable (desktop Electron app, Tailscale/remote-daemon model, attribution term).

Recommendation: REJECT. ADAPT the handoff schema and the "verified resumption" check (a handoff is not done until continuation is confirmed or a fallback is accepted), the ask-through-a-tool pattern for `waiting_for_input`, and the three-state status cue.

## 6. Drift Bot (8090 Software Factory) and open-source analogues

### 6.1 What the 8090 documentation says Drift Bot does (verified by reading the page text of docs.8090.ai/codebase/overview and related pages; changelog read for dates)
- Scope: reviews pull requests (GitHub) and merge requests (GitLab) on a connected repository. It checks the changed code against the project's Blueprints and Requirements and flags code that contradicts a Blueprint or Requirement and code that none of them cover yet.
- Triggers, both off by default: "On commit to branch with open PR" (when a PR is opened or receives new commits; drafts are skipped until ready for review) and Manual (a `/driftbot` comment on the PR; stays enabled whenever the first option is on).
- Output: one summary comment that lists each possible drift finding with the Blueprint or Requirement concerned and the file and lines, or states that no drift was found. The most important findings also get their own line comments. A `drift-bot` commit status passes with no drift and fails when drift is found or the run fails. Changelog: introduced 2026-06-09 (v0.40.0), inline review comments 2026-06-16 (v0.41.0), anchored comments limited to the top two findings per PR 2026-07-01 (v0.43.0).
- Access and ownership: each run uses the access of the person who triggered it (PR author on GitHub; the person who opened or updated the MR on GitLab; the commenter for manual runs), who must be an organization member with a linked GitHub or GitLab account. Only one project per repository can enable it. Saving settings needs the Codebase Connection Editor permission (built-in Owner and Editor roles).
- The surrounding model: Requirements (product overview and per-feature requirements) -> Blueprints (technical specs in Container, Component and Feature categories) -> Work Orders (tasks with acceptance criteria, dependencies, phases, linked PRs) -> code. Blueprints hold code links (repository files and line ranges), which the agent creates when authoring or reverse engineering and which Detect Code Drift updates.
- Separate push-time automations (not Drift Bot): Detect Code Drift (runs after the repository is reindexed on a push; compares changed files with the code linked to blueprints; leaves drift comments on the blueprint and on the linked feature requirements; updates code links), Sync Blueprints and Requirements, Check Blueprint References. They have the run-as user's permissions, cannot create or edit blueprints, requirements, work orders, feedback or themes, and their comments carry the user's name plus "via" and the automation name.
- Guidance in the docs: drift comments are evidence to investigate, not instructions; only behavior the code contradicts counts as drift and features not yet built do not; resolve each comment thread once document or code is back in line; work orders do not update themselves when blueprints change, so ask the agent to review them. Early changelog entries (2025-11-16 "proactive drift detection", 2026-04-28 drift as comments with sync flows treating those comments as the source of truth) show the design evolved from push-time comments to PR-time review.

### 6.2 What is not documented
- How detection works (static analysis, LLM judgment or both), which model, confidence, cost or rate limits for PR runs.
- Severity levels, ranking criteria for "most important", false-positive handling, dismiss/ignore/baseline.
- Any approval path for intentional deviations. The closest features are resolving a comment thread and accepting or rejecting tracked suggestions on a spec. The changelog states nothing on exceptions or approved deviations.
- Whether a failing `drift-bot` status is intended to block merges (branch protection is not discussed), and how re-runs and force-pushes behave.
- How "code that no spec covers" is separated from incidental code (tests, refactors, tooling).

### 6.4 Design proposal for the product's Drift (synthesis, not a quote of any source)
Treat drift as findings produced by checks against approved, versioned requirement records, in this order of authority:
1. Deterministic checks (fail-able): each requirement has a stable ID and integer version; each task, artifact or test link names `id+version`; a link at an older version is `stale`; a requirement with no accepted link is `uncovered`; an artifact path with no requirement is `unspecified` (warning). Machine-checkable predicates evaluated by the existing HOI4 tools (for example: this focus exists, has this prerequisite, parses with no validator errors) are `verified` or `contradicted` with the tool's evidence reference.
2. Model-judged checks (advisory only, never fail a gate): "possible drift: evidence to investigate", with a confidence label, the same wording the 8090 docs use.
3. Findings carry stable IDs by category (as in spec-kit), severity (CRITICAL / WARNING / SUGGESTION), spec reference with version, artifact path and range, evidence, status (open, accepted_deviation, resolved, unavailable, not_applicable), cap on inline anchors (8090 uses two), one summary plus one pass/fail status per run, comment-only authority (the checker never edits specs or code; resolution is a code change, or a spec change through a tracked proposal).
4. Intentional deviation: a `deviation` record keyed by finding fingerprint (requirement ID + version + artifact anchor), with reason, approver and role, optional expiry, and link to a decision. It lapses automatically when the requirement version or the artifact anchor changes, so exceptions cannot rot. This takes the baseline idea from ArchUnit freezing and the justified-bump idea from ratchets, and fills the gap 8090 leaves undocumented.
5. Trigger and gating by autonomy mode: autonomous = run on every attempt completion and before merge, deterministic CRITICAL blocks merge; semi = same checks, block only at configured checkpoints; human-in-the-loop = run on request and at review. Skip draft or in-progress work. One drift policy per project.

Recommended git/worktree policy (adopting the above; no new dependency):
- One worktree per attempt-owning task under a server-controlled root, never inside the repository, named from task short ID and a unique suffix (claude-squad, Blacksmith). Prefer a named branch `<owner>/<task-id>-<slug>` sanitized for illegal characters (a Windows domain user produced a backslash in claude-squad's case) for tasks that open PRs; use detached worktrees for read-only or scratch attempts.
- Record at creation: repo, base branch, base commit SHA, branch name, whether the branch pre-existed, target branch for this task.
- Cleanup: never delete a branch that pre-existed; after merge, delete only if the merged PR's head SHA equals the branch tip (gtr) or merging adds no changes to the target (worktrunk); otherwise keep and mark `needs_attention`. Refuse removal with untracked or uncommitted files unless the task is cancelled and the owner confirms. A policy enum `never | when_safe | always` per project, default `when_safe` (Sculptor).
- Agent branches live in their own ref namespace or remote so a human branch is never touched, and a human reviews by checking out (container-use).
- Integration: single-flight per target branch. Merge target into the task branch, run gates, bounded fix attempts, then fast-forward or squash through the GitHub PR (GitHub stays authoritative for the merge). Run a reconciliation suite every N merges (Blacksmith). Batch-then-bisect (Gas Town) is deferred until a measured queue exists.
- Locks: use `git worktree lock` with a reason for active attempts and `prune` only after the lease has expired, to avoid removing a live worktree (git2-rs exposes the same operations; the CLI has them too).

## 10. Questions for the maintainer (batch)

1. Short task IDs: per project or per account? (Recommend per project, never renumbered; show the GitHub issue number alongside once mirrored.)
2. Is "dependency satisfied" equal to completed-and-accepted, or merged? (Recommend accepted; the PR merge is an effect of acceptance.)
3. Default for a task with no declared path set when parallel agents exist: serialize against everything (recommended) or run optimistically (Blacksmith)?
4. Drift gating: may a failed deterministic CRITICAL drift check block merge in semi-autonomous mode, or only warn? Who may approve a deviation (owner only, or any member with a role), and should deviations expire?
5. Branch cleanup default: `when_safe` (recommended), `never` or `always`?
6. Is a GPL-3.0-only helper binary (Mergiraf) acceptable inside the tool container image if structural merge is added later? And for Clausewitz script, should a custom merge driver built on the existing HOI4 parser be considered instead of a tree-sitter grammar?
7. Should the GitHub mirror support Projects v2 fields (priority, status columns) in the first release, or only issues, sub-issues and dependencies? (Projects v2 was not researched in depth here.)
