## 1. Key findings

1. The kit has three generators plus one checker, all in `.tools/sync/`: `sync_instructions.py` (CLAUDE(_template).md to AGENTS(_template).md), `sync_agents.py` + `agent_sync_common.py` (agents to Codex/Cursor/Qoder/OpenCode plus maps), `sync_skills.py` (skills to `.agents/skills` and `.qoder/skills`), and `check_guidance_size.py`. Config: `instruction_projection.json`, `agent_profiles.json`, `read_limits.json`. There are no other tools in that folder.
2. Nothing runs the generators automatically. No Claude Code hook (`.claude/settings.json` has only `permissions.deny` for `.env`), no Codex/Cursor/Qoder/OpenCode hook, no git hook, no pre-commit config, no `core.hooksPath`. The only triggers are prose in `CLAUDE_template.md:167-175`, `HOI4 Mod Setup` running `check.py setup` after install/update/repair, `check.py quick|full`, and two GitHub workflows.
3. `sync_skills.py --check` passes vacuously in the source repo and in CI: the mirrors are gitignored (`.gitignore:23-26`), so the tool prints "No skill mirrors exist..." and exits 0 (observed). CI therefore cannot detect a stale skill mirror, and the tool's drift logic is not exercised by any test (the only callers are a live-tree `--check` in `scripts/test_agent_sync_contract.py:148` and a stub in `.tools/tests/test_setup.py:51`).
4. Agent add, modify and remove are detected correctly by `sync_agents.py --check` (observed in simulation, section A4). Two friction points: `scripts/test_agent_sync_contract.py:82` hard-codes `len(agents) == 23` (plus `EXPECTED_TIERS`/`READ_ONLY` at 22-35), which contradicts `.tools/sync/README.md:30` ("adding an agent never requires editing a script"); and a non-Haiku agent needs a `tier_policy` entry in `agent_profiles.json` or `--verify` fails.
5. "Never hand-edit generated files" is enforced nowhere. `--check` reports the same `DRIFT` line whether canonical or generated was edited, and a plain sync run silently overwrites a hand edit (observed). AGENTS.md has no generated marker: the only text is `CLAUDE_template.md:11` (stripped by the installer with the Placeholder Guide) and `:162`.
6. GitHub: `main` is not protected and there are no rulesets (`gh api`: "Branch not protected", `[]`), so no CI result is a required check. Both workflows run the sync checks (Validate on every pull request and on path-filtered pushes, Publish after every push to main), but a failure cannot block a merge.
7. Installed mods have no CI and no git hook: the manifest installs no `.github` or `.git*` files (0 matches). The only automatic protection there is Setup's finishing step (`check.py setup` runs the three synchronizers in write mode) and whatever the agent chooses to run.
8. Setup constraints that any design must respect: it rejects a repository whose local `.git/config` sets `core.hooksPath` (`hoi4-mod-setup/src-tauri/src/git.rs:1420`, test at `:3210`); `check.py setup` may rewrite only `.gitignore`, `AGENTS.md`, `.claude/agent-map.md`, `.tools/quality_baseline.json` and files under `.codex/ .cursor/ .opencode/ .qoder/ .agents/` and any other tracked change is refused (`src-tauri/src/agent_setup.rs:33-43`, `docs/15_update_repair.md` "Development tools step"); a settings.json change flows through the `runtime.claude` component (replace_if_unmodified).
9. CR has its own divergent copies. Notably CR's `sync_agents.py` has no `--check` (only `--verify`, which compares model and effort), and CR's `.codex/config.toml` has 20 `[agents.*]` rows for 23 canonical agents: `chaosx_equipment_units_worker`, `chaosx_map_states_worker`, `chaosx_technology_tree_worker` are missing (observed). That is a live example of a silently stale projection.
10. Smallest design that meets all seven criteria (section A5): one declarative generator registry (path to generator, with `needs` ordering), one shared runner reused by `check.py` (`generators` check, a new write mode, `setup`), one Claude Code `PostToolUse` hook that runs only the affected generators, one CI step that runs the same check plus a required-status-check rule, deny rules for generated paths in `.claude/settings.json`, a fix for the vacuous skill check, and a Factory job-completion check using a pinned copy of the tool. The Chaos Redux engine-skill generator becomes one more registry entry, ordered before the skill mirror.
11. Part B: the kit has no consultation rule. The nearest rule is `CLAUDE_template.md:365` ("ask a focused question" when an indispensable input is missing), which is reactive and mid-task, and is copied verbatim in CR (`CLAUDE.md:328`). The template has 55 bytes of headroom under its 60,000-byte ceiling (59,945 bytes), so any new rule must land together with the P11 slimming. Placement, wording outline, per-project records, autonomy behaviour and conflicts are in Part B.

Behaviours that matter for the design (read in source):

- `--check` modes: instructions prints `DRIFT:` (exit 1); agents prints `DRIFT:`/`STALE:` per file (exit 1) and `ERROR:` for malformed frontmatter (exit 1); skills prints `DRIFT:` per skill (exit 1) but exits 0 with a note when no mirror exists (`sync_skills.py:110-113`); guidance prints `OVER:`.
- `sync_agents.py` maintains a runtime only when its folder (or map) exists (`runtime_present`, `agent_sync_common.py:317-322`), and deletes only files carrying its marker whose canonical agent is gone (`generated_files`, `:308-314`).
- `sync_agents.py --verify` adds the tier/effort policy check from `agent_profiles.json` and then reuses `synchronize(check=True)` (`:357-387`).
- `sync_skills.py` compares raw bytes (`filecmp.cmp(shallow=False)`); the other two normalise CRLF to LF before comparing. (inference: on Windows with `core.autocrlf=true` a CRLF canonical skill versus an LF mirror written by Setup would report drift; not reproduced.)
- None of the tools accepts a root path (`MOD_ROOT` is derived from the script location: `sync_instructions.py:26`, `sync_skills.py:31`, `agent_sync_common.py:34`) or a per-item scope (no `--skill`, no `--agent`).
- Timing on this Windows machine: instructions check 234 ms, agents check 956 ms, skills check 206 ms with no mirror, guidance 132 ms, bare Python start 98 ms. With a full 52 MB mirror (sim2, 32 skills, 890 files) `sync_skills.py --check` takes 3.6 s and an unchanged write run 0.5 s.

`check.py` (the repository check suite) wraps the tools: `GENERATORS` (`.tools/check.py:138-145`) maps three generators to input prefixes; `guidance` is a separate check (`:207`). `.tools/lib/setup.py:34` has its own `SYNCHRONIZERS` tuple. These are two hard-coded copies of the same knowledge (plus the CI step list and RELEASING.md): four places to update when a generator is added.

## A4. The seven acceptance criteria today

Evidence from the simulations (scratch copies; kit untouched):

- T1 append a line to `CLAUDE_template.md`, run `sync_instructions.py --check`: `DRIFT: AGENTS_template.md differs from the projection of CLAUDE_template.md.` exit 1. Plain run regenerates. Hand-edit `AGENTS_template.md` instead: identical DRIFT message, exit 1; a plain run then silently removed the hand edit (T1b).
- T2 edit a skill with no mirror: `No skill mirrors exist ...` exit 0. After `--target agents`, a changed skill gives `DRIFT: .agents/skills/hoi4-mtth: changed SKILL.md` exit 1; a new canonical skill gives `missing SKILL.md` exit 1.
- T3 add an agent: DRIFT for 9 outputs (the TOML, `config.toml`, three markdown agents, four maps); remove it: `STALE:` for the four generated agent files and DRIFT for config and maps; malformed file: `ERROR: canonical agent definitions need fixing: bad.md: the file must start with a '---' frontmatter block` exit 1; body-only edit: DRIFT on that agent's four files and the maps; a Sonnet agent with no `tier_policy` entry: `--verify` exit 1 with "model is sonnet; policy requires haiku".

| # | Criterion | Met today? | Why |
| --- | --- | --- | --- |
| 1 | Canonical instruction change updates or flags AGENTS.md | Partly | Flagged by CI (PR and push) and by `check.py quick|full`; updated only by a manual run or Setup's finishing step. In an installed mod nothing flags it unless an agent runs `check.py`. |
| 2 | Canonical skill change updates or flags runtime copies | No (CI), partly (local) | CI check is vacuous (G2). Locally `check.py quick` flags it only if mirrors exist and the change is uncommitted. Nothing updates it automatically (G3). |

## A5. Proposed design (smallest portable set that meets all seven)

### A5.1 Parts

1. Registry. One declarative file `.tools/sync/generators.json` listing every generator and checker with: `id`, command and `--check` form, `inputs` (canonical sources, config files and the generator script itself), `outputs`, `needs` (ordering), optional per-item scope (for skills `--skill <name>`), and `kind` (`generate` or `check`). It replaces the four hard-coded lists (G10). Initial entries: `instructions`, `agents`, `skills`, `guidance` (check-only; same input mapping so a size overrun is reported at edit time). Sketch (names are placeholders):

   ```json
   {"version": 1, "generators": [
     {"id": "instructions", "run": ".tools/sync/sync_instructions.py",
      "inputs": ["CLAUDE.md", "CLAUDE_template.md", ".tools/sync/instruction_projection.json"],
      "outputs": ["AGENTS.md", "AGENTS_template.md"]},
     {"id": "agents", "run": ".tools/sync/sync_agents.py",
      "inputs": [".claude/agents/*.md", ".tools/sync/agent_profiles.json"],
      "outputs": [".codex/agents/*.toml", ".codex/config.toml", ".cursor/agents/*.md", ".qoder/agents/*.md",
                  ".opencode/agent/*.md", "*/agent-map.md", ".claude/agent-map.md"]},
     {"id": "skills", "run": ".tools/sync/sync_skills.py", "scope": "--skill {skill}",
      "inputs": [".claude/skills/{skill}/**"], "outputs": [".agents/skills/{skill}/**", ".qoder/skills/{skill}/**"]},
     {"id": "guidance", "kind": "check", "run": ".tools/sync/check_guidance_size.py",
      "inputs": ["CLAUDE*.md", "AGENTS*.md", ".claude/skills/*/SKILL.md", ".claude/agents/*.md", ".tools/sync/read_limits.json"]}
   ]}
   ```

2. Shared runner in a shared library module (for example `.tools/lib/generators.py`, in the byte-identical shared set already used for `.tools/lib/*`): load registry, map changed paths to generators (glob match, capture `{skill}`), expand with `needs`, order topologically, run in `write` or `check` mode, serialise concurrent runs with a lock file (parallel tool calls can fire two hooks at once; both would write the same outputs), return findings. Consumers: `check.py`'s `generators` check (replacing the `GENERATORS` tuple), a new `check.py sync [--check] [--paths ... | --hook | --all]` mode (precedent: `setup` already writes), and `lib/setup.py` (replacing `SYNCHRONIZERS`, and returning non-zero when a generator fails: G6).
3. Tool changes, all small: add `--root <dir>` to the four tools (needed for temp-dir tests and for Factory running a pinned copy against a workspace), `--skill <name>` to `sync_skills.py`, make `sync_skills.py` distinguish source package from installed mod (see A5.4), and port CR's `UNUSED:` replacement check into `sync_instructions.py`. Use exit 0 ok / 1 drift / 2 cannot run everywhere (matches `check.py` and Factory).
4. Claude Code hook, one entry in the shipped `.claude/settings.json`:

   ```json
   "hooks": {"PostToolUse": [{"matcher": "Edit|Write",
     "hooks": [{"type": "command", "timeout": 30,
                "command": "sh \"$CLAUDE_PROJECT_DIR/.tools/py.sh\" \"$CLAUDE_PROJECT_DIR/.tools/check.py\" sync --hook"}]}]}
   ```

   The runner reads the hook JSON on stdin, takes `tool_input.file_path`, normalises Windows backslashes, finds the repository root by walking up from that path (not from `CLAUDE_PROJECT_DIR`, which stays at the main checkout when Claude works in a worktree - docs; this matters for the maintainer's worktree-based parallel work), maps the path through the registry, and then:
   - path is a registry input: run only the affected generators in write mode (skills narrowed to the edited skill), plus the guidance check for that file; exit 0 and print a `hookSpecificOutput.additionalContext` line naming the regenerated outputs so the agent commits them together; on any failure print the reason to stderr and exit 2 (Claude sees stderr; docs exit-code table);
   - path is a registry output: run the check only and exit 2 with "X is generated from Y; edit Y" (never overwrite without the canonical change);
   - anything else (all mod content): exit 0 immediately, no generator started.
   Hook facts checked in the docs: `PostToolUse` matches on tool name (`Edit|Write`); the file path arrives absolute with native separators (backslashes on Windows); hooks configured in settings also run inside subagents, so a `hoi4_skill_maintainer` edit triggers it too (closes G3); shell form runs in Git Bash on Windows and `sh -c` on macOS; a `PostToolUse` hook does not fire when a Bash command or outside process rewrites the file; the Bash `bashEditDiff` list is beta, best effort and omits git-ignored files, so it is not relied on; `FileChanged` watches only literal file names in the working directory, so it cannot cover `.claude/skills/**`. Each `if` filter holds exactly one rule, so path-specific `if` handlers would need one handler per prefix; one handler with a fast exit costs about 100 ms of Python start per edit (measured 98 ms) and starts no generator for unrelated edits, which is what criterion 4 asks.
5. One launcher `.tools/py.sh`: a POSIX sh script that picks the first working Python 3.9+ (`python3`, `python`, `py -3`), because three callers need the same discovery (hook, optional git hook, docs) and this machine's `python` is a Store stub. Precedent: Factory's `scripts/py.sh`. If the maintainer prefers no new script, the fallback is the docs' plain `python`, and a missing Python then shows as a visible non-blocking hook error (not silent).
6. Enforcement of "do not hand-edit generated files":
   - `permissions.deny` entries in the shipped `.claude/settings.json`, e.g. `Edit(/AGENTS.md)`, `Edit(/AGENTS_template.md)`, `Edit(/.agents/**)`, `Edit(/.qoder/skills/**)`, `Edit(/.codex/agents/**)`, `Edit(/.cursor/agents/**)`, `Edit(/.qoder/agents/**)`, `Edit(/.opencode/agent/**)`, `Edit(/.claude/agent-map.md)`. Docs: `Edit` rules apply to all built-in file-editing tools (permissions.md line 341) and `Write(...)` path rules never match (line 358), so write them as `Edit(...)`. They do not stop `python .tools/...` via Bash, so the generators still work, and they do not stop a Bash `sed -i` (the check still catches that).
   - Output edits that happen anyway are caught by the hook (output branch above), `check.py quick|full`, CI and the optional git hook.
   - Keep AGENTS.md without a header marker: `AGENTS_template.md` is 59,945 bytes against the 60,000 ceiling, so a header line would break `check_guidance_size.py` today. The existing sentence at template `:162` is the marker. Agent files and maps keep theirs. Skill mirrors stay byte-identical (a marker would break identity and add text to skills).
   - Optional: `.gitattributes` `linguist-generated=true` for generated paths so pull-request diffs collapse them (not verified in this repo).
7. CI: replace the five separate sync steps with `python -B .tools/check.py full --only generators guidance` (the registry drives it), keep the pull-request trigger unfiltered for that job (a path-filtered required check never reports and blocks merges), and ask the maintainer to add a ruleset or branch protection requiring the Validate job with a bypass for `github-actions[bot]` because the publish workflow pushes the manifest commit directly to main (`RELEASING.md:57` already anticipates this). The check must fail when zero generators were evaluated (G5).
8. Release gate: `scripts/check_release_package.py` also runs the generators in check mode and asserts every registry output is either gitignored or covered by a manifest component (it already asserts coverage for skills and agents at `:19-23`).
9. Optional local gate for non-Claude runtimes and humans: `check.py setup --git-hook` writes `.git/hooks/pre-commit` (never `core.hooksPath`, which Setup rejects and which would switch off CR's git-lfs hooks) containing three lines that run `.tools/py.sh .tools/check.py sync --check --staged`. Off by default. It is not in Setup's reviewed `expected_writes`, so Setup is unaffected. If Python is missing the hook warns loudly and lets the commit through.

### A5.3 Chaos Redux engine skills as one more generator

P10 (decision record `00-decision-record.md:76`) generates CR engine-system skills as kit text plus a Chaos Redux section, with a check that fails on direct edits. With the registry this is one entry plus one dependency edge:

- `engine_skills`: inputs = a pinned snapshot of the kit skills inside CR (for example `.tools/kit_skills/<name>/**` with a recorded kit commit and file hashes - pinned, not pulled, which is what R1 requires: "Pinned sync with checks stays", decision record `:85`), the overlay files (`.claude/skill-overlays/<name>.md`) and a small mapping file (kit skill to CR skill name); outputs = `.claude/skills/chaos-redux-<engine-skill>/**`; narrowed per skill like `skills`.
- `skills` (the `.agents/skills` mirror) gets `needs: ["engine_skills"]`, so the chain is kit snapshot + overlay to CR canonical skills to mirror, in order, in one runner call.
- A change to the snapshot or the mapping regenerates all engine skills; an overlay edit regenerates one.
- The CR check recomputes the expected bytes and fails on any difference, which is the P10 requirement. A provenance marker (HTML comment under the frontmatter, or a sibling provenance file) is a choice for the plan; a `deny` glob cannot select "generated skills only" because skills must sit flat under `.claude/skills/`, so for CR the check is the enforcement.
- The kit's `check_release_package.py:33-34` ban on "Chaos Redux" in kit skills is unaffected because the overlay lives in CR.
- CR's other generators (catalog CSV, formable puzzles, Event 016) become registry entries; CR's `check.py` `GENERATORS` tuple is deleted.
- The sync tools themselves should have one source. Proposal: the kit is the source (it has `--check`, stale handling, split modules); CR adopts them with its own `agent_profiles.json`; add `.tools/sync/` and the new `lib/generators.py` to the shared-tool mechanism. Today `scripts/shared_tools.json` declares CR as upstream, so the direction needs a decision.

### A5.4 Fixing the vacuous skill check

- Source package (detected as today by `CLAUDE_template.md` present and `CLAUDE.md` absent): the mirrors are generated at install, so the contract test builds a temporary root with `--root`, runs `sync_skills.py` to create the mirror, then asserts `--check` passes, mutates one file, and asserts it fails. CI therefore tests the tool's real logic every time.

### A5.5 HOI4 Factory job-completion validation

When a job's diff touches any registry input path, the job-completion check runs the generators in check mode; if stale it runs write mode inside the job worktree and adds the regenerated outputs to the same commit, then re-checks; a residual DRIFT or a generator error fails the job with a finding. Security: the project's own `.tools/sync/*.py` is repository-supplied code and must not be executed in the hosted service. Run Factory's pinned copy of the tool (Python standard library only) with `--root <workspace>`; read `generators.json`, `instruction_projection.json` and `agent_profiles.json` as data; run only generator ids on Factory's allowlist and report unknown ids as "unverified" (never as pass). This is consistent with A4 (project `CLAUDE.md`/`AGENTS.md` are labelled data without authority, decision record `:97`). An alternative is a Rust reimplementation of the three built-in generators; the Python route reuses tested code and is the smaller change (inference).

### A5.6 Setup and runtime compatibility constraints for the design (criterion 6)

- No `core.hooksPath` (Setup refuses such repositories).
- Every new generated path must be inside Setup's rewritable allowlist (`agent_setup.rs:33-43`), or `check.py setup` is refused/reported after it regenerates it. A cross-repository contract test is needed: every registry `outputs` entry for the installed layout is covered by that allowlist. Adding a runtime folder (format 6) needs a Setup change as well.
- Shipping hooks and deny rules changes `.claude/settings.json`, which belongs to `runtime.claude` (replace_if_unmodified, preserve_local_additions). Installs with an unmodified file update cleanly; installs with a user-modified file go through Setup's conflict flow. Not tested (not verified): update a mod whose settings.json already contains user hooks.
- A project-level hook is code that runs on the user's machine on every edit. It points at hash-tracked files installed by Setup, but it is new behaviour for Setup's security documentation (docs/13); the maintainer should decide whether Setup's review screen should mention it.
- `check.py setup` should exit non-zero when a generator fails and Setup should keep treating the step as non-blocking (as today) but show the failure on the Ready line.
- Regenerating AGENTS.md overwrites a hand-maintained or three-way-merged `AGENTS.md` without a backup (inference from `core.agents` being a three-way-merged managed file and `AGENTS.md` being in the rewritable list). Worth a one-time warning in `setup` when the existing AGENTS.md differs from the projection of its CLAUDE.md before overwriting.
- Shared working trees (kit `hoi4-shared-git-commit`, CR concurrency rules): the hook's `additionalContext` must tell the agent which outputs changed so they are committed with the canonical change; otherwise the next `--check` flags drift.
- Template and test constraints for any text added to the template: `scripts/test_agent_sync_contract.py:160-182` requires certain headings, forbids "Chaos Redux", "chaosx", "OneDrive", "klimp" in the template, and fails on mid-sentence hard wraps in `CLAUDE_template.md`, `AGENTS_template.md`, `docs/runtimes.md` and `.tools/sync/README.md`.

### A5.7 Deliberately not proposed

## B2. Conflicts with the new rule

1. `CLAUDE_template.md:365` (and CR `CLAUDE.md:328`): "ask a focused question when something indispensable is missing" is the opposite pattern (mid-task, one at a time, no default offered). Replace with the rule's late-question clause.

## B3. Placement and outline wording (not final text)

### One canonical rule in `CLAUDE_template.md`

Place a new `### Upfront consultation` subsection in section 0 immediately after `### Specs and Plans` (`:237-252`), because that is where decisions are already recorded, and replace the sentence at `:365` with a one-line pointer to it. Skills reference it; they do not restate it. Keep the rule runtime-neutral (no tool names) because AGENTS.md copies it to Codex, Cursor, Qoder, OpenCode, DSH and, with format 6, to every client that reads AGENTS.md.

Outline (about 10 short lines, one sentence per physical line to satisfy the hard-wrap test):

1. When it applies: a substantial task is one that creates or reshapes a feature, system, country, route set or asset set, spans three or more surfaces, or has no accepted spec. Bug fixes, single-surface edits and follow-ups inside an accepted spec skip it.
2. Inspect first: project instructions, relevant specs and plans, the decisions record, and the mod files the task touches. Never ask what a file can answer.
3. Sort every open point into three groups: established (stated by the user, a spec or the decisions record), yours to decide (derivable from instructions, precedent, vanilla or the engine rules, including every routine implementation choice), and genuine questions (change player-visible design, scope, canon, cost, risk or an irreversible action, cannot be derived, and have no safe reversible default).
4. Present the genuine questions once, in one message, grouped by surface, each with a suggested answer and a one-line reason; show the decided items as a short list the user may overrule. For large tasks announce the batches up front (intake, then named later points such as "after the spec draft") with at most about seven questions each.
5. Record every answer and every default in `docs/specs/<feature_slug>/decisions.md` (and the spec it affects) with origin: user, established, or agent default (wording of template `:244-246` for the acceptance basis).
6. Then work without re-asking recorded points. A later question is allowed only when it was not foreseeable or hits a hard gate (spend above the authorized budget, permission-gated actions listed in this file, widening scope). Ask it once, batched with others, with a suggested default, and continue independent work meanwhile.
7. Never ask about naming, file layout inside the established layout, localisation keys, code factoring, tool choice, ordering of work, check selection or retries, nor for logs or in-game testing.
8. Subagents have no user channel: they put open items in their handoff, the parent folds them into the next batch.
9. Autonomy: follow the project's checkpoint policy for where and how often the consultation is held; the contents of the consultation do not change with the level (B5).

Hard constraint: the template has 55 bytes of headroom (59,945 of 60,000). This block is roughly 1.5-2.5 KB, so it can land only in the same change as the P11 slimming (dedupe or move to references, never drop, with a diff audit; decision record `:70`). Candidates already identified in report 04 section 11: the skill routing list (`:88-111`, 4.9 KB, restating descriptions), the Subagents block (9.7 KB, restating `hoi4-subagents`), the Agent runtimes block (2.9 KB, restating `docs/runtimes.md`). ## B5. Behaviour under each autonomy level

Levels are presets of one checkpoint policy over design brief, visual review, plan, diff, commit, merge or publish, each `auto | ask | notify` (A2, `:95`). The consultation is the design-brief checkpoint (P12's tiers: story gaps, design calls with a recommendation, quick confirms with defaults, `:77`; P12 is adopted for HOI4 Factory only). Proposed mapping (inference where marked):

| | Fully autonomous | Semi-autonomous | Human-in-the-loop |
| --- | --- | --- | --- |
| Intake consultation | `ask`, exactly once, whole task. If the project's policy sets the design brief to `auto` (no human reachable), apply every suggested answer as an agent default tagged for review and show them in the completion notice (inference) | `ask` at intake | `ask` at intake, in smaller batches per surface or phase |
| Later checkpoints | none for design; merge `ask` by default, owner may set standing `auto` (A2 change) | the configured ones (plan, visual review, diff) carry batched questions | every configured checkpoint carries its own small batch |
| Late (unforeseeable) question | only a hard gate (budget, permission-gated action, widening scope): the job pauses with a notification; no other questions | batched with the next checkpoint, with a default; independent work continues | asked at the next small checkpoint, with a default |
| Routine implementation choices | never asked | never asked | never asked (the level changes how often non-trivial decisions are surfaced, not what counts as trivial) |
| Idea-selection rounds | the parent decides and logs dispositions (kit behaviour) | one round per tranche, answered Adopt/Adapt/Defer/Reject | same, possibly per proposal |

Switching level mid-job (A2: "switchable mid-job at the next checkpoint without widening grants") keeps all recorded answers because they are in the repo.

## B6. Interaction with the improvement loop and the Adopt/Adapt/Defer/Reject rounds

- Separate mechanisms. The consultation settles requirements and missing decisions once, before work. The improvement loop proposes new design depth after a tranche; its rounds are scheduled checkpoints, not interruptions that could have been asked earlier. The consultation announces them in advance ("after the first implementation tranche I will bring improvement proposals; answer each with Adopt, Adapt, Defer or Reject").
- Vocabulary map to the kit's six dispositions (template `:248`, improvement-loop skill): Adopt = implemented or promoted to a named spec; Adapt = promoted with the change recorded; Defer = queued with a reason; Reject = rejected with a reason. Superseded and blocked stay as they are. One mapping sentence in the improvement-loop skill is enough.
- Answers go to the same `decisions.md` (with the proposal id), so a later session or autonomy level does not re-propose a rejected idea.
- The existing guard "planner not re-deployed until the previous addendum is resolved" (`SKILL.md:284`) already prevents proposal stacking; the rounds present one batch per resolved addendum.
- In the maintainer's own research sessions the rounds are the interactive workflow recorded in `00-decision-record.md` (choices defined at `:5`); that stays a maintainer-level process and is not a product rule.
