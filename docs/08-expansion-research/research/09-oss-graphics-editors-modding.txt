## 0. Short answer (details and caveats follow; the consolidated recommendation is in section 8)

1. Graphite: reject as a dependency now. It is a real, active, dual MIT/Apache-2.0 node-graph editor, but it is alpha, its document format is mid-migration, its crates are unpublished (`publish = false`, version 0.0.0, Rust 1.98), its CLI renders through wgpu, and it has no DDS output. Adapt three ideas (recipe as a node DAG, content-addressed resources, versioned migrations). Revisit after its stable-format and batch-tools milestones.
2. OpenDesign: a TypeScript/Node daemon + Next.js UI that orchestrates third-party coding agents to make HTML prototypes, decks and videos. Not a graphics engine. Reject as a dependency; borrow the DESIGN.md style-spec and lint-before-accept ideas.
3. Canvas: React Flow (`@xyflow/react`, MIT) is the best fit for a grid-based focus tree and for event chains. tldraw is licensed out (no production use without a key). Excalidraw/LiteGraph/Rete are poor or riskier fits. Konva/Pixi/Fabric are for pixel-level editors (maps, GUI) later. dagre (MIT) for event-chain layout; elkjs only if ports/orthogonal routing are needed (it is `EPL-2.0 OR GPL-3.0-or-later`).
4. Pipeline: do DDS in-process in Rust with `image` + `image_dds` (which wraps `intel_tex_2` and `ddsfile`), but write the DDS header with `ddsfile` yourself because `image_dds` emits DX10-extension headers for BC1/BC3/BC7, whose acceptance by HOI4 is UNVERIFIED. Write TGA flags with a tiny own writer because `image`'s TGA encoder is RLE + top-left origin by default while the HOI4 wiki says uncompressed 32-bit, bottom-left origin. texconv is Windows-only as a tool; Compressonator CLI ships Linux x86_64 only; ImageMagick/Pillow are usable as test oracles.
5. New find with high value: "CWTools MD Edition" (MillenniumDawn/cwtools-vscode, MIT) contains a Rust rewrite of CWTools, HOI4-first, with a CLI (`cwtools validate`, JSON/SARIF) and LSP. It could replace the F# CWTools worker. It is extremely active (pre-release numbering at v4.1.299, four tags published within about an hour on 2026-10-31), so pin by SHA and evaluate in a bounded spike. Also noted: RHoiScribe (AGPL-3.0 Rust MCP server for HOI4 agents) and hoi4skill (GPL-3.0 Rust CLI) overlap with hoi4-agent-tools.
6. AI art: keep ComfyUI as an external HTTP service (GPL-3.0, separate process, no linking). The maintainer's portrait repo ships API-format workflows and a DDS saver; its model (FLUX.2 Klein 9B) is gated and non-commercial, so support "bring your own endpoint" before hosting weights.

## 1. Graphite (GraphiteEditor/Graphite)

Identity: first inspected at 210aef541b1e202889853a5f989cedba23abce16 (2026-10-31 11:50Z); head later f04bbe1c5a26efcde0848757cef5ca456a656a04. Rust (workspace) + Svelte/TypeScript frontend. GitHub size 61 MB. 184 contributors (list paging count). At least 100 commits between 2026-10-01 and 2026-10-31 (the API page cap). One rolling "latest-stable" prerelease tag from 2022; no versioned releases.

License (VERIFIED, L+M): LICENSE-APACHE and LICENSE-MIT both present; workspace `license = "MIT OR Apache-2.0"`; the website license page says dual-licensed at your choice. GitHub API reports Apache-2.0. Either choice is AGPL-3.0 compatible (inbound).

What it is (from code and docs):
- A node-based, non-destructive vector/raster editor. Document = node network; the "Graphene" engine (`node-graph/` crates: graph-craft, interpreted-executor, graphene-std, nodes for raster, vector, blending, brush, text, transform, path-bool, vectorize) compiles and runs the network.
- Frontend is Svelte; the Rust editor compiles to WebAssembly via `frontend/wrapper` (crate type cdylib+rlib) built by the repo's own `cargo run` tooling. Its frontend README says the backend is the source of truth for state and the frontend is presentation only.
- Documents: legacy `.graphite` (serialized runtime structs) and a new `.gdd` archive format. A design RFC (node-graph/rfcs/document-format.md) describes a flat node registry, content-addressable resources (images, fonts, declarations) and a CRDT-style delta tree that also drives history, migrations and incremental compilation. The newest commits on the day I read it add the `.gdd` migration core and CLI, so the format is in flux. The features page (WebFetch) says a stable document format is planned for "Alpha 5" and "automation/batch processing tools" for "Beta 2"; raster compositing is described as still experimental.

Is it embeddable in a web app? No supported path (VERIFIED by absence): all crates have `publish = false` and version 0.0.0; the WASM wrapper is built only through the repo's tooling and exposes the editor's message protocol to its own Svelte UI; there is no documented embedding API or npm package. Embedding means hosting a fork of the whole editor (an iframe) with no hook into our auth, Git or proposal model. `tools/web-editor-driver` drives the editor with real input plus screenshots via Playwright (for QA/agents); it is a driver, not an integration API.

Is Graphene usable server-side for batch pipelines? Partly, with heavy caveats:
- `node-graph/graphene-cli` has `compile`, `export`, `list-node-identifiers`, `extract-legacy-doc`. `export` reads a `.graphite` or `.gdd` and writes svg, png, jpg, webp, tiff, bmp, tga, ico or gif with scale/size/transparent/frame options.
- It defaults to the `wgpu` feature and enumerates GPU adapters (`Backends::all()`); a comment in the editor runtime says raster falls back to the SVG pipeline when there is no GPU, as in headless tests. Raster export in a GPU-less container is therefore UNVERIFIED (would need software Vulkan).
- Build cost: 39 workspace entries (two are globs over `node-graph/libraries` and `node-graph/nodes`, so dozens more crates), `rust-version = 1.98`, edition 2024, and git-pinned forks of `vello_gpu/vello_common/vello_gpu_shaders` (Keavon/vello, a specific rev). That would fight a pinned `rust-toolchain.toml` and bloat the image.
- DDS: none. Workspace `image` features are png, jpeg, bmp, gif, webp, tiff, ico, tga, hdr, exr, serde; code search found 0 hits for `DXT1` and `image_dds`; `BC7` appears only in a blog post and lockfiles. DDS would have to be produced by our own encoder after a PNG export.

Maintenance: very active, large community, but alpha. Churn is a risk for a pinned dependency: node names, document schema and even the GPU path changed within hours (a commit retiring the "Rust GPU" path and "Upload Texture" node landed the same day).

Overlap with hoi4-agent-tools renderers: none (Graphite renders arbitrary vector/raster art, not HOI4 UI). It could in principle author source art, not game files.

Verdict: REJECT as a dependency now. ADAPT IDEAS:
1. A recipe is a small DAG of pure, typed, versioned operations on content-addressed inputs (our "transform recipe" with source hash, profile id, parameters, output hash and receipt).
2. Content-addressed resource store keyed by hash for source images, fonts and generated outputs (maps to SPEC-010 "original retained, receipt recorded").
3. Schema-versioned documents with explicit migrations from day one (apply to our recipe and technical-profile files).
Revisit trigger: stable `.gdd` + batch tooling + a documented CPU raster path + a DDS output node. Even then, run it as an optional sandboxed worker, not an in-process crate. Maintainer approval: not applicable now (no adoption).

## 2. OpenDesign (nexu-io/open-design)

Identity: SHA 12d970eacc8971150e3c76470d2a9afe16dc2ed1 (2026-10-30). TypeScript. Created 2026-04-28. ~105k stars, ~444 contributors, release open-design-v0.26.1 (2026-10-22). GitHub size 3.6 GB (history and media). License: Apache-2.0 (A; LICENSE file present, 11 KB, text not read; README badge agrees). AGPL-3.0 inbound compatible.

What it actually is (VERIFIED from repo layout and docs/architecture.md): a pnpm monorepo for a "design agent workspace":
- `apps/daemon`: a local Express daemon plus the `od` CLI. It owns the HTTP/SSE API, a SQLite store, skills/design-systems/artifacts registries, and it spawns coding-agent CLIs or ACP processes (the README matrix lists Claude Code, Codex, Cursor, OpenCode, Kiro and others).
- `apps/web`: Next.js 16 + React 18 UI; `apps/desktop`: Electron shell; `packages/*`: contracts, sidecar protocol, plugin runtime, etc.
- Content: `skills/` (171 entries), `design-templates/` (116), `design-systems/` (154 brand DESIGN.md files), `craft/` (brand-agnostic rule sheets such as accessibility, typography, "anti-ai-slop"), `plugins/` (8).
- Media: the daemon has `media/` and `media-adapters/` (image-generation retry policy, stock search, a HyperFrames video runtime). The image skills I opened are catalogue entries pointing to an upstream skills bundle; I found no raster processing, texture or sprite code. docs/external-media-orchestration.md says it should not become a generic provider router; the host owns budgets, credentials and provider policy.
- Telemetry: PRIVACY.md says product analytics are on by default with an opt-out, plus an always-on reliability channel in builds that have a destination.
- Runtime: Node 24, pnpm, better-sqlite3 (native build on Windows per its AGENTS.md).

Relevance: it produces HTML/slides/video design artifacts with coding agents. It is not an asset pipeline, has no DDS/TGA/GFX concepts (not an exhaustive grep), and would add a second runtime and a second agent loop next to our Rust one.

Overlap with hoi4-agent-tools: none on rendering. Overlap with our own agent loop and UI design track (ADR-025): conceptual only.

Verdict: REJECT as a dependency. ADAPT IDEAS:
1. DESIGN.md: a per-brand, agent-readable style spec. PROPOSAL: a per-mod "art style guide" file (palette, framing, text-free rule, size profile) that the agent reads before generating portraits or icons.
2. `craft/` rule sheets as short checklists injected into prompts and reused as review criteria.
3. A deliverable lint step before accepting output (`lint-artifact`), matching our validate-before-apply rule.
4. Run-scoped media policy where the host, not the agent, owns provider budgets (already SPEC-010).

Fit analysis (PROPOSAL, based on the facts above plus HOI4 focus semantics from the project's own specs; not tested):
- Focus tree (x/y on a grid, `relative_position_id`, prerequisites with AND groups of OR sets, `mutually_exclusive`): positions are author-defined, so no auto-layout is needed. The Rust adapter should resolve relative chains to absolute cells and own the write-back (moving a node rewrites `x`/`y` relative to its `relative_position_id` reference, or re-parents). The canvas only needs fixed-grid snapping, custom node UI (server-rendered icon, label, status), orthogonal prerequisite edges with an OR/AND visual, a distinct mutual-exclusion edge, selection, keyboard operation and viewport culling. - Community prior art that skipped a graph library: the browser focus designer LesMiserablesMod/hoi4-focus-tree-designer (Next.js, custom canvas, no license file so ideas only) and 1725381449-cell/hoi4-focus-viewer (MIT, zero dependencies, positions taken from the author's x/y). A zero-dependency DOM+SVG renderer is therefore a real fallback if the maintainer declines a new runtime dependency; the cost is re-implementing pan/zoom, marquee selection, minimap and keyboard/a11y.

Overlap with hoi4-agent-tools: its focus/event/tech renderers produce game-accurate images from source (they are server-side evidence). The browser canvas should be an editing surface fed by the same normalized model, with the server-rendered image kept as verification evidence, not replaced by the canvas.

Verdicts:
- @xyflow/react: INTEGRATE (client dependency; needs maintainer approval; S04 spike first).
- @dagrejs/dagre: INTEGRATE later, for events/decisions (needs approval; not needed in S04).
- elkjs: ADAPT IDEA (keep as the escalation path; GPL option only).
- tldraw: REJECT (license). Excalidraw: REJECT (wrong model). LiteGraph: REJECT (stale/archived/GPL host). Rete.js: REJECT as primary; acceptable fallback.

## 4. Image processing and DDS for an asset pipeline

### 4.1 What HOI4 requires (documented vs claimed)
- Flags (VERIFIED, HOI4 wiki "Country creation"): TGA, uncompressed 32-bit ARGB; bottom-left origin (top-left flips the image); 82x52 (about 16.6 or 17.1 KiB), 41x26, 10x7; files go under `gfx/flags` with each size in its own subfolder (exact subfolder names not captured; check the page); 24-bit loads with a performance warning.
- Sprites (VERIFIED, wiki "Graphical asset modding"): `.gfx` spriteType/frameAnimatedSpriteType/corneredTileSpriteType entries; texture paths relative to the game folder; sprite DDS files should stay under about 16 MB; the page is marked outdated and does not state DXT/mip rules.
- Portraits: the wiki says usually 156x210 and gives no format rules. The maintainer's own repo states in its DDS saver docstring that vanilla leader portraits are 156x210 uncompressed A8R8G8B8 with no mipmaps, and offers DXT5 as an option. That is a repo claim, not independently verified here.
- Event pictures: the wiki event page gives only the sprite pattern (`GFX_*` in an interface `.gfx`, DDS path) and no pixel sizes; 210x176 / news sizes come from the task brief and are UNVERIFIED here.
- Focus/idea/decision icons: DXT choice and mip policy are not stated by any page I fetched. UNVERIFIED. A search snippet suggests vanilla interface textures usually have no mipmaps (non-HOI4 sources); treat as a hint only.
- What the maintainer's own decoder accepts (VERIFIED, `src/hoi4_agent_tools/gui/dds.ts`): legacy FourCC DXT1/DXT3/DXT5, uncompressed RGB16/24/32, and two DX10 formats (RGBA8 sRGB, BGRA8 sRGB); RXGB is intentionally not decoded. This is decode-only; there is no DDS encoder anywhere in that repo. Its raster stack is `sharp` (libvips) + custom DXT decode.
- PROPOSAL: derive technical profiles from data, not memory (SPEC-010 already requires this): a one-off scan of the installed game's `.dds` headers (format, mip count, size histogram per folder) run on the server-side reference copy, stored as versioned profile files; only the derived numbers enter the repo.

Game-correctness note (PROPOSAL, grounded in the reads above): "valid DDS" and "loads in HOI4" are different evidence kinds. `image_dds` output defaults to DX10-extension headers for BC1/BC3/BC7; whether HOI4 accepts those, and whether it needs mip chains for icons, is UNVERIFIED. Safe default until an in-game test: legacy FourCC DXT5 for alpha icons, DXT1 for opaque art, uncompressed A8R8G8B8 for portraits (matching the maintainer's tool) and TGA 32-bit uncompressed bottom-left for flags. Make BC7 and DX10 headers opt-in profile entries that stay "unverified" until the maintainer observes them in the game. Wrap `Surface.data` (raw blocks) with `ddsfile::Dds::new_d3d` to force legacy headers.

TGA detail (VERIFIED in `image` source): the flags profile cannot use `TgaEncoder` as-is. Write the 18-byte header and BGRA rows yourself (roughly 40 lines, no dependency), bottom-left origin, no RLE, and add a golden test against a vanilla flag's header and a byte-compare of a re-decode.

### 4.3 Browser-side and desktop editors (for non-destructive authoring by humans)
- Photopea: closed source web app (UNVERIFIED beyond that). Not embeddable or auditable here. REJECT.
- miniPaint 4.14.3 (viliusle/miniPaint, MIT): layered raster editor in plain JS, last commit 2026-04-19. Its non-destructive claims are UNVERIFIED. Not a pipeline component. REJECT as dependency; fine as a user tool.
- Penpot 2.18.5 (MPL-2.0; MPL lists AGPL as a secondary license): vector UI design and prototyping, large self-hosted service stack (not inspected). Wrong tool for raster/DDS art. REJECT.
- Krita (GPL-3.0, desktop, active) and GIMP (GPL with a stated exemption text, desktop): the real editors modders will use for layered work; interoperate through an open layered format rather than embed. ADAPT (interchange only).

### 4.4 Layered/non-destructive source formats
- OpenRaster (VERIFIED, openraster.org spec 0.0.6): a zip with `mimetype` (first, stored), `stack.xml`, `data/` PNG layers, a required thumbnail and `mergedimage.png`. Layers carry `src`, `name`, `x`, `y`, `opacity`, `visibility`, `composite-op` (default `svg:src-over`, plus multiply, screen, overlay, etc.). The site lists Krita, GIMP, MyPaint and Scribus as supporting apps. No license stated on the site (copyright notice only).
- PSD: Rust `psd` crate (Apache-2.0, 284 stars, last commit 2025-01-30, release 0.3.4 from 2022) parses PSD for reading/flattening, not authoring (UNVERIFIED for writing). PSD is proprietary; do not make it a source of truth. REJECT as source format.
- Graphite documents: unstable (see section 1). REJECT for now.
- A small Rust ORA reader exists (AnAverageGitUser/ora-reader, MIT, 0 stars, last commit 2025-08-08): too young to depend on. REJECT.
- PROPOSAL: the Git-native layered source is "master PNG(s) + masks + a recipe JSON + provenance receipt", exactly the shape the maintainer's portrait workflow already emits (1024x1365 master PNG, game-size PNG, DDS). Where a human wants layers, store the OpenRaster layout (`stack.xml` + `data/*.png`) unzipped in Git so diffs are per layer, and zip it on download for Krita/GIMP. No new dependency is needed for the MVP if the host only emits and reads its own recipe and treats `.ora` as interchange.

## 7. Risks and unknowns worth carrying forward

1. HOI4 acceptance of DX10-header DDS, BC7 and mip chains is unverified; only game observation can settle it. Needs a maintainer test on his Windows machine with a small fixture set (DXT1, DXT5, A8R8G8B8, BC7/DX10, with and without mips) before BC7 is advertised.
2. Event picture and icon sizes in the task brief are not on the wiki pages I fetched; derive them from a vanilla header scan.
3. `image_dds`/`intel_tex_2` ship precompiled ISPC machine code; amd64+arm64 availability is inferred from source, not built. If unacceptable, `texpresso` is the pure-Rust fallback (no BC7, license file missing in repo).
4. CWTools MD Edition churn: decide pin policy (by SHA, vendor binary hash) before any adoption. Its crates are consumed by git rev elsewhere (RHoiScribe), not from crates.io.
5. React Flow `parentId` vs `relative_position_id` mapping, 300+ node performance and a11y behavior are unverified.
6. FLUX.2 Klein non-commercial terms versus a hosted public service.
7. Graphite and others change daily; any future adoption review must re-read at that time.
8. GitHub code search is token-based and fuzzy; "0 hits" results (for example DDS terms in Graphite and libvips) are indicative, not exhaustive.

## 8. Consolidated recommendation

Naming at most one dependency per responsibility. "Approval" means the maintainer must approve per CLAUDE.md (new runtime dependency or changed accepted plan).

(a) Focus / event / decision editor canvas stack
- Canvas, selection, pan/zoom, grid snap, custom nodes/edges: `@xyflow/react` (React Flow 12, MIT; brings zustand, classcat and d3-zoom/drag/selection/interpolate). Approval required. Keep the small "React Flow" attribution visible (Pro is only for removing it).
- Auto-layout for event/decision chains only (not for focus trees, which use author coordinates): `@dagrejs/dagre` (MIT) when the events stage starts. Approval required then. Escalation path if ports/orthogonal routing are needed: `elkjs` under its GPL-3.0-or-later option.
- Architecture: the Rust adapter owns the normalized model (absolute cells, relative_position_id write-back, prerequisite groups, exclusion sets, unknown-field preservation); the canvas is a projection; hoi4-agent-tools' server-rendered images remain the verification evidence.
- Gate: an S04 spike that proves (1) relative-position write-back, (2) a 300-400 focus tree stays responsive with `onlyRenderVisibleElements`, (3) keyboard and screen-reader operation under the existing jsx-a11y lint, (4) AND/OR prerequisite and mutual-exclusion visuals. If it fails or the maintainer declines the dependency, fall back to a DOM+SVG renderer with no library (precedent: two community focus tools).
- Not chosen: tldraw (license), Excalidraw, LiteGraph, Rete, Konva/Pixi/Fabric (revisit Pixi at S07 for province bitmaps).

(b) Server-side asset pipeline including DDS
- Raster decode/resize/PNG: `image` (Rust). Use `imageops` for Lanczos resizing; no separate resize crate.
- BC compression and DDS handling: `image_dds` (pulls `ddsfile` and `intel_tex_2`). Approval required (precompiled native kernels). Fallback: `texpresso` (pure Rust, no BC7).
- Own code, no dependency: a TGA flag writer (uncompressed 32-bit, bottom-left origin) and a DDS header step that forces legacy FourCC (DXT1/DXT5) or A8R8G8B8 through `ddsfile::Dds::new_d3d`; profile-driven (`dds_profile` data derived from a vanilla header scan, versioned) with BC7/DX10 disabled until game-verified.
- SVG sources (only if wanted, S06+): `resvg` with bundled fonts. Approval required then.
- Generation: ComfyUI as an external HTTP service reached through the capability adapter, using the maintainer's `.api.json` workflows; BYO endpoint first. No new library dependency (HTTP client already exists).
- Test oracles (not dependencies): hoi4-agent-tools' DDS decoder, Pillow or ImageMagick on a dev machine for independent decode, Compressonator/texconv on Windows for cross-encoding, and a recorded in-game observation as the separate evidence kind.
- Related validator decision (separate approval): evaluate MillenniumDawn CWTools Rust engine as the optional validation subprocess in place of the F# worker.

(c) Non-destructive layered asset sources
- One format decision: store a Git-native source bundle per asset: master PNG(s) and masks, a versioned `recipe.json` (crop, filter, mask/background step, target profile id, DDS format, mip count) and a provenance/transform receipt (source hash, recipe hash, output hash, generator version, seed). Re-export DDS/TGA deterministically from the recipe; originals stay untouched (matches SPEC-010).
- For human layered editing use OpenRaster (`.ora`, open spec 0.0.6, supported by Krita and GIMP), kept as an unzipped layout in Git or zipped for download. Zero new dependencies in the MVP (the host only reads its own recipe and treats ORA as interchange); add a small XML/zip crate later only if reading foreign ORA files becomes a requirement.
- Not chosen: Graphite documents (unstable, GPU render path, no DDS; revisit after its stable-format and batch milestones), PSD (proprietary, read-only crate), Photopea (closed), Penpot (wrong domain), miniPaint (not a pipeline component).

Dependencies needing maintainer approval, in order of need: `@xyflow/react` (S04), `image` + `image_dds` (S06; `image` may already be planned), `@dagrejs/dagre` (events stage), `resvg` (only if SVG sources are accepted), and the decision to trial the Rust CWTools engine. Items needing an explicit maintainer answer: ComfyUI/FLUX hosting stance, permission to run an in-game DDS acceptance test, and whether to keep the React Flow attribution link.
