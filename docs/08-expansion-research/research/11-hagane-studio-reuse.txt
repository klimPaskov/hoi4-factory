# 11 - Hagane Studio: engineering assessment for direct reuse by HOI4 Factory

Scope: read-only engineering assessment of the shallow clone of github.com/hagane-works/hagane-studio
(commit 1e831623ed162e1a64763c242c55b249376ba20c, v0.1.2, GPL-3.0-only). Nothing was built, run or
downloaded; no model calls. Numbers come from `git ls-files` plus `wc -l`/`grep` on the clone.

Paths: `H/...` means <projects>\hoi4-factory\.work\ext\hagane-studio\...
`AT/...` means <projects>\hoi4-factory\.work\ext\agent-tools\src\hoi4_agent_tools\...
Evidence tags: [V] verified by reading or measuring; [I] inference; [U] could not verify.
Effort scale (agent-assisted engineer-days, my estimate, excludes the ADR-025 design-lab loop and
maintainer approvals): Small <= 3, Medium 4-10, Large > 10.

New fact taken as given: the maintainer reports that the Hagane Works author agreed that the maintainer
takes over development and may use the project in any way. Section 7 lists what should still be put in
writing before code moves.

## 0. Findings in brief

1. [V] The valuable part is small and mostly knowledge, not code. The Go backend is 234,477 non-test lines
   (19,731 of them two generated unicode tables) and the React frontend is 195,134 non-test lines (724 files)
   plus 38,765 test lines. Only about 5.8k Go lines (about 2.5 percent) and a few thousand TS lines are worth
   carrying over (section 6.1). The earlier overview's "about 106k TS/TSX lines" does not reproduce: I measure
   195,134 non-test + 38,765 test lines. The Go figures (123.5k internal/hoi4, 81.5k domains, 16.5k toolapi) match.
2. [V] The data model is the blocker for direct reuse. Every editor, store and tool works on JSON table rows
   (`project.json` + `data/<table>.json`, 54 tables in H/internal/schema/tables.json) and regenerates mod files on
   export. HOI4 Factory edits native files in place. The editors cannot be re-pointed at native files by changing
   a base URL. They need an adapter (native parse -> view model, edits -> source-bound proposals), and only the
   graph-shaped ones are cheap to adapt.
3. [V] The Go Clausewitz parser is lossy (comments-only trivia, no byte offsets, canonical tab-indented
   re-emission). It is not a basis for source-preserving edits. The maintainer's own TS lexer
   (AT/core/source/lexer.ts, start/end offsets and whitespace tokens) is already better. Do not reuse it.
4. [V] Largest overlap with existing assets: focus layout and geometry (agent-tools focus/layout.ts 2,879 lines,
   geometry.ts 382 lines use the game's 176x116 px grid; Hagane's editor grid is 130x180), map tooling (agent-tools
   map/ 47,776 lines vs Hagane mapgen 6,645 + worldmap 8,091), GUI rendering (agent-tools gui/ 18,826 lines vs Hagane
   guirender 23,000), tech and event tooling. Porting the Go versions would create duplicates.
5. [V] Best code to take: the focus-graph React/xyflow interaction shell (about 3.4k lines after dropping layout),
   the event/decision "in-game preview" cards (274 + 164 lines), the save-diagnostics delta model, the sha256-guarded
   span repair plan (clausewitz/crossref.go), the draw.io importer (398 lines), the DLC/dead-flag/perf lint rules as
   specs, gamedir/install/log-parsing for the local companion.
6. [V] Frontend is Tailwind-class styled (8,151 className sites), use-intl i18n, zustand + SWR state, 494 inline
   `style={}` sites. Factory uses plain CSS custom properties, i18next, no state library, a no-`style=` source rule
   and an i18n literal-text lint. Visual components therefore need a restyle, a message-format conversion and a
   lint pass whatever else is decided. Logic modules transfer, JSX does not.
7. [V] The Go backend builds without cgo and has non-Windows stubs, so a Linux build is plausible, but it listens
   on 127.0.0.1 only, mints a session cookie for any visitor, keeps process-global singletons and needs the user's
   game files mounted. It is a single-user local server, not a hosted service. Hosting it behind our Rust server as
   a worker is possible but is a poor trade.
8. [V] Recommendation: Option C, phased. Phase 1 is Option A (harvest selected editors, rules and ideas), phase 2
   builds the local companion from the few local-integration modules, and Hagane Studio goes to maintenance-only
   with a stated sunset trigger. Reject Option B. Section 6.

## 1. Architecture map

### 1.1 Process model [V]

- One Go process, `H/cmd/haganeworks/main.go` (188 lines). Serves the embedded SPA (`H/web/embed.go:8`
  `//go:embed all:dist`) and the JSON API on 127.0.0.1 only (`main.go:153-165`, `listen`). Flags: `--port`,
  `--no-window` (`main.go:28`), `--version`, `--config`. A second launch finds the running copy through
  `GET /api/app/ping` (`main.go:167-176`).
- Window: WebView2 via go-webview2 in `cmd/haganeworks/window_windows.go` (442 lines). On other systems
  `window_other.go:5-7` returns `errNoWindow` and the program opens the default browser (`window.go:19-28`).
- CLI: `H/cmd/hw/main.go` (621 lines) is a thin client for the tool API; it starts the program with `--no-window`
  if it is not running (`docs/cli.md`).
- Project storage: `H/internal/project/project.go` (`Row = map[string]any`, whole project in memory, JSON files,
  temp-and-rename saves). Not typed structs, not native files.

### 1.3 HTTP surfaces [V]

(a) Web API, cookie session. About 263 `HandleFunc("METHOD ...")` registrations (more via helper loops).
Prefixes: `/api/go/projects/{id}/...` (49 literal routes), `/api/app/*` (status, settings, folders, game-index, quit,
install), `/api/go/vanilla/*` (18), `/api/go/lint/*` (7), `/api/go/import/*` (6), `/api/go/export/*`, `/api/go/image-batch/*`,
`/api/go/basemod/*`. Registered in `H/internal/api/app.go:67-92` and `api/domains.go:18-40`. The `/go/` segment and the
26 `*.goRouting.test.ts` files are a legacy of porting a hosted Python backend to Go: the frontend contract is the
hosted platform's REST contract.

(b) Tool API, bearer token: `GET /api/tools`, `GET /api/tools/{name}`, `POST /api/tools/{name}`, `GET /api/tools/fields[/{doc}]`
(`H/internal/toolapi/api.go:16-22`). Tools are wrappers that call (a) in-process through a fake transport
(`rest_proxy.go:26-60`, `handlerTransport`), so every tool inherits the JSON-table semantics. Input schemas are
generated by reflection from Go structs; field guidance lives in `jsonschema:"..."` tags (for example
`tools_focus_proxy.go:15-19`). No MCP protocol is spoken; the code mimics MCP SDK type names only (grep for
jsonrpc/modelcontextprotocol is empty). 144 direct `AddTool(s,` call sites in the code vs "149 tools" in docs/cli.md
(helper loops register more; not run, so not reconciled [U]).

(c) Middleware chain in `toolapi/server.go:6-12`: editRevisions, mutationReceipt, idReassignment, authoringDefaults,
fieldReferenceHint.

- API client: `lib/api/_client.ts` (250 lines; `API_BASE = "/api"`, cookie credentials, retry, 401 reload) + 14 domain
  modules (`lib/api/*.ts`, 7,978 lines including tests).
- i18n: use-intl. `web/messages/{en,zh,ru,de,es,fr,ja,ko}/` each 136 namespace JSON files, about 7,876 entries per
  locale (en 560,651 bytes), `import.meta.glob` plus English fallback merge (`src/i18n/messages.ts:1-40`); 58
  plural/select messages, 1,211 interpolated messages, 46 `t.rich(` sites. 308 files call `useTranslations`.
- UI kit: `components/ui` 2,157 lines on @base-ui/react 1.4.0, Tailwind 4 utility classes (8,151 `className=` sites),
  shadcn-derived `app/globals.css` (804 lines) with `--color-ingame-*` tokens for the game-like preview skin.
- Size by area (non-test lines): `components/workbench` 69,714; `app/[locale]/game-view` 62,993 (7,304-line page.tsx);
  project pages 18,401; `lib` 22,832; gui-renderer about 6.6k.
- Other deps: Monaco 0.57 (local copy via `scripts/copy-monaco.mjs`), recharts, html-to-image, react-image-crop,
  driver.js (tours), sonner, cmdk, lucide-react.

### 1.5 Coupling of the frontend to Go API shapes [V]

- 231 non-test files import `@/lib/api`; 509 `/go/...` path literals in `lib/api`; row types mirror database rows
  (`types/*.ts`, 2,369 lines: `project_id`, `*_en`/`*_zh`, `raw_extras`, `source`).
- The edit-concurrency protocol is baked in: `X-Edit-Revisions` header (`domains/focus/revision.go:58,135`) and
  `components/workbench/save-diagnostics/*` (582 non-test lines).
- Page level coupling is high (store + API + routing). Component level is mixed: `FocusTreeGraph` is a controlled
  component (`nodes: FocusNode[]` plus 12 callbacks, `focus-graph/FocusTreeGraph.tsx:79-120`) but still imports
  `focusTreeStore`, `contentLocaleStore`, `useBaseModDepKeys`, `toast`, `useConfirm`. The editors (EventEditor,
  IdeaEditor, CharacterEditor ...) each import 30-37 modules including stores and API clients and are not extractable
  without a rewrite.
- Conclusion: reuse at module level (pure TS and presentational pieces with injected data), never at page or store level.

### 1.6 Loopback security (also feeds section 5) [V]

`H/internal/server/server.go`: strict Host equality with the listener address (:48), Origin must equal
`http://<host>` (:52), `Sec-Fetch-Site` must be `same-origin` or `none` (:56), `X-Content-Type-Options`, `Referrer-Policy`,
CORP set. Web routes need a per-process random 32-byte session cookie (HttpOnly, SameSite=Strict, Path=/api/;
:77, :118-119), compared in constant time. The tool API needs a bearer token from `tools-token` next to settings.json
(created 0600 by `settings/settings.go:112-135`), constant-time compare (:90).
Gaps: the cookie is minted for any request that reaches `GET /` with the right Host (`serveWeb`, :93-120), so any local
process of the same user gets full control, including `GET /api/app/folders` (arbitrary directory listing,
`api/app.go:275-309`), `POST /api/app/quit` and install-into-mod-folder. That is an acceptable desktop trade-off and
an unacceptable network one. There is no Content-Security-Policy header (grep empty) and `web/index.html:8-10` has an
inline `<script>`. A companion that a hosted site talks to from a browser origin needs the opposite design (explicit
allowed origin, pairing token); Hagane's refuse-all-cross-origin model does not transfer.

## 2. Frontend editors, one by one

Cross-cutting facts first (they apply to every row below).

- Styling: Tailwind utility classes everywhere. Inline `style={}`: 494 sites in non-test TSX, 11 in focus-graph
  (`FocusContextMenu.tsx:35`, `FocusGraphNode.tsx:77`, `FocusGraphRuler.tsx:62,72,86,100`, `FocusTreeGraph.tsx:939,950,1009`,
  edge `style` at `FocusMutexEdge.tsx:60`, `FocusPrereqEdge.tsx:77`). Factory's rule (`web/README.md:30`, CSP in
  `crates/server/src/hardening.rs`) is no `style=` attributes and no inline scripts/styles.
- xyflow and CSP [I]: React applies `style` props through the CSSOM (`element.style`), which CSP `style-src` does not
  block; xyflow 12.10.2 positions nodes and the viewport with such props and ships a separate stylesheet
  (`import "@xyflow/react/dist/style.css"`, FocusTreeGraph.tsx:23). So the library should run under `default-src 'self'`.
  Our own code must still follow the source rule, which means dynamic positions (ruler ticks, context menu at pointer
  coordinates, minimap offset) are set with `ref.style.setProperty` in an effect or with SVG attributes, never a
  `style=` attribute. Needs a one-hour spike with the real header; node_modules was not available to confirm xyflow
  injects no `<style>` tag [U]. `html-to-image` (PNG export) needs `img-src data: blob:`, which the CSP already allows.
  Monaco injects `<style>` elements at runtime and is the likely real CSP problem [I]; the Factory CSP also blocks
  CDN loading, but Hagane copies Monaco locally.
- New dependencies for Factory (all need maintainer approval, GOAL-UI rule): @xyflow/react 12.10.2 (MIT; brings
  @xyflow/system, classcat, zustand 4, d3 packages), html-to-image 1.11.13 (optional; agent-tools `hoi4_focus_render`
  could replace it), react-image-crop (characters), a code editor for script boxes.
- Accessibility: 916 `aria-` and 192 `role=` uses across the app, but no jsx-a11y in `eslint.config.js`. Literal English
  strings in `aria-label` (50), `title` (14) and `placeholder` (140) would fail Factory's `i18n.test.ts` literal-text
  rule. Graph canvases rely on xyflow defaults for keyboard access (no `ariaLabelConfig`, `nodesFocusable` etc. set)
  and creation is pointer-only (double-click pane, drag handle) with xyflow's `deleteKeyCode` for nodes
  (`FocusTreeGraph.tsx:925`) and a window `keydown` for selected edges (`:870-885`). The side forms (FocusNodeEditor with reference dropdowns) give a keyboard path.
- i18n: 8 locales, but the English strings are what transfers (ADR-021 is English-only). Conversion work: use-intl ICU
  to i18next (58 plural/select, 1,211 interpolations, 46 rich-text sites). Some strings never reached message files:
  69 inline `zh:`/`en:` dictionaries in TS (for example `shared/editors/cwtoolValidate.ts:21-60`,
  `types/event.ts` labels like "Country Event / 国家事件").
- Tests: 317 test files, 1,815 `it(`/`test(` calls; 106 test files read source text with `readFileSync` and assert
  substrings (brittle contract tests). Pure-logic tests (focusTidyLayout, focusEdgeDisplay, exportTreeGeometry,
  controlledNodeSelection) are portable.

PATTERN (copy the design only), IGNORE.

## 4. Build and run feasibility (by reading only)

### 4.1 Linux and macOS build [V/I]
- No cgo (`import "C"` absent). Windows code is isolated by filename: `window_windows.go`, `fatal_windows.go`,
  `start_windows.go`, with stubs `window_other.go` (returns `errNoWindow`), `fatal_other.go`, `start_other.go` (Setsid).
  go-webview2 and go-winloader are imported only from `cmd/haganeworks/window_windows.go`. `internal/gamedir` already
  handles darwin and linux. So `go build ./cmd/haganeworks` should work on both; `--no-window` is the headless mode.
- The Go build needs `web/dist` first (`//go:embed all:dist`; the clone has no `web/dist`, so a Go build fails until
  `npm --prefix web run build` has run). CI works around it with a build artifact.
- Never tested off Windows: CI is `windows-latest` only (`.github/workflows/ci.yml:14,41`); only the dependency-submission
  job runs on ubuntu. README and CONTRIBUTING say Windows 10/11 is required to build. Tests with backslash paths exist
  (`paradox/vanilla_corpus_test.go:13` hard-codes `G:\Steam\steamapps\common\Hearts of Iron IV`, skipped when absent).

### 4.2 Headless in Docker as a service [I]
Possible only as an internal worker, not as the product. Blockers measured: bind address is hard-coded to
127.0.0.1 (`main.go:154,164`); Host and Origin checks are string-equal to that address (`server.go:48,52`), so a published
container port fails them; the session cookie is issued to any visitor; settings, game index (`gameindex.SetDefault`),
reference tables and CWTools dir are process-global (`api/app.go:47-49,64`), so one process serves one user; a project is
loaded whole into memory; game files must be mounted read-only. Patching bind address and allowed host is a few lines,
but the missing multi-tenancy is not. Our Rust server owns accounts, RLS and workspaces; a Go worker behind it would be
a second brain for the same project.

### 4.3 Test suite [V]
- Go: 527 test files, 2,266 `Test` functions, 9 Fuzz/Benchmark, 88,327 test lines (37.7 percent of non-test lines);
  58 `t.Skip` in 49 files, mostly "set HOI4_GAME_DIR / HOI4_GAME_ROOT" real-game gates (25 files). The default suite uses
  a synthetic mini game (`internal/gameindex/gameindextest/game`, files labelled "Synthetic test fixture written for

  importjob 3,677, mapgen 3,493; paradox 1,749; importsvc only 613 (thin for 12k lines).
- TS: 317 test files, 38,765 lines, 1,815 `it(`/`test(`; 106 files assert on source text.

  "bug-compatible" cases): these pin behaviour that no longer has a reference [I].
- Pass/fail status of any of it: [U], not run.

### 4.4 CI [V]
`ci.yml`: frontend job (npm ci, `npm audit --audit-level=low`, typecheck, eslint, design-token lint, set-state-in-effect

## 6. Strategic options

### 6.1 What is actually worth carrying over (sizes)
- Go ideas to port, about 5.8k lines of Go: clausewitz span/repair plan 1,238; drawio 398; dlc lint 389; dead-flag lint 261;
  perf lint 557; gamedir 186; export.Install 249; errorlog + playtest 1,176; savediagnostics 263; loc parser 384; receipt,
  id self-check, revisions about 730 (patterns).
- TS to port or rewrite: focus graph shell about 3.4k lines (after dropping layout); event and decision preview cards 438;
  save-diagnostics and revision-conflict UX 582; edge-display and selection helpers 141 + tests.
- Data to review before use: 34 + 14 knowledge articles, 42 field-reference tables, the 40-row coverage ledger, the finding-code
  catalog (158 `Code:` literals), en message files for the ported components.
- Not worth anything to us: row-based stores, REST client modules, export engine, importers, emitters, GUI renderer,
  map generators, game-view layers (63k lines), Windows shell.

### 6.2 Option A: harvest selected editors and ideas, freeze or archive Hagane Studio
Pros
- Cheapest. Keeps Factory's single source of truth (native files + Git) and one implementation of parser, validator,
  renderer. Fits the design-lab rule: each ported component is restyled anyway.
- Small and reversible: each harvested module arrives with attribution (`PROVENANCE.md`, path, commit 1e83162, GPL-3.0-only).
Cons
- Existing Hagane users lose their local app (the hosted site closes 2026-11-11 per the earlier note) unless a migration
  path exists. Their export ZIPs are native mod files, so Setup can import them, but with the consolidation losses in the
  ledger.
- Throws away the maintainer's newly granted ownership as a user-facing asset. Reputation risk if "taken over" means
  "abandoned".
Effort: Small-to-Medium in total, spread over stages: rules and data 5-8 days; pure TS modules 6-10 days; focus graph shell
6-10 days; previews 4-6 days. About 25-35 engineer-days for everything listed in 6.1.
Risks: provenance and licence paperwork (section 7); partial copies drifting from upstream, which is acceptable because
upstream is frozen.

### 6.3 Option B: Hagane Studio becomes the local/desktop edition, shares React editors with Factory via a common package
Pros
- Keeps the Windows desktop product alive and gives a local-first story without building a companion first.
- One React editor family in principle.
Cons (all measured above)
- Two data models cannot share editors: JSON rows with regenerate-on-export versus native files with source-bound proposals.
  The shared package would need a neutral document model plus two adapters, which is the adapter work of Option A plus a
  permanent compatibility layer.
- Two design systems and toolchains: Tailwind/base-ui/use-intl/zustand/SWR vs plain CSS/i18next/no state library, different
  CSP rules, different lint (jsx-a11y absent in Hagane). A common package must pick one; either side pays a rewrite.
- Two backends for the same responsibilities: Go parser/validator/renderer/map code (about 100k+ lines) next to Rust and
  agent-tools. This is the "two competing implementations" outcome, with three languages.
- Maintenance: 234k Go + 195k TS lines to own, no architecture docs, comments stripped, Windows-only CI, Python-parity tests.
- GPL-3.0-only on the shared package would force the package, and everything linking it in the hosted app, under GPL terms
  (fine for AGPL Factory) but never into the Apache-2.0 agent-tools without a relicense grant.
Effort: Large. Initial extraction 8-12 weeks [I], then about double the maintenance for every editor change.
Risks: maintainer bandwidth (hobby project), divergence on first change, local edition blocks Git-native workflows.

### 6.4 Option C: converge; port the valuable Go logic; one client serves hosted and local
Pros
- One implementation per responsibility (table in 6.6). Local use is served by the Factory client plus a small companion,
  matching the planned "local companion" in CLAUDE.md and the CSP `connect-src 'self'` constraint.
- The portable Go value is about 5.8k lines, so "port" is cheap compared with the size of the backend.
Cons
- The largest piece of work after A, and it must wait for the companion design (new ADR for CSP, pairing, threat model).
- Existing Hagane Studio users need a stated path and time frame.
Effort: A (25-35 days) plus companion modules 6-10 days plus importer/migration notes 3-5 days plus rule ports 8-12 days:
about 45-60 engineer-days over several stages [I]; no single large rewrite.
Risks: scope creep into porting game-view or map code (do not); relicensing of ports into agent-tools (needs the grant);
companion language choice (Rust keeps one toolchain; Go would make the companion a third language).

### 6.5 Recommendation: Option C, executed as "harvest first (A), converge second", reject B
Why C and not A alone: the companion needs gamedir/install/log-parsing and a decision about local-folder sync (Hagane already
solved discovery and safe install, and demonstrated a browser-only fallback with the File System Access API in Chromium).
A without a plan leaves those users and those modules orphaned. Why not B: sections 6.3 and 1.5; the shared package would
be the permanent cost of the data-model mismatch.

Sequence
1. Paperwork (section 7); decide the maintenance posture of the Hagane repo.
2. Phase 1 (with S04): port the pure items and the focus graph shell; port the save-diagnostics delta; feed the finding-code
   catalog and traps into test fixtures; add the dead-flag query and DLC rule to mod_index-based lint.
3. Phase 2 (with the companion ADR): port gamedir, safe install, log-parsing facts into the companion; define pairing and
   origin rules from scratch.
4. Hagane Studio: tag a final release, README banner pointing to Factory, security and data-loss fixes only, no features.
   Sunset trigger (to record as a maintainer decision): when Factory can import a Hagane export ZIP with a fidelity ledger,
   the companion handles local mod-folder sync, and focus/event/decision/character editors exist; then archive.

### 6.6 How it avoids two implementations of the same responsibility

| Responsibility | Single owner after C | Hagane disposition |
|---|---|---|
| Lossless lex/parse with spans | agent-tools `core/source` (TS) for tools; Rust workspace/Setup for the host | Go `paradox`/`clausewitz` frozen, never extended |
| Source-preserving edit | Rust host: proposals bound to file hash + span; agent-tools `source-update`/`rewrite` | idea of sha-guarded span plans ported once |
| Validation | agent-tools `script_validate`, `mod_index`, `impact`; one rule catalog | 158 finding codes become spec + test fixtures, each ported at most once |
| Rendering (focus, event, GUI, tech, map) | agent-tools render tools | Go guirender/mapgen frozen |
| Editors | Factory client (plain CSS, i18next) | Hagane React copied module by module, restyled; originals frozen |
| Project format | native mod files + Git | JSON-table projects are legacy; migration = Hagane "Export mod (ZIP)" -> Setup import |
| Local integration | companion | gamedir, install, log facts ported once |
| Tool/agent conventions | broker with grants | receipts, id and revision conventions as patterns |

How it fits native files + Git: Hagane's rows are never imported as truth. Editors receive a view model derived from
parsed native files (with source ranges), and every edit leaves as a proposal revalidated on the server. Hagane's
`edit_revision` and `source_snapshot` ideas map to file hashes and Git three-way merges; its "export never blocks" and
fidelity ledger become Setup scan honesty; the lossy consolidation it performs on export is the exact failure our design
exists to avoid.

## 7. Provenance and licensing steps before code moves [I, not legal advice]

1. Get the grant in writing from the copyright holder (the commit author is the entity "Hagane Works", no person named, no
   copyright lines in files): a short statement in a GitHub issue or commit in the repo, naming the maintainer, scope ("any
   use, including relicensing"), and whether the name and icon are included. Transfer or fork the repository under the
   maintainer's control.
2. Decide the target licence per destination: into AGPL Factory the GPL-3.0-only code is allowed as is (GPLv3 section 13);
   into Apache-2.0 hoi4-agent-tools it needs an explicit relicense grant, otherwise write from the rule specs only.
3. Put adapted files under a provenance note and headers (path, commit, licence) because the originals carry none.
4. Do not move: screenshots showing game data, game-derived runtime paths, brand assets, pet avatars (unknown provenance).
5. Record the decision in `docs/02-architecture/maintainer-decisions-2026-10-24.md`.
6. Knowledge text: use only after (1) and a game-version fact check; the wiki licence of the sources needs a look [U].
