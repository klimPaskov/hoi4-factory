### 2.1 hoi4-investigate (skills/hoi4-investigate/SKILL.md, 100 lines)

1. Purpose and activation
- Frontmatter (line 3): fire the moment a bug, regression or "why is X broken" appears, before writing any fix; confirm the mechanism against live platform state and the exported mod, verify the premise instead of trusting memory, a previous report or a green validate. It says to invoke it automatically on any bug report.
- When-to-use (lines 18-22): any bug/regression/in-game crash/"it worked last time"; whenever an agent reports "done" or "validate is green"; before scoping work off a plan doc, backlog item or memory note; auto-invoke, do not start patching.
- Receives control from: the cross-link footer of every build card ("error.log is the final gate -> hoi4-investigate", for example hoi4-build-api/SKILL.md:184, hoi4-build-scripting/SKILL.md:199-200), and from hoi4-mod-design step 11 (hoi4-mod-design/SKILL.md:143-144, 164).
- Hands off to: hoi4-build-api for how to apply the fix (investigate:88-89, 99) and hoi4-mod-design for the end-to-end loop (investigate:100).

2. Workflow (my words)
(1) No edit until you can point at the exact broken field, entity or exported line. (2) Re-check any premise that came from memory, plans, backlog, prior audits or status reports against current live state; anything older than a few days is suspect. (3) Treat an accepted write or a green validator as "accepted", not "correct"; re-read the entity or re-export and confirm the change landed on the right id; verify against the fresh artifact plus the game's own error.log. (4) If an agent fixed something through a mechanism you did not expect, treat it as an alarm and trace the real path. (5) Quantify guessed counts from the real artifact before fixing a "drop". (6) State the root cause with concrete evidence first; if only part is proven, fix only that part and note the rest. (7) For a crash to desktop, read the player's log folder before analysing any mod content (details under techniques). (8) Fix through the API, then validate, lint, rebuild through the export job channel, load the fresh ZIP in the game, read error.log.

3. Dependencies
- [P] entity GET routes, export/validate, lint/tree-validation, the export-job channel, MCP export_project (lines 90-96).
- [G] the player's own data folder (Documents\Paradox Interactive\Hearts of Iron IV\logs, crashes, dlc_load.json), counting entities, reading error.log.

4. Verification routine and false-positive avoidance
- A ladder of evidence is implied: request accepted (HTTP 200) < platform validator green < entity re-read < fresh re-export < game error.log. Only the last two count (lines 38-47, 84-85).
- "I changed the field" is not evidence; re-read it (lines 41-44).
- Surprise is a red flag: if an agent "fixed" something with an invented mechanism, assume the success report may be satisfying the letter of the ask (lines 45-47, 82).
- Magnitudes get measured, not guessed (lines 49-52).
- Never patch just to turn a validator green (lines 55-56).
- Never call a reproducible in-game issue "just vanilla/environment" without reproducing it in a clean setup (line 85).

5. Notable techniques (file:line)
- T1. Iron Law: root cause first, applied to edits and API writes alike. 26-28.
- T2. Premise red-flag phrases that force a re-check: "the plan says", "memory mentions", "a previous pass found", "should/probably/usually". 32-36. Staleness rule of thumb: more than a few days old is suspect. 30-32.
- T3. Evidence ladder (see 4). 38-47.
- T4. Magnitude measurement before a fix. 49-52.
- T5. Output discipline: evidence-first root cause statement, partial fix allowed. 54-56.
- T6. Crash protocol. Read, in order: logs/game.log (the last line carries the start date the game actually reached and the last subsystem loaded, which localizes the phase), crashes/hoi4_<timestamp>/exception.txt (an access violation means an engine null dereference, so error.log stays quiet), and dlc_load.json (active mods/DLC, to rule out conflicts). It explicitly authorizes reading these because they are the player's own game output. 58-69.
- T7. Never assume the start date from what your mod intends. If game.log shows a start you did not design, your custom start did not load; re-export, reinstall, re-check log before anything else. A multi-day crash hunt is cited that assumed an early start while the game was executing history years later. 70-77.
- T8. Six-item anti-pattern list ending with "do not dismiss without clean repro". 79-85.
- T9. Fix path with retired-route warning (the old download route times out on big projects and enforces a retired gate). 87-96.

6. Version-sensitive or doubtful claims
- Log file names and structure: confirmed (V40). Outer .mod / dlc_load.json relationship: confirmed structurally (V41).
- "Access violation means nothing useful in error.log": plausible, inferred; not tested.
- Fix-path routes are platform-time-sensitive (they changed three times in the CHANGELOG, section 3).

### 2.2 hoi4-mod-design (skills/hoi4-mod-design/SKILL.md, 231 lines; DESIGN_DOC_TEMPLATE.md 58; CONCEPT_TEMPLATE.md 52)

1. Purpose and activation
- Frontmatter (line 3): start of a new mod or large content project and drive it end to end: turn a creative brief, concept docs or a story idea into a playable mod through design (base-mod audit, feasibility root, decision-locked bible, author-facing doc, phased roadmap) and then the build, export, game-verify, fix loop. The author does only conversation and in-game verification.
- When to use (lines 18-21): brief/story idea in hand; new mod or overhaul, especially a submod on a large base mod (TNO/KR/TFR named); it is explicitly the orchestrator that delegates mechanics.
- Receives: author's filled CONCEPT_TEMPLATE (lines 49-51). Hands off: build mechanics to hoi4-submod/hoi4-build-api (127-131), in-game failures to hoi4-investigate (143-144), cross-entity wiring to hoi4-wiring (230).

2. Workflow (13 steps in my words)
Part 1, design: (1) take creative direction only from the author's own material and inventory every lore element, named entity, timeline beat, puppet and mechanic; (2) for overhauls, audit the base mod with parallel read-only passes (per playable nation plus cross-cutting); (3) find the single feasibility root of the dissonance; (4) write the bible; (5) gap-audit it against the step-1 inventory; (5b) run domain-expert self-critique passes; (6) write the author-facing design doc with tiered questions; (7) lock a phased roadmap with dependency boundaries and depth allocation.
Part 2, per phase: (8) build all entities for the phase through the API; (9) export and self-verify before touching the author's time; (10) the author load-tests with a short specific checklist; (11) iterate through hoi4-investigate, re-export as v1/v2/..., keep the last accepted export as the demo snapshot.

3. Dependencies
- [P] authenticated API building, export/validate, lint/tree-validation, base-mod reference index, vanilla reference data / states picker.
- [G] documents (bible, audit, roadmap), parallel read-only analysis, chat with the author, the author's game.

4. Verification routine
- Run the platform checks before the author's game test (step 9, lines 133-136) so the human's run is not wasted on what a validator would find.
- But green validation does not mean it loads. The listed killers are invisible to validators: bad effect/modifier tokens, wrong recruit_character location, an undefined ideology, a country with no capital. The in-game error.log pass is mandatory and a few export-fix cycles (v1 to v3) are normal (lines 158-163).
- Align versions first because a base-mod version mismatch is a crash that is not your content (140-141).
- Phase is "accepted" only after the author's game report (143-146).
- The meta-verification: verify prior audits before building on them (63-64) and verify feasibility by tracing the real setters, never assuming (78-79).

5. Notable techniques (file:line)
- T1. "Front-load the audit and design bible; never go step-by-step" because per-phase rediscovery of base-mod facts causes inconsistency. 23-25.
- T2. Operating model: the human does only chat and in-game testing; the agent never tells them to click a workbench, and the text gives the catch-phrase to watch for. 27-34, 158.
- T3. Recommend-then-decide: lead each fork with the agent's pick and reasoning, never a pile of open questions; work in coherent chunks and pause for the author to check the logic. 35-40.
- T4. Author's source is the only creative authority; the base mod is mechanical baseline, never canon. 44-48, 165.
- T5. Per-nation 5-point audit: start state, storyline, custom mechanics, dissonance surface (where base content contradicts the new vision, with severity), build-on (reframe vs gut). 55-60.
- T6. "Audit what the bookmark actually loads, not raw entity counts": separate live from dead/cut/debug-gated arcs by following the active bookmark and focus-tree loading. 60-64.
- T7. Feasibility root: trace where key global flags are set; a cascade hanging off one suppressible event can be made dormant by cutting that root; multi-rooted means scope balloon. 74-79, 167-168, 204-209.
- T8. Bible requirements: "decide everything derivable, surface only genuine forks", provenance tags (locked / mine-derived / open-for-author) so derivations are never mislabeled as author decisions. 84-86, 169.
- T9. Reusable alt-history engine: date-gated historical spine, divergence at a point where history could really have turned, endings derived from two real structural dilemmas as two orthogonal axes giving four endings; historicity tags per ending; lock tone as a first-class decision and treat tone feedback as a rewrite pass across all text. 87-103.
- T10. Domain-expert self-critique before locking (historian pass, game-numbers pass sanity-checking against vanilla number ranges). 109-114, 218-222.
- T11. Capability recon before promising a custom mechanic (hooks, workbenches, standalone support). 181-186.
- T12. Meter-mechanic guardrail: unbounded accumulators overflow and get idle-farmed; recompute each period from sticky "earned" plus current "positional" components, clamp, and hide raw totals behind dimensions and tiers. 187-190.
- T13. Multi-nation ownership rules: the leader nation owns faction creation, members only join; agree cross-line global flag names up front; never write one nation's history from another nation's build. 174-177.
- T14. Never hand-guess vanilla data (state ids, portrait/flag names, ownership); pull from reference data; reuse a vanilla tag to pick its art. 191-194.
- T15. Output set naming: index, baseline audit, story bible, locked roadmap, design doc, versioned exports; for heavy mods also per-faction backbone, node-level spec per nation per phase, mechanic system rules, world-year setup with real state ids, capability-recon note. 148-154.
- T16. Mechanism hiding: keep platform detail out of the author-facing doc. 170.
- T17. DESIGN_DOC_TEMPLATE: authoring rules block (strip mechanism, mark undecided beats, questions at the bottom in tiers, author's language, open by confirming it is drawn from their material) lines 5-10, 14; questions tiered A story gaps / B design calls with recommendation / C quick confirms with defaults, lines 42-54; closing line noting the first slice already proceeds in parallel, line 58.
- T18. CONCEPT_TEMPLATE: 12-section input brief; blanks are acceptable and become the question list (lines 3-5, 51-52); calls out faction/alliance structure as easy to forget and decisive for day one (36-37); notes whole-state ownership granularity (49).

6. Version-sensitive or doubtful claims
- recruit_character "only at history setup" (named among the invisible killers, line 162; also hoi4-wiring:136): not supported by the documentation; see V10.
- Hooks named for the custom meter (on_monthly, on_capitulation, line 212-213): both exist in 1.19.3 (V15).
- "States are form-level" (lines 131, 193-194) is a platform limit, not a game limit.

### 2.3 hoi4-submod (skills/hoi4-submod/SKILL.md, 213 lines)

1. Purpose and activation
- Frontmatter (line 3): building or extending a dependency-style submod (declares a base mod like TNO/KR/TFR and references its characters, tech, art, ideologies); covers additive architecture, base-mod reference index, base-mod-idiom toolkit, assets and the append-only limit. Invoke for "make or add content to a submod of <base mod>".
- Lines 21-27: also use it to settle architecture before scoping any feature; defers routes to hoi4-build-api and orchestration to hoi4-mod-design.
- Receives from hoi4-mod-design (build step), hands to hoi4-build-api, hoi4-build-characters (91), hoi4-wiring (196), and the full cross-link list (204-210).

2. Workflow
(1) Accept additive-on-canon as the only architecture; redesign any "suppress" idea as a reaction. (2) New empty project, declare the exact dependency names and align supported version. (3) Ingest the base mod's index (stage files, then index). (4) Build via API. (5) Use the base-mod idiom toolkit with real tokens from the index. (6) Handle states through the platform seed route or byte-exact copies. (7) Ship own assets via upload. (8) Understand super-event scheduling quirks. (9) Validate on the platform, then load in game and grep error.log for your own identifiers; retime long delays for tests.

3. Dependencies
- [P] import/stage-files, import/basemod-index, basemod-index/refs and ideology-registry, seed_states_from_vanilla/get_states/edit_state, upload endpoints, export/validate, lint, the PAT env vars (lines 47-77, 107-121, 151-157, 165-172).
- [G] the toolkit effects (promote_character, set_character_name, kill_country_leader, create_country_leader, set_politics, load_focus_tree), the iron rules on states and tags, error.log grepping, retiming delayed events.

4. Verification routine
- Platform validate and tree-validation first, then the real game: read logs/error.log and grep for your own tokens (tag, focus/event ids, ideology, state ids); base-mod animation/entity noise is not yours; logs/text.log shows loc collisions (lines 165-172).
- Headline distrust: "export succeeded" proves nothing; a typo'd cross-reference can be dropped silently and only surface in game (197-198).
- Long-delay features: retime the trigger in a test build, then restore (174-177).
- Index-backed lint turns on only after ingest; un-indexed submods fall back to trusting all references, so a quiet lint is not coverage (62-69).

5. Notable techniques (file:line)
- T1. Additive-on-canon rule and the honest list of what cannot be done: there is no disable_event, on_actions only append, scheduled events cannot be cancelled; trigger denial through an on_startup flag works only when the target event has a checkable trigger. 18-19, 29-39.
- T2. Two-step base-mod index ingestion: stage the files, then index; index-only (content discarded), shared across submods of the same dependency; documented exception to the platform's route migration inline. 47-60.
- T3. Dual benefit of the index: autocomplete for real base-mod ids and lint that flags undefined base-mod tags/states/ideologies/focuses/decisions; explicit trust-all fallback before ingest. 62-71, and hoi4-mod-design/SKILL.md:65-72.
- T4. Idiom toolkit: promote_character with ideology to activate an existing latent leader role; add_country_leader_role is rejected on a character that already holds that role; rename by set_character_name; death by kill_country_leader; ruling_party takes the ideology group while ideology and promote_character take the subtype; swap a base nation's focus tree with load_focus_tree because an explicit load beats tree scoring. 83-98.
- T5. Read the base mod's ideology registry before choosing tokens, because base mods may redefine the ideology space. 93-95.
- T6. State handling: never write provinces from memory; rename a state only through a loc override and never change the name key inside the state file; check tag against the live vanilla roster; layouts drift between game versions; byte-for-byte copy including irregular original filenames if using local files. 107-143.
- T7. A new custom tag that owns no state is dead at start (not listed in the bookmark, on_startup never fires) until a state is assigned. 145-147.
- T8. Own-asset rule: referencing another mod's sprite name gets dropped and shows a placeholder; upload bytes. 151-157.
- T9. Super-event scheduler switch semantics (a quirk a GET will not reveal). 159-163.
- T10. Test retiming of long delays. 174-177.
- T11. Hook sanity: some base mods comment out hooks, so confirm your intended hook actually fires; prefer your own on_monthly_<TAG>/on_weekly_<TAG>. 193-196.
- T12. Idea attach control: a per-idea switch to prevent auto-attachment at game start when the idea should arrive later via focus/event. 190-192. [P]

6. Version-sensitive or doubtful claims
- add_country_leader_role rejection: confirmed with a nuance, it is per ideology (V02). set_character_name argument: misleading (V03). Ruling party group: confirmed (V04).
- BRN since 1.18; state 333 and 1023 filenames; layout drift: confirmed (V32, V33).
- "STATE_<id>:0 triggers a loc-key collision that vanilla wins": unverified (V36).
- "No disable_event": confirmed from the docs (V35). But see the internal tension with _timeline-and-replace-path.md:35-36, 85-86, which allows shadowing a base file with a neutered copy.
- "Base mods comment out on_ruling_party_change": the hook exists in vanilla (V16); the base-mod behaviour is unverifiable here.

### 2.4 hoi4-wiring (skills/hoi4-wiring/SKILL.md, 145 lines)

1. Purpose and activation
- Frontmatter (line 3): use when connecting workbenches into live behavior: focus fires event, option sets flag read later, on_action hooks, leader succession, cosmetic-tag rename, scripted-snippet reuse, and scope passing. Invoke whenever a build step crosses two entities or asks "how do I make X trigger Y".
- It is the cross-cutting card (lines 13-17); single-entity maps are in the build skills. Hands to all build cards and to hoi4-submod/hoi4-mod-design (139-145).

2. Workflow
Section 0: for every token placed into a raw field, check that it exists and that its scope is legal where it runs. Then pick one of six chains (focus fires event; choice sets flag or variable read later; automatic firing through on_actions; leader succession or allegiance flip; country rename plus dynamic modifier; reuse via scripted blocks and event targets), each given as a token sequence plus its footgun. Section 2 gives the scope table. Section 3 self-check: validators first, then game error.log, then a per-chain checklist (tokens present in output; setter and reader in same scope; one active leader per ideology; rename has display-name loc in both languages; snippets called with = yes).

3. Dependencies
- [P] Events workbench fields (on_action_attach, auto_fire_on_startup), export auto-guard, effect_tooltip_locs, scripted snippets workbench, validate/lint routes (lines 59-67, 55-57, 108-118).
- [G] the chain token sequences and scope semantics.

4. Verification routine
- Same two-stage platform then game. In addition a per-chain assertion list (119-122) and the explicit caveat that lint can warn about submod base-mod refs but local dangling refs are silently dropped by the export gate with no lint warning (111-115). The way to see local dangling refs is the relations graph (field-reference/_validation-tools.md:6-15).

5. Notable techniques (file:line)
- T1. "Validate the token AND its scope." Two questions per token: does it exist, and is the scope legal. The number-one wiring bug is a country-scope effect run in a state or iterator scope, which silently does nothing. 26-34.
- T2. On_action hook names are attach points, not effects or triggers, so a token validator must not flag them. 36-38, 128-129.
- T3. Flag/variable handoff: the flag lives on the country that executed the setter; the reader must run in the same scope; setters have no auto-tooltip, so a reward made only of flag/variable changes needs a custom tooltip. 49-57, 125-126, 131.
- T4. On_actions are global attach points; an unguarded effect would run for every country. A self-requeuing heartbeat event fires itself again. 59-67.
- T5. One active country_leader per ideology; a second same-ideology leader with no promoting event is a dormant duplicate; succession is event driven (kill plus create), allegiance flip with the same person is a different effect. 68-74, 132.
- T6. Cosmetic tag swaps the internal tag only; the visible name is separate localisation keyed by the cosmetic tag and a second form; both languages needed. 76-81, 133.
- T7. add_dynamic_modifier declares a slot only; the stat definition must exist elsewhere. 81-84, 134.
- T8. Reusable scripted blocks must be called with "= yes", and they inherit the caller's scope; event targets persist across events while PREV and FROM do not survive a fresh event fire. 85-93, 135.
- T9. Scope-symbol table (THIS, ROOT, FROM, PREV, event_target:NAME) with "state iterators cannot run a country effect directly; address the owner". 95-106.
- T10. recruit_character called out as history-only. 136-137.

6. Version-sensitive or doubtful claims
- Cosmetic tag loc "_DEF adjective form": contradicted (V06).
- add_dynamic_modifier "days = -1" in chain 5 (line 77): unsupported (V07).
- recruit_character history-only: unsupported by docs (V10).
- Event-target persistence: unverified and conflates scoped and global targets (V47).
- "Second same-ideology leader is dormant": consistent, but the docs say the kill effect promotes the next in line (V05).

### 2.6 hoi4-build-api (skills/hoi4-build-api/SKILL.md, 184 lines)

1. Purpose and activation
- Frontmatter (line 3): about to drive the platform's workbenches through authenticated API; route table, payload shapes, export idioms; invoke when hoi4-submod or hoi4-mod-design reaches "build via API" or when a route/field shape is needed.

2. Workflow
(1) Learn a workbench's exact shape by GET, then POST the same shape (defaults fill omissions; PUT is partial). (2) Use PAT bearer auth and always set a User-Agent. (3) Consult the route table (about 35 resources). (4) Apply idioms a GET will not reveal. (5) Validate, lint, rebuild via the export job channel and read native warnings. (6) On a 422, GET an existing entity of that type and copy.

3. Dependencies: entirely [P] (REST routes, PAT, CDN behaviour). The generic residue is in section 4 idioms.

4. Verification routine: section 5 (lines 156-173): validate, lint, export job with status poll, read native_warnings from the status call (the place where the export reports what it dropped, line 169), then error.log in game.

5. Notable techniques (file:line)

## 5. Weaknesses, internal inconsistencies and things not to copy
---------------------------------------------------------------------------

1. Suppression is declared impossible in one place and offered in another. hoi4-submod/SKILL.md:29-39 and 180-181 say a base mod's events cannot be cancelled and the platform only appends, while field-reference/_timeline-and-replace-path.md:35-36 and 80-86 tell you to shadow a base or vanilla event file with a neutered same-name copy. Both are true for different tools (the structured workbench cannot, the raw-file route can), but the reader is not told. For a general kit the honest statement is: no script switch exists to disable an event (V35), file-level shadowing is the only suppression, and it freezes a copy of the original that goes stale.
2. The wiring self-check says project-local dangling references are silently dropped with no lint warning (hoi4-wiring/SKILL.md:111-115), yet the relations graph reports exactly those as unresolved (field-reference/_validation-tools.md:6-15; hoi4-build-api/SKILL.md:101). The fix is to run the graph in the self-check; the skill does not say so.
3. One permanent-attach recipe uses days = -1 (hoi4-wiring/SKILL.md:77) while their guide omits days (guides/dynamic-spirit-from-variables.en.md:124); vanilla never uses a negative value (V07).
4. A copy-paste defect: the curl recipe in hoi4-build-api/SKILL.md:164 and 166 has a literal backslash-n where a line continuation should be, whereas the same recipe at field-reference/_editing-existing-mods.md:47-49 is correct. Cause (inferred): the recipe is duplicated across files and one copy rotted. Lesson: keep one canonical copy of a recipe and link to it.
5. Hand-curated vocabulary drifted (V45, V46) even though the same page says it is only a filling aid.
6. Release lag between the two delivery channels is a documented hazard (CHANGELOG:25-27, 61-65): an agent on MCP reads old field-reference while an agent with skill files reads new text.
7. The auto-update directive (README.md:110-115 and the header block of every skill, for example hoi4-investigate/SKILL.md:6-9) makes every session pull and then trust moving instructions from a remote repository. That is convenient for a hobby product and an instruction-supply-chain risk for ours. They also offer pinning (README.md:115). See H-A100.
8. Many rules are phrased as absolutes ("never") that the evidence supports only in a narrower form (V02, V10). A catalog entry should carry the scope in which the rule was observed.
9. The platform vendors, validates and exports; most of the clever machinery (export gate, tag guard, tooltip injection) is not available to a generic kit. Anything that says "the export does X for you" is platform behavior to re-implement, not a technique to copy.

Platform-specific mechanics to ignore for generic use: PAT auth and User-Agent handling, /api/go route family, workbench resources and field names (dm_id, effect_tooltip_locs, raw_extras, scope_kind, source flag semantics), 409/422 behaviours, export job API and native_warnings, seed_states_from_vanilla/get_states/edit_state, upload endpoints, auto_fire_* super-event switches, auto_attach_on_start, the 25 MiB binary cap, the template-based raw-file routes, UI panel beta, the translate API, and the translation quota.

### A. Investigation and debugging

H-A01 Root cause before any edit
- Idea: forbid every edit, API write or patch until the agent can name the exact broken field, entity or output line. If it catches itself proposing a change earlier, it goes back to finding the cause.
- Src: INV:26-28, 54-56 (state evidence first, then fix; fix only what is proven; never patch just to turn a validator green).
- Class: generic. Area: investigation and debugging.
- Example: an event option calls country_event with an id that does not exist. The agent must first show the option, the missing id and the file it came from before touching anything, instead of adding a stub event that merely silences the warning.
- Home: several (Kit rule plus Chaos Redux workflow; Factory agent-loop policy for "fix" requests).

H-A02 Re-verify the premise against live state; use trigger phrases
- Idea: facts that come from memory, plan docs, backlog items, earlier audits or status reports are point-in-time; before scoping, re-read the current files. A list of tell-tale phrases ("the plan says", "a previous pass found", "should", "probably") tells the agent when it is about to rely on a stale premise. Anything more than a few days old is suspect by default.
- Src: INV:30-36; also DES:63-64 (re-verify a prior audit before locking on it).
- Class: generic. Area: investigation and debugging / agent workflow design.
- Example: a handoff note says focus CR_x_a was renamed to CR_x_alpha. Before editing a prerequisite, grep the current focus file for both names; the note may predate a later revert.
- Home: several (Kit rule; Chaos handoffs; Factory stage handoff template already moves in this direction).

H-A03 Evidence ladder: an accepted write or a green validator is not proof
- Idea: define explicit rungs of evidence: request accepted, validator green, entity re-read, artifact rebuilt, game error.log clean, in-game observation. Only the higher rungs close a bug. Verify against the real artifact (fresh export plus the game's own log), never against an intermediate signal.
- Src: INV:38-47, 84-85; SUB:197-198; DES:158-163.
- Class: generic. Area: validation / avoiding false success reports.
- Example: a static validator passes a mod whose event uses a token that only the game rejects at load; the error.log line is the only rung that sees it.
- Home: several (Kit core rule; Factory acceptance rows already distinguish source parsing, rendering, game execution; Chaos validators).

H-A04 A surprising fix mechanism is a red flag, not cleverness
- Idea: when an agent reports success through a path nobody expected (for example it "fixed" a missing loc line by adding the key to a file the game never loads, or by relaxing a check), the reviewer treats the surprise as a trigger to retrace the real path.
- Src: INV:45-47, 82.
- Class: generic. Area: agent workflow design / validation.
- Example: a sub-agent reports "focus tree now loads" after it moved the focus into a new file; the review checks whether the original file still defines the same focus id twice.
- Home: several (reviewer step in the Factory agent loop; Kit review checklist).

H-A05 Measure the magnitude before fixing a "drop"
- Idea: quantify any guessed count from the real artifact (list the entities, count the validator findings) before spending effort; the real number is sometimes zero.
- Src: INV:49-52.
- Class: generic. Area: investigation.
- Example: "we lose dozens of loc keys at load": count distinct duplicate-key lines in text.log first; if there are three, the fix is three renames, not a loc pipeline rewrite.
- Home: Kit / Chaos.

H-A06 Crash triage reads the player's own logs before analysing mod content
- Idea: for a crash to desktop, read in order: the last lines of logs/game.log (the in-game date and subsystem reached), crashes/hoi4_<timestamp>/exception.txt (exception class; an access violation is an engine null dereference and will not appear in error.log), and the active mod list (dlc_load.json, plus mods_registry.json in the crash folder, inferred extra). Only then read content.
- Src: INV:58-69. Verified file names and layout (V40).
- Class: generic. Area: investigation and debugging.
- Example: a CTD right after the loading bar: game.log ends at "Start-date" lines and the exception is C0000005, so inspect country history, state ownership and capital settings for the played tag rather than hunting event text.
- Home: Kit (a crash-triage skill and a small log-summary script); Factory (a "paste or upload crash folder" tool, since the hosted app cannot read the player's disk); Chaos.

H-A07 Confirm which start date and bookmark actually ran
- Idea: never assume the start the mod "intends"; the last log line's in-game date is ground truth. If it differs from the design, the whole analysis is built on the wrong world, so first fix what the player selected (or what the mod offers as default).
- Src: INV:70-77; FR/_timeline-and-replace-path.md:28-34 (the case of vanilla's 1936 bookmark resurfacing).
- Class: generic. Area: investigation.
- Example: a mod meant to start in 1748 crashes at a date-gated vanilla block; game.log shows the player started the 1936 bookmark.
- Home: Kit / Chaos.

H-A08 Outer launcher .mod versus inner descriptor drift check
- Idea: the launcher uses the outer mod/<name>.mod file that dlc_load.json lists, and its replace_path lines must match the inner descriptor. After any manual reinstall or update, compare the two; a stale outer file silently resurrects vanilla directories.
- Src: FR/_timeline-and-replace-path.md:28-34. Verified layout (V41).

- Example: replace_path = common/bookmarks exists in the inner descriptor only; the player sees vanilla bookmarks and starts a world the mod was never built for.

H-A09 Reproduce in a clean setup before blaming vanilla or the environment
- Idea: dismissing a reproducible in-game issue as "just vanilla" is an explicit anti-pattern; reproduce in a clean mod set first.
- Src: INV:85.
