# HOI4 Factory: current-state audit for the expansion plan

Audited tree: `<projects>\hoi4-factory`, branch `main`, commit `7c70b0c` (clean at start). Read-only audit. All paths below are relative to that root unless they start with a drive letter. Line numbers are 1-based and refer to the files as read on 2026-10-31.

Evidence kinds used in this report:
- **[code]** read in source under `crates/`, `migrations/`, `web/src`, `compose.yaml`, `docker/`.
- **[doc]** a planned or decided statement in `docs/` or `evidence/`. A "Proposed" spec is design intent, not behavior.
- **[absent]** searched for and not found (grep over `crates`, `web/src`, `docs`, `evidence`, `migrations`).

Not run: nothing (no builds, tests, Docker or model calls). Test counts below come from `grep` of test attributes and from recorded evidence files, not from a fresh run.

---

## 0. Headline findings

1. **Implemented is S01 plus S02 only.** A hosted, multi-tenant foundation exists: accounts, projects with four roles, PostgreSQL row-level security, server workspaces with a controlled Git layer, ZIP/folder upload, GitHub App import (read-only), the HOI4-Mod-Setup flow over HTTP, a read-only game-reference check, and a React Setup wizard. Everything in the new request areas (autonomy modes, jobs, notes, tours, Git workflow beyond a baseline, drift, graphics) is **not implemented**.
2. **There is no task, run, attempt, grant, event-stream, approval-card (other than Setup), memory, canon, notes, issue/PR, webhook, push, invitation or agent route in this checkout.** `crates/agent` contains provider adapters, an SSE parser, a frame protocol and cost estimates and is used in production only by the server's Setup-analysis model client (`crates/server/src/model.rs`). S03 crates (`crates/tasks`, `crates/broker`, `crates/hoi4-tools`, migrations 0600-0799) are planned in `evidence/S03/scope.md` and are absent here.
3. **The planning docs already contain a rich authority model that the new areas must plug into**: C-03 RunEvent, C-04 ToolReceipt, C-06 ContextBundle, C-07 MemoryItem/FeedbackEvent, C-08 ApprovalGrant (revocation epoch, standing grants, "a grant cannot exceed the grantor's role"), SPEC-003 task/attempt state machines, SPEC-005 review records and in-app GitHub hub (ADR-018). Autonomy modes, jobs, Git workflow and Drift are largely **extensions of existing contracts**, not greenfield.
4. **Genuinely uncovered**: Kanban/project view, labels/milestones/acceptance criteria on native tasks, user-editable notes or an Obsidian-style workspace, any first-run tour or in-app help, spec-versus-implementation drift detection as a product or dev feature, image/GFX generation pipelines beyond a spec, a browsable decision history, configurable approval checkpoints, mid-task mode switching, a review queue.
5. **Documented tensions that need a maintainer decision** are listed in section 3 (ADR-022 "no memory page", ADR-007 single writer, ADR-012 web-only, ADR-018 GitHub-authoritative issues, mode-versus-privilege wording, REQ-042 with no stage packet, role matrix).

## 2. Planned design already covering the new areas

Statements are from proposed specs unless marked as a recorded maintainer decision (ADR-011..ADR-025 are recorded decisions in `docs/02-architecture/maintainer-decisions-2026-10-24.md`; ADR-001..010 are provisional, in `docs/02-architecture/options-and-decisions.md:61-88`).

### 2a. Autonomy modes, grants, approvals, pause/revoke, lifecycle, review boundaries

**Covered**
- **Three interaction modes with one authority model** (`docs/01-product/visual-and-autonomy-model.md:7-13`): Visual, Hybrid, Autonomous. Autonomous = "Approve objective, scope, limits and checkpoints" / "Progress without an open canvas" / "Every effect passes host authorization". "The mode does not determine privilege... Permission comes from the active grant and operation preconditions" (L13). "Changing modes does not silently add capabilities" (L27). SPEC-007:37: "The product stores the mode as an interaction preference. Authorization is a separate grant with enforceable limits" and Autonomous mode "reports at policy checkpoints". REQ-009, REQ-010, REQ-014, REQ-015.
- **Grants (C-08)** (`docs/02-architecture/contracts-and-interfaces.md:73-79`): grant ID, grantor and role, workspace/run scope, operation classes, roots, provider destinations, cost/time/attempt/change limits, expiry, policy version, revocation epoch. "Some grants authorize a plan class, others a specific proposal hash. The UI states which one applies." Publication classes (local commit, push owned branch, PR creation, repository creation, default-branch integration) are separate from editing classes. "A grant cannot exceed the grantor's project role." "Existing valid authorization is reused within scope rather than repeatedly requested." SPEC-011:50-54 lists categories (read indexed source, create proposal, apply owned changes, run named validator, local commit, push owned branch, open PR, create repository, integrate into shared default branch) and says "A standing grant can authorize multiple bounded operations. New scope, a changed executable or a wider outbound data policy requires a revised grant."
- **Grant examples**: read / proposal / apply / commit / merge grants; "The default small focus task can authorize edit, validate and branch commit while reserving main-branch integration for review" (`visual-and-autonomy-model.md:23-27`).
- **Approval cards / review binding** (`visual-and-autonomy-model.md:52-58`): review cards bind to an immutable proposal hash, show changed paths, semantic impact, previews and exact validation coverage; plan approval authorizes only its operation class; "A proposal changed after exact-result approval requires a new approval or a still-valid wider grant"; "Protected policy, credentials and approved canon are outside ordinary content-edit grants." SPEC-005:31-39 (review record: reviewer account and role, decision, time, proposal hash, evidence set, rationale; "A standing task grant may authorize bounded apply or commit without another modal prompt. The host records which rule authorized the decision"). C-02 ChangeProposal (`contracts:31-37`). S04-W4 "Unified change card".
- **Pause/revoke/steering** (SPEC-003:53-61; REQ-015; SPEC-011:54; C-08): pause is a durable scheduler condition recorded with expected task version and C-03 event; active operation settles at a safe boundary; "The host revokes future effect capability before signalling the worker"; steering is a visible event; "A scope expansion creates a revised plan and checks whether the existing grant covers it". Scenario 3C in `docs/01-product/users-and-workflows.md:60-66`: an unattended task "pauses for an uncertain side effect, a budget limit, a scope violation or a meaningful required approval. It does not ask the user to approve every harmless read." Tests ORCH-05/06/07, VIS-06/07, T-RUN-03, EXT-03.
- **Task lifecycle**: authoritative states in SPEC-003:21 `planned, ready, running, waiting_for_input, in_review, completed, blocked, cancelled`; attempts (L23) `running, interrupt_requested, reconciling, succeeded, failed, cancelled, unknown_effect`. Presentation diagram (Draft/Approved/Running/Paused/Review/Reconcile/Revision/Accepted) maps to those (`visual-and-autonomy-model.md:50`). SPEC-003:21: "A task records objective, requirement IDs, bounded artifact scope, dependencies, owner, acceptance policy, current version and **selected mode**." Completion "is determined by acceptance policy, not a model's assertion" (L35).
- **Review boundaries**: "Review is required only at the meaningful boundary established by the existing grant and project policy" (SPEC-007:11); "Task notifications represent a blocker, completed review boundary or meaningful fault, not every internal step" (`visual-and-autonomy-model.md:21`). Roles bound approval: Contributor cannot `ApproveProposal` (`crates/accounts/src/model.rs:62-66`); "an agent run started by a member carries that member's role as an upper bound" (SPEC-005:91).
- **Implemented analogue today [code]**: the Setup wizard is the only working checkpoint flow: evidence approval, confirmation of exact values, plan approval bound to plan hash and root identity (withdrawn on any conflict decision), apply consuming the approval, rollback-only recovery after partial apply (`crates/server/src/setup_api.rs` module docs; `setup_approvals` unique active approval per plan).
- **Planned build**: S03 (grants, pause/revoke, durable tasks, minimal task screens), S04 (all three modes on the focus slice, change card, `REQ-014`), S05 (cross-session recovery).

**Missing**
- **Configurable approval checkpoints**: no document lets a user or project define *where* the agent must stop (per step type, per path set, per cost, per operation class) other than policy-derived stops (uncertain effect, budget, scope violation, "meaningful required approval") and the grant's operation classes. No checkpoint object, template or presets named "fully autonomous / semi-autonomous / human-in-the-loop".
- **Mode switching mid-task**: only implied by "Changing modes does not silently add capabilities". No operation, event type or UI behavior for switching a *running* task's autonomy level; "Switch model" (SPEC-002:52) is defined, "switch mode" is not. `selected mode` is a task field (SPEC-003:21) with no transition rule.
- **Review queue / inbox**: none across tasks or projects. Closest: the Changes panel for one task; lane-C owner review of `KnowledgeCandidate` (SPEC-004:63); in-app GitHub PR list (ADR-018). No pending-approvals list, SLA, reassignment, or "who can approve" routing beyond roles. The notification channel ("task notifications") is not defined (in-app? email? none specified).
- **Decision history**: pieces exist as data (C-03 events, C-04 receipts, review records with rationale, SPEC-004 write ledger, SPEC-005:109 "A run links task, acting account, model profile, visible user intent, tool receipts, evidence and commits") but no browsable history/timeline requirement or screen. ADR-022 explicitly declines a memory page.
- **Terminology**: existing "Autonomous" already includes human-approved scope and checkpoints, so it is closer to the new "semi-autonomous"; a "fully autonomous" mode (no checkpoints) is not defined and would need grants covering publication classes that docs reserve as separate authorizations (SPEC-005:73 requires "separate explicit authorization every time unless a standing rule names it" for shared default branch).
- Per-mode defaults for grants (which operation classes each mode pre-authorizes) and per-role limits for choosing a mode.

- **Skills/ACP**: `contracts:101`: "Agent Skills... is an instruction packaging format. Its metadata does not grant authority. ACP v1 is optional interoperability... The factory remains functional without it." REQ-042 (S05, AC-042, T-SEC-02): "Use MCP and skills appropriately, consider ACP as optional editor interoperability, and keep the native runtime replaceable." - **Skills in the generated mod** [code fixtures]: Setup writes provider-neutral guidance into the user's mod (`AGENTS.md`, `.agents/skills/...` appear in `crates/setup-adapter/tests/fixtures/import/`; SPEC-001:76-78). That is what external coding clients see; the product runtime itself uses its own native loop.
- **Replaceable runtime**: ADR-011/ADR-003, "keep the provider adapter boundary narrow so a different runtime can still replace it".

**Missing**
- **Product-runtime skills**: no design for loading, installing, scoping or versioning Agent-Skills-style bundles inside the hosted agent (the seven skills in `.claude/skills` are for developing the repo). No trust model for user-supplied skills (text only vs scripts); SPEC-011 forbids user-supplied executables.
- **REQ-042 has no stage packet** (S05 lists W1-W6 with no MCP/skills/ACP work).
- **User-configurable MCP servers** (remote services are allowed by SPEC-011 table L29 "Remote MCP service: External service with declared data flow; per-service auth, approved outbound data and unknown-effect reconciliation") but no UX, storage of per-user MCP endpoints/credentials, or egress policy implementation.

- Model-specific prompt/tool schema conditioning exists only as an intent ("provider adapters may change serialization").

## 4. UI design track (ADR-025, `docs/06-agent-handoffs/GOAL-UI.md`) and how new screens would flow through it

**Decision (ADR-025, `maintainer-decisions:216-220`)**: the S02 client is "functional and temporary". A separate interactive session, run **after S03 and before S04**, builds for each page 3-4 working variants in a development-only design lab (`/design-lab`, only when `import.meta.env.DEV`), with realistic HOI4 fixtures; the maintainer picks; the agent implements, then moves to the next page. Start with an overall visual direction and a shared component set. "Stages keep building working screens... S03 adds only minimal task and API key screens with the existing components. Screens added by S04 and later stages use the design system the track produces, and new or changed pages go through the same preview-and-pick loop. S08 still runs the usability pilot."

**Process** (`docs/07-developer-workflow/skill-workflows/ui-design-iteration/BODY.md`; skill listed in CLAUDE.md as "Agent, for any client page design"): (1) inventory the page with all states and screenshot it; (2) build 3-4 variants in the lab that differ meaningfully; (3) self-check at 375 px and desktop; (4) ask the maintainer with one question, one option per variant, never choose for them, batch independent pages; (5) implement the choice in the real page, keep i18n and API calls, update tests, delete losing variants; (6) run `web/scripts/docker-npm.sh run check`, take after-screenshots, record in `docs/design/DESIGN-DECISIONS.md`, commit; (7) repeat. Needs an API change, new runtime dependency or server change → ask first. Screenshots are design evidence, not usability evidence.

**GOAL-UI sequence**: direction → design system (CSS custom-property tokens for color/spacing/type/radius, light/dark, shared components in `web/src/components/ui.tsx`: buttons, fields, cards, tables, dialogs, notices, empty states, step indicators; shown on a components page in the lab) → pages in default order sign-in, project list, project page, Setup wizard → record in `docs/design/DESIGN-DECISIONS.md`, screenshots under `docs/design/screenshots/`. Rules: all strings in i18n, accessibility (jsx-a11y, contrast, keyboard), behavior unchanged, no new dependency without asking, `run check` green after each page. The inventory in step 3 of GOAL-UI explicitly lists "the task and API key screens S03 added"; `evidence/S03/scope.md`/`GOAL-S03.md` require S03 to update GOAL-UI's inventory.

**State in this checkout**: `docs/design/` does not exist; no `/design-lab` route or code; `ui.tsx` has only six primitives; `styles.css` has no design tokens beyond what exists. The track has not started.

**How the new screens would flow through it**
- *Before the track starts*: every new-area screen that is built in S03 must be minimal and listed in GOAL-UI's inventory. Anything new would be a **design-system input**: the shared components should cover boards/cards (jobs), diff viewer and file tree (Git), Markdown editor/renderer and link graph (notes), step/stepper and popover/spotlight (tours), approval/checkpoint cards and timelines (autonomy), asset grid/image preview (graphics), status chips for evidence kinds (source/static/simulated/observed/stale, SPEC-007:73-83).
- *After the track*: each new page (jobs board, task detail/approval inbox, Git/changes view, notes, onboarding tour surfaces, drift report, asset library) is a separate `ui-design-iteration` run: add fixtures, add variants to the lab on the approved tokens/components, ask, implement, record in `DESIGN-DECISIONS.md`.
- *Constraints every new screen inherits* [code/doc]: English strings in `en.json` with the literal-text lint test; CSP `default-src 'self'; img-src 'self' data: blob:; connect-src 'self'` and "no `style=` attributes" (affects Markdown rendering of remote images, embeds, Monaco/CodeMirror from CDN, tour libraries, charts that inject styles); same-origin `/api/v1` only; no streaming client exists yet (task/event screens need the C-03 cursor/gap protocol, SSE or polling, to be built in S03); sanitize rendered mod content, localization text and model output (`deployment-and-security.md:31`); a11y and keyboard operation (VIS-10); phone width (375 px) check; dark and light themes.
- *Roles in UI*: Viewer/Contributor/Maintainer/Owner differences (read-only notices exist today in `Project.tsx`); public-project read-only view per ADR-021.
- *Unresolved interactions with the track*: the track is "restyle and keep behavior" (GOAL-UI rule: "Do not change API calls, routes or server code unless a design needs a small, reviewed API addition"), so introducing new areas (boards, notes, tours) is feature work, not restyle; they should enter as stage packets (S04+ or a new stage) whose screens then use the loop. Usability evidence only arrives in S08-W5 / T-RELEASE-04 (non-scripter, technical contributor, maintainer, invited collaborator), so tours/onboarding cannot claim usability earlier.
