Date: 2026-10-31. Research only. Nothing was built, installed or run from third-party code. No image was generated and no paid API was called. The `gptimage` MCP server that is connected in this session was not used.

Evidence tags used throughout:
- [V] verified this session from the cited file, command output or vendor page
- [INF] my inference or calculation from verified inputs, stated with its assumptions
- [UNV] unavailable or not verified, with the reason

What I created: a shallow clone at `<projects>\hoi4-factory\.work\ext\gptimage`, and under `<projects>\hoi4-factory\.work\research\`: `measure_assets.py` and `parse_sprites.py` (my own stdlib-only read-only scripts; they read at most 148 bytes of each DDS, 18 bytes of each TGA and the text of `interface/*.gfx`), plus their JSON outputs `_asset_survey_full.json`, `_asset_survey.json`, `_sprite_survey.json`, `_survey_stdout.txt`. ## 1. Summary of findings and recommendations

1. Upstream is small (1,420 lines in 20 files, JavaScript, Node 20+, two dependencies, one commit lineage of 8 commits by one author, 4 stars, no tests, no releases). Only its MCP tool shape, the reference-first workflow text and the auto-versioning idea are worth keeping. Its authentication and generation core is an impersonation of the OpenAI Codex CLI against an undocumented endpoint. Its file saving has no project containment. (Section 2.)
2. The kit already integrates gptimage as a verbatim vendored copy (one line differs) and makes it the default image provider in the provider catalog. It also already ships a hardened Python stdio MCP (`.tools/image_generation/runtime/server.py`, 1,800 lines) with about 20 provider routes, project-contained saves and a no-overwrite rule. What the kit lacks is a HOI4-aware layer: category profiles, preprocessing, DDS and sprite registration in one pipeline, batch validation and a machine-readable provenance ledger. That layer is the real value of the new MCP; the provider adapters are the commodity part. (Section 3.)
3. Measured HOI4 1.19.3.0 asset facts: 95.8% of 15,126 surveyed DDS files are uncompressed A8R8G8B8 and 93.0% have one mip level. The kit's DDS contract (one-level uncompressed BGRA) is confirmed. Several kit canvas conventions are not vanilla: focus icons are 100x88 in 94.1% of `focus_*` files (kit convention 94x86), decision icons 33x32 (kit 32x32), idea pictures 65x67 or 60x68 (kit 64x64). The kit's `.tools/gfx/profiles.json` confirms category icons, report, news and counters; it has no row yet for focus, decision, idea, technology, MIO, agency, portraits or super events. (Section 4.)
4. Providers (checked in vendor docs on 2026-10-31): `gpt-image-2.5-sunburst` and `gpt-image-2.5-flare` are the current OpenAI models; `gpt-image-1` was shut down on 2026-10-23; Imagen is shut down in the Gemini API and discontinued on Vertex (2026-06-30); `gemini-2.5-flash-image` shuts down 2027-03-15. Native alpha is documented only for OpenAI GPT Image (GA on 2.5, preview on `gpt-image-2`). Everything else needs a background-removal route. (Section 5.)
5. Language: build in Rust. The core as a library crate that Factory links directly (no subprocess, which suits SPEC-011's "audited built-in adapter" rule), plus a thin rmcp stdio binary for the kit. Fork-then-rewrite keeps upstream's history and MIT notices. (Section 7.1.)
6. Reuse `.tools/gfx/profiles.json` as the owner of canvas, accepted sizes, margin, frames and evidence. Add an optional `imagegen` sub-object per row for the extra export and naming fields. `gfx.py` reads only `canvas`, `margin` and `accepted`, so extra keys are safe. (Section 7.3.)
7. Cost exposure: with a $1 monthly allowance, one finished asset (5 provider calls at about 1 megapixel) costs about $0.015 to $1.06 depending on provider and quality tier. Medium-quality OpenAI and Gemini Pro-class tiers would consume the whole allowance on 1 to 4 assets. Recommendation: operator-funded image calls limited to a cheap-tier allowlist, expensive tiers bring-your-own-key only. (Section 6.)

Open questions for the maintainer are in section 9.

### 2.2 MCP server (src/server.js)

- Transport: stdio only (`StdioServerTransport`). Server name `gptimage`, version `0.1.0`. [V]
- Tools [V]:
  - `generate_image` with zod schema: `prompt` (string, required), `out` (string, required; "relative to the project directory unless absolute; an existing file is auto-versioned"), `quality` (`low|medium|high|auto`, default high), `size` (free string, "auto or WIDTHxHEIGHT, multiples of 16, max edge 3840, ratio <= 3:1"; description only, not enforced in code), `reference_images` (array of paths). One image per call. Returns text "Image saved to <abs path>" plus notes (versioned, or a nudge to use `references/`).
  - `list_references`: lists image files directly under `<project>/references/` (creates the folder on demand).
  - `image_auth_status`: reports the credential store in use, the plan type and the account id decoded from the token.
- Project root: `GPTIMAGE_PROJECT_DIR` or `process.cwd()`; relative `out` and reference paths resolve against it.
- Errors are returned as `isError` text results, not exceptions.
- CLI (`src/gen.js`): `--prompt/-p --out/-o --ref (repeatable) --quality --size`; `login.js` offers `--status` and `--logout`.

### 2.3 Image handling and file safety (src/images.js) [V]

- Reference images are read from any path (absolute or relative), the MIME type is taken from magic bytes (PNG, JPEG, WebP, GIF) and falls back to the file extension. A file named `x.png` with other content is therefore still sent. No size limit and no count limit exist in code.
- References are sent as base64 data URLs inside the request body.
- Saving: `savePng` resolves `out` (absolute allowed), `mkdir -p`, then `pickNonOverwritePath` tries `name`, `name-v2`, `name-v3`, ... up to 999 using an `access()` existence check, then `writeFile` without an exclusive-create flag. There is no project containment (any absolute path, any extension, `..` accepted), no symlink handling, and a check-then-write race (two concurrent writers can pick the same name). The saved bytes are always treated as PNG, whatever the extension.
- Overwrite protection: the auto-version idea is good and is what the kit's test `scripts/test_gptimage_reference_upgrade.py` exercises (`out.png` then `out-v2.png`). Its implementation is not safe enough to reuse as is.

### 2.4 Authentication and the unofficial backend (exactly how it works)

All of this is in `src/auth.js`, `src/login.js`, `src/codex.js` [V].

1. Login (`login.js`): an OAuth 2.0 authorization-code flow with PKCE (S256) against `https://auth.openai.com/oauth/authorize`, using the fixed public client id `app_EMoamEEZ73f0CkXaXp7hrann`, redirect URI `http://localhost:1455/auth/callback`, scope `openid profile email offline_access`, and extra query parameters `id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, `originator=codex_cli_rs`. These are the parameters the official Codex CLI uses; the tool presents itself as the Codex CLI. A loopback HTTP server on 127.0.0.1:1455 receives the code (state is checked), then the code is exchanged at `https://auth.openai.com/oauth/token`.
2. Token storage: the access token, refresh token, account id (decoded from the access-token JWT claim `https://api.openai.com/auth.chatgpt_account_id`), and expiry are written to `~/.gptimage/auth.json` (mode 0600; on Windows the mode has no effect). Resolution order at call time: `GPTIMAGE_ACCESS_TOKEN` env, then `~/.gptimage/auth.json`, then the Codex CLI's `~/.codex/auth.json`. When a token is within 60 s of expiry it is refreshed (`grant_type=refresh_token`, same client id) and the rotated tokens are written back to whichever file they came from, including the Codex CLI's file. Writing into another tool's credential file, and rotating its refresh token, is a risk of its own [INF].
3. Generation (`codex.js`): `POST https://chatgpt.com/backend-api/codex/responses` with headers `Authorization: Bearer <subscription access token>`, `chatgpt-account-id`, `originator: codex_cli_rs`, `Accept: text/event-stream`. Body: `model` default `gpt-5.5` (override `GPTIMAGE_MODEL`), a fixed instruction "always satisfy the request by invoking the image_generation tool exactly once", the user prompt plus each reference as an `input_image` data URL, `tools: [{type: "image_generation", output_format: "png", quality, size?}]`, `tool_choice: image_generation`, `stream: true`, `store: false`. The SSE stream is parsed for `response.output_item.done` with an `image_generation_call` item whose `result` is base64 PNG. This is the Responses-style protocol of the ChatGPT Codex backend, not the public Images API. Which image model actually runs is not stated by the route (the kit's own docs say the same).
4. Billing and limits: the ChatGPT plan's allowance. 401 and 429 are mapped to messages. There is no cost or usage reporting.
5. The upstream README and skill state it themselves: "Grey area, by design ... not an officially sanctioned API ... Heavy use can trigger plan rate-limits (429) or, worst case, account restrictions" [V README]. OpenAI's own Codex auth page (https://learn.chatgpt.com/docs/auth, accessed 2026-10-31) says to "treat ~/.codex/auth.json like a password" and, for general OpenAI API calls, to "continue to use Platform API keys" [V]. A secondary source reports that OpenAI's Terms of Use prohibit automatic or programmatic extraction of Output except as permitted through the API; I could not fetch the primary text (HTTP 403), so the exact current wording is [UNV] and must be checked before the plugin documentation quotes it.

What must be removed from the default product (and isolated per decision 3): `auth.js`, `login.js`, `codex.js`, the `~/.codex` fallback and write-back, `GPTIMAGE_ACCESS_TOKEN`, `GPTIMAGE_ORIGINATOR`, the `chatgpt-account-id`/`codex_cli_rs` header impersonation, the `gpt-5.5` forced-tool request, `image_auth_status` as implemented, the "Pinterest/Dribbble sourcing" advice in the skill, and every doc sentence saying "no API key, no per-image bill".

### 3.2 The existing Python provider runtime (do not duplicate) [V `.tools/image_generation/runtime/server.py`]

- Stdio MCP (protocol version `2025-11-25`) started per provider as `server.py --provider <id> --project-root .`. Reads the project's `.hoi4-setup/image_generation.json` (written by Mod Setup), checks it against the trusted `provider_catalog.json`, refuses symlinked settings, and takes API keys from the OS credential store using references `credential://image_generation_api_key/<provider>_<field>` (Windows Generic Credential target `<reference>.com.klimpaskov.hoi4-mod-setup`, macOS `security` keychain, Linux `secret-tool`).
- Tools: `generate_image`, `edit_image`, `remove_background`, `image_auth_status` with schemas derived from per-model capability profiles.
- Routes: the catalog has 24 entries, 20 of them `stdio_adapter` routes served by this runtime: openai_api, gemini_api, fal_ai, replicate, black_forest_labs, stability_ai, ideogram, recraft, leonardo, adobe_firefly, xai_grok, together_ai, openrouter, comfyui_local, automatic1111_local, forge_local, vertex_imagen, microsoft_foundry, aws_bedrock, huggingface_inference. The other four are gptimage (Node `local_package`), codex_native (client built-in), and the manual routes midjourney_manual and none. Default models include `gpt-image-2.5-sunburst` for OpenAI and `gemini-nano-banana-2.1` for Gemini, which match the vendor docs I checked.
- Safety properties already solved there and worth keeping: project-relative paths only, `..` and symlinks rejected, reference files validated as real PNG/JPEG/WebP, caps (message 8 MiB, image 32 MiB, reference 24 MiB each and 64 MiB total, prompt 12,000 chars), per-provider host allowlists for API and image download hosts (https, port 443, no redirects, no private addresses), no overwrite ("The output file already exists"), temp file plus fsync plus rename, alpha and transparent-pixel detection on the saved PNG, secrets redacted from errors.
- Gaps relevant to HOI4: no notion of asset category, canvas, DDS, sprite, validation beyond PNG alpha, preprocessing, lineage or approval. Its ComfyUI route builds a fixed checkpoint text-to-image or img2img graph (`CheckpointLoaderSimple`, `KSampler` 24 steps, `SaveImage`, `POST /prompt` with `client_id`, poll `/history/<id>`, fetch `/view`), which cannot run the maintainer's FLUX.2 Klein portrait workflows. The model/size profile data (`model_profiles`) is a hand-reviewed catalog; it already contains stale choices relative to my checks (section 5.2).

### 3.5 What not to duplicate

## 4. HOI4 asset specifications measured from the installed game

Game: Hearts of Iron IV `rawVersion` 1.19.3.0, version string "Operation Postern v1.19.3.0.c01a (5632)" (`launcher-settings.json`), folder `C:\Program Files (x86)\Steam\steamapps\common\Hearts of Iron IV` [V]. Method: `measure_assets.py` reads the DDS header (128 bytes plus the 20-byte DX10 extension when present) and the 18-byte TGA header only; `parse_sprites.py` parses `interface/**/*.gfx` text. Pixel contents were not read, so "alpha" below means header-level capability (an alpha channel is declared), not proof that the pixels use it. For pixel-level alpha behaviour I cite the kit's own calibration (`.tools/gfx/README.md`: on the same game, the opaque-canvas and empty-subject rules matched 0 of 4,440 focus, decision and idea textures; ghosted focus icons 5.5%; chroma fringe 4-7%) as [V in kit docs, not re-run by me].

### 4.1 Overall DDS contract [V]

- 15,126 DDS files surveyed across 29 icon, portrait, event and GUI folders: 14,485 (95.8%) are uncompressed 32-bit with masks R=00FF0000 G=0000FF00 B=000000FF A=FF000000 (D3DFMT A8R8G8B8, legacy 128-byte header, no DX10 header); 14,072 (93.0%) have a single mip level.
- Other formats: X1R5G5B5 with 8 mips 444 (all older leader portraits), DXT5 123, DXT1 35, DXT3 10, RGB24 20, DX10-header files 8 (all B8G8R8A8_UNORM_SRGB or R8G8B8A8_UNORM_SRGB), RXGB 1. No BC7 and no BC4/BC5 occur.
- So the kit's `convert_to_dds.py` contract (texconv BGRA, 1 mip; `write_bgra_dds`: 128-byte header, `RGB|ALPHAPIXELS`, straight alpha, `DDSCAPS_TEXTURE`, file length `128 + w*h*4`) matches the dominant vanilla format. An in-process Rust writer can produce byte-identical output without texconv [INF; verify with a golden test against `write_bgra_dds`].
- Flags are TGA, not DDS (4.3).

### 4.3 How sprites are declared, frames and shine [V]

- Plain icon: `spriteType = { name = "GFX_x"  texturefile = "gfx/....dds" }`. `SpriteType` and `spriteType` both occur (case-insensitive). Optional keys seen: `noOfFrames`, `effectFile`, `legacy_lazy_load`, `alwaysTransparent`, `generate_mip_maps`, `masking_texture`, `animation = { ... }`.
- Frames: a horizontal strip whose width is `noOfFrames` times the frame width. Examples: 21-frame decision category UI strips; 2-frame agency logos and counters; 18-frame `idea_traits_strip`; medals up to 7 frames. `gfx.py sprites` already warns when the width does not divide by `noOfFrames` (vanilla has 79 uneven strips of 1,798, per the kit README).
- Focus shine: every focus icon has a second sprite named `<icon sprite>_shine` in `interface/goals_shine.gfx` (3,122 shine sprites against 3,131 goal sprites). Pattern: same `texturefile` as the icon, `effectFile = "gfx/FX/buttonstate.lua"`, two `animation` blocks with `animationmaskfile` = the icon texture, `animationtexturefile = "gfx/interface/goals/shine_overlay.dds"`, `animationrotation = -90.0` and `90.0`, `animationlooping = no`, `animationtime = 0.75`, `animationdelay = 0`, `animationblendmode = "add"`, `animationtype = "scrolling"`, `animationtexturescale = { x = 1.0 y = 1.0 }`, `legacy_lazy_load = no`. The kit's skills do not mention the shine sprite at all (search for "shine" in all skills and references found nothing). Whether a mod focus without a shine sprite logs an error was not tested [UNV]. The sprite registration step should generate the shine sprite from this template and mark it "pattern observed in vanilla, game behaviour untested".
- Implicit lookups: idea `picture`, focus `icon`, decision `icon`, achievements and flags resolve by name or file without explicit sprite for flags and achievements; the kit's `gfx.py families` already follows focus, decision and idea consumers through the registry.

### 5.3 Recommendation for first targets

Phase 1: `openai` (Images API; also covers Azure OpenAI by `base_url` and auth-style variants), `gemini` (Gemini API image models), `comfyui` (workflow-template runner), plus `fal` as the recommended other hosted API: one key reaches FLUX.2 Pro and its edit endpoint, Nano Banana, and several transparent-output and Ideogram/Recraft endpoints; it has an asynchronous queue with request ids, which makes lost-response reconciliation possible; prices are explicit per megapixel or per image.
Phase 2: `stability` (cheap deterministic Remove Background and inpaint/erase at 5 credits, fills the transparency gap for providers without native alpha), `bfl` (direct FLUX.2 with up to 8 references), `azure-openai` (same wire format as `openai`).
Not first: Replicate (overlaps with fal; 1-hour output deletion), the kit-runtime-bridge long tail (optional, kit mode only).
Reason for fal over BFL in phase 1 [INF]: BFL's pricing and limits were not readable in the docs I could fetch, so budget reservation could not be implemented from verified data today.

Constraint for hosted Factory [V in SPEC-011/SPEC-002]: provider requests are outbound data operations with per-project destination policy; a task restricted to one provider cannot fail over silently (EXT-09); custom endpoint URLs (the ComfyUI endpoint) pass the outbound check that blocks private, loopback, link-local and metadata addresses, so on the hosted service a ComfyUI endpoint must be a public HTTPS URL the user supplies.

Reading the exposure [INF]:
- With a $1 allowance, a medium-quality OpenAI or a Pro-class Gemini tier gives 1.5 to 4 assets per user per month. The cheap tiers (`gpt-image-2` low, Gemini 2.1 / Lite, flux-2, schnell) give 6 to 66.
- Quality is not linear with price for tiny targets: a 100x88 focus icon is a downscale of the generated image, so low or medium tiers plus careful references may be enough. This is a hypothesis to test in the first recorded runs, not a finding.
- Recommended policy: operator-funded image calls are limited to an allowlist of cheap-tier models (candidates: `gemini-nano-banana-2.1` at 1K, `gpt-image-2` low or medium, `fal-ai/flux-2`), with a default per-task cap (suggest $0.25) and per-user monthly image sub-limit inside the same $1; expensive tiers, high-resolution tiers and bulk batches require the user's own key. Both the per-task and the per-user limits apply whoever pays (SPEC-002 section on budgets).
- Budget mechanics for image calls: price-per-image providers have deterministic cost, so reserve exactly; token-priced providers (OpenAI 2.5, Gemini token tables) reserve an upper bound from a dated price table, then settle from the response `usage` fields (OpenAI returns `usage.input_tokens`, `output_tokens`, with image/text details [V]); missing usage becomes `usage_unknown` with the reserve held, never zero (existing Factory rule, `crates/agent/src/cost.rs`).
- A lost response on a synchronous API (OpenAI Images API, Gemini generate) cannot be reconciled by job id; treat as an uncertain charge and require an explicit user decision before resubmitting. Asynchronous providers (BFL `polling_url`, fal queue request ids, Replicate prediction ids, ComfyUI `prompt_id`) can be reconciled by reading the job. Whether the OpenAI Responses API offers a background-retrieval mode that would allow reconciliation was not checked [UNV].

### 7.2 Core design

Environment abstraction (the same code runs in the kit and in Factory): `ProjectFs` (rooted at the mod, containment enforced), `GameRef` (installed game folder in the kit; Factory's read-only mount, headers and decoded pixels used for preview and calibration only, never copied out), `Credentials` (OS keyring using Mod Setup's exact references; environment variables; or a Factory-supplied handle resolved by the host), `Egress` (HTTP client with per-provider host allowlists, https/443 only, no redirects off the allowlist, private-address block; Factory injects its outbound policy), `Spend` (reserve, settle, refuse), `Clock`.

Provider trait (outline):

```rust
#[async_trait]
pub trait ImageProvider: Send + Sync {
    fn descriptor(&self) -> &ProviderDescriptor;          // id, reviewed model table with retrieved-date, limits, cost model
    async fn estimate(&self, r: &Request) -> Result<CostEstimate, ProviderError>;     // exact or upper bound, no network
    async fn generate(&self, r: GenerateRequest, c: &CallContext) -> Result<ProviderOutput, ProviderError>;
    async fn edit(&self, r: EditRequest, c: &CallContext) -> Result<ProviderOutput, ProviderError>; // refs, optional mask
    async fn remove_background(&self, r: BgRequest, c: &CallContext) -> Result<ProviderOutput, ProviderError>; // optional
    async fn reconcile(&self, job: &JobRef) -> Result<Reconciled, ProviderError>;     // async providers; sync ones return Unknown
}
// Capabilities in the descriptor, per model: max_refs, mask, native_alpha (ga|preview|none), sizes (arbitrary{mult,min_px,max_px,ratio}|fixed|tiers),
// formats, async, cost_model (per_image|per_megapixel|tokens|gpu_time|plan_quota), moderation, terms_ref, doc_url, retrieved.
```

Rules: the pipeline selects a provider and model from the descriptor, never from a prompt string; unsupported options fail before any request; one asset per call; no silent fallback to another provider (Factory EXT-09 and the kit's "never silently switch providers"); `n` is always 1 even where the API allows 10.

Pipeline for one asset (every step writes a ledger entry and an immutable artifact addressed by SHA-256):
1. Resolve category and profile (7.3), effective canvas, generation size (smallest allowed size with the profile's aspect, then downscale), alpha policy, export container.
2. Collect and preprocess references: project-owned approved style references, optional installed-game or kit-shelf references (policy-gated, see risk R4), user attachments, previous candidates. Decode and re-encode to clean PNG (strips metadata and ancillary chunks), enforce pixel and byte caps, number the references by role (style anchor, subject anchor, geometry anchor, edit target) as the kit's `generation-and-review.md` requires.
3. Plan: deterministic prompt assembly from the profile template plus the brief plus the project style profile; return a `plan_id` (hash) with estimate, provider/model, output paths, approvals needed. No spend yet.
4. Reserve budget, check grant (Factory) or confirmation (kit), call the provider, store the raw output unchanged as `candidate vN`.
5. Transparency: if the profile requires alpha, use native alpha when the model documents it (OpenAI 2.5), otherwise a provider remover (Stability) or a ComfyUI matte workflow, then deterministic defringe and alpha checks. Never accept a prompt-only claim; the saved pixels must prove it (existing kit rule).
6. Deterministic processing: crop or cover-fit to the exact aspect, resize with Lanczos3 in premultiplied alpha, composition steps owned by the category (frame strip assembly, news black and white, report card via the existing tool, shine companion). Resizing is a step, never a verdict.
7. Deterministic validation (7.7), producing findings with stable codes.
8. Preview artifacts: native size, 4x nearest-neighbour, dark, light and checker backgrounds, contact sheet with the approved style references beside the candidate.
9. Visual review record (human or agent with image viewing) against the profile's rubric: composition, silhouette readability at native size, style match to the approved references, era fit, no text, no unintended elements. Stored separately from the deterministic results.
10. Approval checkpoint (policy: user, agent, or auto for drafts). Install requires: validation pass, review approved, candidate hash unchanged, plan hash unchanged.
11. Install: export DDS or TGA to the final path, write the provenance record, then either write `gfx_handoff.md` with the ready sprite snippet (kit default, matches the rule that asset workers do not edit `.gfx`) or register the sprite (explicit scope; through the shared Rust HOI4 engine, or as a C-02 proposal operation in Factory).

Naming, placement, versions (kit conventions reused, not reinvented): working files under `docs/assets/<feature_slug>/` with `source_png/`, `processed_png/`, `contact_sheets/`, `prompts/`, `manifest.md`, `gfx_handoff.md` (skill section 7), plus `imagegen/records/<asset_id>.json`; final files in the feature-scoped category folder (skill section 2.2); lowercase snake_case, category prefixes from the profile. Candidates are `v1`, `v2`, ... created with exclusive-create plus temp file, fsync and rename (and the exclusive hard-link technique `gfx.py` already uses); a collision never overwrites. A final runtime path that already exists is a conflict unless the ledger shows this asset owns it and the user approved `replace`, in which case the previous hash is recorded. Sprite names stay stable.

Provenance record (one JSON per asset, rendered into `manifest.md` rows): schema version; asset id and category; profile source (path, sha256, row); request (prompt text and hash, style profile id and hash, provider id, exact model id, parameters, seed when supported, idempotency key, request hash); references (path or artifact id, sha256, role, origin: project, user upload, kit shelf, installed game, previous candidate); response (provider request id, raw output sha256, usage); cost (estimated, reserved, actual, `usage_unknown` flag, funding source); lineage (parent candidate); processing steps (operation, parameters, input and output sha256, tool and crate version); validation findings; review (reviewer, verdict, rubric id, notes); approval (who, grant or policy id, time); install (final path, DDS sha256, decoded `pixels_sha256`, sprite name, `.gfx` file, replaced hash); rights (source mode "generated", provider terms reference, watermark note such as Gemini SynthID). This aligns with SPEC-010's provenance fields and with the kit's `pixels_sha256` convention used for report cards.

### 7.3 Profiles: reuse `.tools/gfx/profiles.json`, add an `imagegen` sub-object

Facts [V]: `gfx.py` loads only `canvas`, `margin` and `accepted` from each row (lines 34-38, 209-214) and tolerates other keys; row names double as `--profile` choices; the file already carries `frames` and `source` for human evidence; the README says focus, decision and idea rows are project decisions that the source package intentionally leaves out.

Proposal: `profiles.json` remains the single owner of geometry and evidence (canvas, accepted sizes, margin, frames, source). Each row may carry an optional `imagegen` object that `gfx.py` ignores, holding what the generator needs: `category` id, `automation` (`generate` | `import_only` | `user_run_only`), generation aspect and background, export (container, format, mips), placement folder and name pattern, sprite template (including companions such as `shine`), required checks, reference folders and the rubric id. Example for the focus row (values are proposals; the canvas needs a maintainer decision):

```json
"focus": {
  "canvas": [100, 88], "accepted": [[100,88],[102,90],[99,88],[98,88]], "margin": 2, "frames": 1,
  "source": "Project decision <date>. 2,681 of 2,849 vanilla focus_* DDS are 100x88 (header survey, HOI4 1.19.3.0).",
  "imagegen": {
    "category": "focus_icon", "automation": "generate",
    "generation": {"aspect": "100:88", "background": "transparent"},
    "export": {"container": "dds", "format": "a8r8g8b8", "mips": 1},
    "placement": {"folder": "gfx/interface/goals/{feature_slug}/", "prefix": "goal_"},
    "sprite": {"gfx_file": "interface/{feature_slug}_goals.gfx", "name": "GFX_{prefix}{asset}", "companions": ["shine"]},
    "checks": ["size", "alpha", "fringe", "opaque_canvas", "fill"],
    "reference_dirs": ["icons/national_focus"], "rubric": "focus_icon_v1"
  }
}
```

Two helper commands keep the numbers honest: `hoi4-imagegen calibrate` reads DDS/TGA headers and `.gfx` text from the installed game (kit) or the read-only mount (Factory), compares them with every profile row and prints a proposed diff with counts (the same method as `measure_assets.py`), and never writes silently; `hoi4-imagegen profiles` lists rows with their evidence and flags any row whose canvas is not the dominant vanilla size. Rows for the categories in section 4 that the kit lacks are produced as proposals from that calibration. Category ids: `focus_icon`, `idea_icon`, `decision_icon`, `decision_category_icon`, `decision_category_picture`, `tech_icon_small`, `tech_icon_medium`, `event_report`, `event_news`, `event_super`, `flag_set` (three TGA sizes), `mio_icon`, `agency_logo`, `officer_spirit`, `leader_portrait` (156x210), `gui_texture` (profile-less, size from the consumer), `custom`. Categories that other tools own are `import_only` or `user_run_only`: advisor 65x67 (`create_advisor_icon.py`), achievement triplets (`process_achievement_icons.py`), grounded portraits (user-run ComfyUI workflow), counters (need the exact vanilla reference), animation (real per-frame art, `hoi4-frame-animation`), 3D.

Project style profiles: `.hoi4-imagegen/styles/<name>.json` (project-owned, committed): reference images pinned by SHA-256, prompt fragments, negative rules, palette notes, applicable categories, preferred provider and model, seed policy, approver and date. A style profile is data with no authority, like a Factory memory item.

### 7.4 The opt-in ChatGPT-login plugin (decision 3)

Goal: the upstream backend remains usable for a single person on their own machine, with zero reach into hosted Factory and zero coupling to the asset logic.

- Separate crate `provider-chatgpt-login` containing the Rust port of `auth.js`, `login.js` and `codex.js` under the original MIT notice with a header naming the upstream file and SHA. It implements only `ImageProvider`; core and the other provider crates have no dependency on it and no mention of its endpoints.
- Not in `default-members`, not in the default feature set, not in release artifacts of the default build. Enabling it needs all of: building `imagegen-mcp` with `--features unofficial-chatgpt-login`; `[providers.chatgpt_login] enabled = true` in `.hoi4-imagegen/config.toml`; environment variable `HOI4_IMAGEGEN_ACCEPT_UNOFFICIAL=1` at start-up (so a project file alone cannot switch it on); and `--mode local-stdio` (the plugin refuses `--mode hosted`, any HTTP listener, and any process that has the Factory broker profile).
- Behaviour changes from upstream: its own credential file only (user data directory, 0600 on Unix and a user-only ACL on Windows); it never reads or writes `~/.codex/auth.json` (no cross-tool refresh-token rotation); no `GPTIMAGE_ACCESS_TOKEN`; `originator`, model slug and client id are configuration constants in one place with a loud doc comment; capability descriptor says: references yes, mask no, native alpha no (proven pixels only), cost model `plan_quota` so budgets record `usage_unknown` and never charge the operator allowance.
- Isolation checks that run in CI: `cargo tree -e normal -p imagegen-core -p imagegen-providers -p imagegen-mcp` (default features) must not list the plugin crate; a test greps the default-build binary for the strings `chatgpt.com`, `auth.openai.com`, `codex_cli_rs`; Factory's own dependency on the library uses `default-features = false` with an explicit allow-list of provider features, and Factory CI repeats the `cargo tree` and string checks on the server binary (new EXT test, see section 8).
- Documentation shipped with the plugin (`docs/unofficial-chatgpt-login.md`): how it works (section 2.4), that it impersonates the Codex CLI, that the endpoint is undocumented and can change or be blocked without notice, that the model slug is not a stable image model, upstream's own warning about rate limits and account restrictions, OpenAI's guidance to use Platform API keys for general API calls and to treat `auth.json` like a password, the unverified Terms-of-Use question (open item), that it is for the user's own account and personal use, not for sharing tokens, not for servers, and that the maintainers do not support the account consequences.
- Distribution (open question 6): source-only build is the cleanest way to keep the official binary free of it; a separately named prebuilt artifact is possible later.
- The kit's vendored Node copy can stay until the plugin replaces it; afterwards remove `.tools/image_generation/providers/gptimage/` and the `gptimage` default in the catalog.

### 7.6 Deterministic validation versus visual review

Deterministic (Rust, reproducible, finding codes reused from `gfx.py` where the rule is the same): exact dimensions against `accepted`; per-frame alpha statistics, empty subject, ghosting (mean alpha), margins at alpha >= 16, subject span >= 80% for icon families, opaque-canvas corners, chroma fringe (magenta/green key colours), halo and fake-checkerboard detection (periodic grey/white pattern in opaque pixels), DDS header exactness (128-byte header, masks, no mips, length `128+w*h*4`), flag TGA origin, frame strip divisibility, name collision and containment, sprite resolves, provenance present, LFS pointer and truncation. Advisory heuristics: palette and luminance distance to the approved references, native-size edge energy, perceptual-hash near-duplicate of a vanilla or existing asset (guards against copying), optional OCR for stray text. Visual review (human or agent, recorded separately): subject readability and silhouette at native size, style match against the approved references side by side, period fit, no text or watermark artefacts, composition and centring, forbidden additions. A resize that passes the size check is never reported as "suitable"; the report separates `deterministic: pass` from `visual: pending|approved|rejected`.

Image-QA code scope [INF, open question 13]: port only what Factory needs without Python or texconv (BGRA DDS writer, TGA writer, resize, alpha stats, size/margin, defringe, fringe check, checker detection, header validators), expose the check ids, and prove parity with `gfx.py` and `convert_to_dds.py` on a synthetic corpus. Do not port report-card, advisor, achievement or portrait tools in phase 1; in kit mode the MCP can call them when present.

### 7.7 Kit integration

- Install procedure (end user): select "HOI4 image generation" in HOI4 Mod Setup; Setup fetches the pinned binary, verifies SHA-256 and size from the manifest, registers the MCP for the chosen clients, and asks for the provider key through the existing credential UI (OS vault, references `credential://image_generation_api_key/<provider>_<field>`). The new server reads the same `.hoi4-setup/image_generation.json` selection and the same vault entries as the Python runtime, so Setup needs no new secret handling. Manual install: download the release for the platform, verify the published SHA-256, put it on PATH, then `hoi4-imagegen doctor` (providers, key presence, game folder, profile hash, calibration summary).
- Distribution choices (open question 5): (A) npm platform packages carrying the Rust binary, installed by the kit's existing SHA-512-pinned npm bootstrap (`.tools/mcp/bootstrap_*.py`), which already handles Windows and Linux; (B) GitHub Release binaries consumed by a new "release binary" component kind in Mod Setup, which also covers macOS. (A) needs no Setup code change; (B) is cleaner long term.
- Client configuration (all with empty `env`, no secrets): `.mcp.json` `hoi4_imagegen` stdio entry with `--project-root .`; `.cursor/mcp.json`, `.qoder/mcp.json` the same shape; `.opencode/mcp.json` with the `command` array form; `.codex/config.toml` a `[mcp_servers.hoi4_imagegen]` table with the same timeouts as `hoi4_agent_tools` (startup 120 s, tool timeout 600 s). Manifest components (names are proposals): `mcp.hoi4_imagegen` (category `mcp`, platforms windows/macos/linux, expected files with sha256 and size, health check `initialize` and tool list), `runtime.<client>.imagegen_mcp` merged-config entries (three-way merge like `runtime.claude.mcp`), `workflow.imagegen` (skill, references, examples), `docs.imagegen`. The `HOI4_MOD_SETUP:IMAGE_GENERATION_PROVIDER` marker text in the three agents and the two asset-skill files is filled with a short description of this route and the selected provider.
- Skill `hoi4-imagegen` (under 8 KB with `references/` for category details and recipes, text only, evidence-tagged rules, per P8/P9): when to call, the plan-generate-validate-review-install loop, reference roles, one asset per call, never trust prompt-only transparency, what the MCP will refuse, where each tool's output lands. ### 7.8 HOI4 Factory integration

Stage reality [V]: S01 and S02 are done; S03 (native agent and durability, which brings the tool broker) is not started; SPEC-010 schedules generation workflows for S06 and a minimal asset package in S04. This section is a design to keep that future cheap, not a request to start anything. `crates/agent` today holds only provider adapters and cost estimation; broker, grants and budgets are specified (C-04, C-08, SPEC-002, SPEC-011) but not implemented.

- Form: Factory links `imagegen-core` and `imagegen-providers` (git dependency pinned by revision like the Setup pin, `default-features = false`, explicit provider features) as an audited built-in adapter. No MCP subprocess and no user-supplied executables (SPEC-011). The stdio binary exists for the kit and for development.
- Broker tool profile "assets": `asset.plan` (read), `asset.generate` and `asset.edit` (external paid effect), `asset.process`, `asset.validate`, `asset.preview`, `asset.review`, `asset.propose_install` (produces a C-02 ChangeProposal with binary-replacement and `.gfx` source-span operations; the host applies it, the tool never writes the workspace directly), `asset.ledger`. Provider calls run in the host process behind the egress policy; decoding and processing of untrusted provider bytes run in the per-task gVisor container with size, pixel and time limits.
- Grants (C-08): a new operation class `generate_image` bound to workspace or run scope, a provider and model allow-list, a cost ceiling and an expiry; `edit` of an existing candidate is the same class; install is a proposal grant like any other file change. A standing grant allows repeated generations within its ceiling without re-prompting. Fallback between providers or funding sources needs an explicit policy.
- Funding and budgets (SPEC-002): a profile per provider with funding source `user_key` or `operator_allowance`; the user's key is stored encrypted, never returned to the browser, never used for another account. Reserve before the call (exact for per-image providers, upper bound from the dated price table for token-priced ones), settle from the response, `usage_unknown` keeps the reserve. Limits: per task, per project, per user per month, plus an image sub-limit inside the $1 allowance; allowance-funded calls restricted to the cheap-tier allowlist (section 6). Operator-held image keys count against operator budget and rate limits like model keys; abuse limits apply per account, project and source address.
- Reconciliation (C-04, SPEC-010 test "generation disconnect after submission"): write the intent (final normalized arguments, idempotency key, price table version) before the call; asynchronous providers are reconciled by job id before any retry; synchronous ones record an uncertain outcome and ask the user. Pass the OpenAI `safety_identifier` as a hash of the account id so one user's abuse cannot flag the whole key.
- Artifact store: candidates, processed files, previews and the ledger JSON live as tenant- and project-scoped artifacts with SHA-256 keys; a changed hash after approval invalidates the approval and previews (SPEC-010 "approved variant replaced"). Game-reference material is mounted read-only and is never written to artifacts or sent to a provider by default.
- Approval checkpoint: the visual-review step maps to Factory's per-project checkpoint policy (A2: auto, ask or notify per checkpoint, switchable mid-job without widening grants). Default for a new style profile: ask. The UI shows candidate, previews, validation findings, cost so far and the exact install diff.
- Provider destinations and ComfyUI: per-project destination policy; ComfyUI endpoints are user-supplied public HTTPS URLs that pass the outbound check; Factory never starts or stops RunPod pods. The FLUX.2 Klein 9B non-commercial weights must not be offered by any Factory-operated endpoint.
- Plugin: never compiled into Factory; CI asserts it (section 7.4).

## 8. End-to-end test plan

Principles from the Factory CLAUDE.md: never fabricate model output or results; live calls use real providers; faults a live API cannot produce on demand are injected into recorded real responses and labelled recorded-real replay; anything that could not run is marked unavailable with the reason; test normal, failure and recovery paths; run platform-sensitive code on both machines and in Linux (`scripts/linux-tests.sh`); keep fixtures in short paths under the worktree or `.work/`.

| Layer | Tests | Evidence kind |
|---|---|---|
| L0 unit (`imagegen-core`) | profile parsing and unknown-key tolerance with the real `profiles.json`; category resolution; name and placement patterns; version allocation under concurrent writers (exclusive create, no lost writes); containment (`..`, absolute, symlink, Windows junction, UNC, 8.3 short names, case folding); reference validation (magic bytes, caps, decompression bomb, wrong extension, SVG rejected); prompt-plan snapshots; ledger round-trip and hash chain; cost reservation and settlement incl. `usage_unknown` | source parsing |
| L0 parity | Rust DDS writer vs `convert_to_dds.py write_bgra_dds` byte-for-byte on a synthetic corpus; header field-by-field comparison with vanilla header samples (read-only, headers only); TGA writer origin bit vs the 5 / 221 / 3 vanilla top-origin counts; alpha stats, size/margin, defringe and fringe findings equal to `gfx.py` on the same synthetic images; Pillow decode round-trip of Rust-written DDS (dev-only Python) | source parsing and binary comparison |
| L1 provider contract | for each provider and capability (generate, edit with refs, edit with mask, native alpha, async job, 400, 401, 429, moderation block, malformed body, truncated image, oversized image, redirect to a non-allowlisted host): one real recording per path, stored hash-addressed with request redaction; replay tests for retry class, reconcile, `usage` parsing and price settlement; faults injected into recordings are labelled recorded-real replay. | L3 MCP protocol | spawn the binary with an rmcp client over stdio: initialize, tool list and schema hashes, every tool's positive path, invalid arguments, unknown category, traversal, overwrite attempt, missing key, refusal when validation failed or review missing, cancellation, idempotent retry returns the same candidate; real Claude Code session with the project `.mcp.json` (project trust prompt) as a manual evidence run | tool-protocol evidence |

## 9. Risks and open questions (batched for one consultation)

Risks
- R1 Model and endpoint churn (three retirements in eight months): data-file model tables with dates, drift test, never ids in skills.
- R2 Rights and terms not verified: output terms for BFL, Stability and fal models; Paradox's rules and Steam Workshop disclosure for AI-generated mod assets were not researched. The documentation must not promise anything until checked.
- R3 Plugin account risk is borne by the user; wording per section 7.4; terms question open.
- R4 Sending Paradox's vanilla art as references to a third-party provider is a data transfer of copyrighted material. Hosted Factory must default to off (REQ-048, SPEC-011 EXT-15); the kit's `vanilla_reference` shelf ships Paradox-derived PNGs inside an Apache-2.0 repository while NOTICE says the artwork belongs to its owners, a question that exists independently of this MCP.
- R5 Quality of tiny assets from 1 MP generations is a hypothesis; the first recorded runs decide the default tiers.
- R6 Duplicate QA logic in Rust and Python until `gfx.py` is retired; mitigated by parity tests and shared finding codes.
- R7 Windows build size (11 GB free on C:): shared target directory, release artifacts built in CI.
- R8 ComfyUI workflows are brittle (node versions, custom nodes); workflow templates need slot files and a version check against `/object_info`.

Open questions for the maintainer
