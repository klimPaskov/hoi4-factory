## 1. Executive summary

Net result across the three topics: zero required new web runtime dependencies, one optional (CodeMirror 6), three small Rust crates on the server, and no change to the Git engine.

Topic 1 (notes): Do not invent a format. Use Obsidian-compatible CommonMark + GFM Markdown with YAML frontmatter, `[[wikilinks]]`, tags and aliases, stored as files in the project's Git repository (default `.factory/notes/`), with PostgreSQL holding only a rebuildable search/link index (an ADR-009 "search projection"). Parse and render on the server with `pulldown-cmark` (MIT, has Obsidian-inspired wikilink support), parse frontmatter with `serde-saphyr` (Apache-2.0/MIT, `unsafe` forbidden, configurable budgets), sanitize with `ammonia`. Notes complement ADR-022: memory stays automatic, unbrowsable and about agent behavior; notes are explicit, browsable, Git-versioned project knowledge with a status field (confirmed, proposal, assumption, outdated) and are the natural destination for ADR-022 Lane D canon/lore "design proposals". Karpathy's LLM-wiki pattern (verified from the original gist) fits, except that `index.md` and `log.md` must be generated, not hand-appended, or parallel agent worktrees will conflict on them. Retrieval: PostgreSQL full text + pg_trgm + one-hop link expansion; no embeddings now. Biggest open risk: how the Paradox Launcher uploads a mod folder is UNVERIFIED (no public statement found), so the Factory's own packaging step must be allow-list based and a disposable upload test is needed when Workshop publishing starts.

Topic 2 (onboarding): Build a small in-house tour on the platform (Popover API + CSS anchor positioning, both Baseline "newly available" in 2026) with tours as versioned data, `data-tour` target attributes, i18n keys, completion verified from server state, and a CI test that every target exists. If the maintainer wants a dependency instead, pick Driver.js (MIT, zero deps, 8 KB gzip, role=dialog and focus trap in source). Reject Shepherd.js and Intro.js (AGPL-3.0 or paid commercial license: compatible today, but a trap if the project ever earns revenue), Reactour (focus lock disabled, hard-coded English aria-labels), Onborda/NextStep (Next.js oriented), OnboardJS (release candidate), Usertour (a separate service).

Topic 3 (Git): Keep shelling out to `git` (already the design). Do not add git2 (second engine, C dependency) or gix now (push, apply, rebase, cherry-pick, stash and merge-state persistence are unchecked in its own status file). Use patterns proven by GitHub Desktop and lazygit: hunk/line staging by generating a patch and running `git apply --cached`; conflict detection by `git merge-tree --write-tree` (git 2.38+, present in bookworm's 2.39.5); undo through recorded ref snapshots (jj operation log / GitButler Undo Timeline idea) layered on the restore-point refs that already exist. Render diffs with an in-house accessible table component fed by server-parsed hunks (react-diff-view is the fallback dependency). Resolve conflicts with a per-region chooser; CodeMirror's merge package has no 3-way mode. Reject Mergiraf (GPL-3.0, no Paradox grammar, languages are compiled in) and difftastic (CLI); adapt the idea as entity-keyed merging using the project's own HOI4 parser. Image diffs: GitHub Desktop's four modes (two-up, swipe, onion skin, difference blend) with CSS only, server-side DDS/TGA to PNG conversion, pixelmatch only if a mismatch count is wanted.

### 2.1 Formats and conventions (portable first)

| Item | Pin | License | Status |
|---|---|---|---|
| Obsidian format conventions | help pages on obsidian.md/help (fetched); source repo obsidianmd/obsidian-help @4aa30a3370, last commit 2026-10-28 | The help repo has no LICENSE file (API 404, repo listing showed none), so reuse terms are unstated: use it as a reference, do not copy its text | Verified. There is no formal spec for Obsidian Flavored Markdown. |
| JSON Canvas | obsidianmd/jsoncanvas @456f843cb2 (2026-07-24); spec 1.0 dated 2024-03-11 | MIT (LICENSE file) | Verified. Formal open spec, 3,748 stars, no release tags, small. |

Verified Obsidian conventions (from the help pages):
- Obsidian follows CommonMark, GFM and LaTeX, and adds internal links `[[Link]]`, embeds `![[Link]]`, block IDs `^id` with block references `![[Link#^id]]`, comments `%%text%%`, highlights `==text==`, callouts `> [!note]`. Internal links, comments and highlights are Obsidian specific.
- Links: `[[Note#Heading]]`, `[[#Heading]]` for same note, pipe for display text `[[Note|Custom]]`, Markdown links are supported "for interoperability", wikilinks are the default. Block IDs may contain only Latin letters, numbers and dashes, and "block links don't work outside Obsidian". A link to a nonexistent note creates it at the written folder path.
- Properties are YAML frontmatter between `---` lines; types are text, list, number, checkbox, date, date and time, tags; default properties `tags`, `aliases`, `cssclasses` (lists). JSON frontmatter is read but rewritten as YAML.
- UNVERIFIED: the "shortest path when unique" wikilink resolution rule (the fetched page did not state it), how Obsidian treats `.txt` mod files when a vault root is a mod repo, and whether GitHub's web UI renders `[[ ]]` (it likely does not). Do not depend on these.

JSON Canvas 1.0 (verified): two optional arrays `nodes` and `edges`; node types text, file (path plus optional `#` subpath), link (url) and group; edges have `fromNode`, `toNode`, optional sides, ends, color, label; colors hex or preset "1" to "6". The file extension is `.canvas` (the repo ships `sample.canvas`; the spec page itself did not state it). Recommendation: allow `.canvas` files to live in the notes folder as opaque, preserved files; add a read-only SVG viewer later only if users ask. Third-party React viewers exist but I did not evaluate them.

Compatibility profile to adopt ("Factory Markdown"):
1. Required: CommonMark + GFM (tables, task lists, footnotes), YAML frontmatter, `[[wikilinks]]` with `|alias` and `#heading`, tags (`#tag` inline plus `tags:` property), `aliases:`.
2. Preserve byte-for-byte, never rewrite: callouts, `![[embeds]]`, block IDs `^id`, `%%comments%%`, `==highlights==`, math, unknown frontmatter keys, `.obsidian/` folders. This mirrors SPEC rule "unknown script constructs remain preserved".
3. Do not generate `^id` block IDs (they do not work outside Obsidian). Address sections by heading anchors.
4. Filenames: lowercase ASCII slugs, no characters illegal on Windows, unique case-insensitively (macOS and Windows are case-insensitive, the Linux server is not); reuse the workspace `paths::resolve` rules. Use LF endings via `.gitattributes`.
5. Cross-note links: accept wikilinks and Markdown relative links on read; emit wikilinks by default with a per-project switch to Markdown links (Obsidian documents that switch).

### 2.2 Karpathy's "LLM wiki" pattern (original source read)

Source: gist `karpathy/442a6bf555914893e9891c11519de94f`, file `llm-wiki.md`, first commit ac46de1ad27f (2026-04-04), gist updated 2026-10-31. It is an "idea file" meant to be pasted to an agent; it has no code and no license statement. Accurate description:
- Contrast with RAG: instead of re-deriving from raw documents on every question, the LLM incrementally builds and maintains a persistent interlinked Markdown wiki that sits between the human and the raw sources; knowledge is compiled once and kept current; cross-references and contradictions are already flagged.
- Three layers: raw sources (immutable, the source of truth), the wiki (LLM-owned Markdown), and a schema document (CLAUDE.md or AGENTS.md) describing structure, conventions and workflows.
- Three operations: ingest (read a source, discuss, write a summary page, update index, update affected entity/concept pages, append to the log; one source may touch 10 to 15 pages), query (search, read, answer with citations; good answers can be filed back as pages), lint (find contradictions, stale claims, orphans, missing concepts and cross-references, data gaps).
- Two special files: `index.md` (content catalog, per page a link and one-line summary, organized by category, read first when answering; claimed to work at roughly 100 sources and hundreds of pages without embedding infrastructure) and `log.md` (append-only chronology with a greppable entry prefix such as a dated heading).
- Optional tooling: a local search engine for larger wikis (the gist names tobi/qmd), Obsidian Web Clipper, graph view, Marp, Dataview over frontmatter; "the wiki is just a git repo of markdown files".
- It has the same shape as this repo's own CLAUDE.md/AGENTS.md "schema".

Mapping to HOI4 Factory: raw sources = mod files, imported mods, game reference and uploads (immutable inputs); wiki = project notes; schema = a short per-project notes guide (conventions, status vocabulary, naming) loaded into the agent's context.

Two necessary adaptations:
- Do not let agents hand-append `log.md` and hand-maintain `index.md` in the notes folder. With parallel task worktrees (already the design) these are guaranteed merge-conflict hotspots. Generate both views server-side from the index (and `git log`), and render them in the UI; optionally commit them only on demand as export files.
- The gist lets the LLM own the wiki. For a shared mod, `confirmed` status must require a human decision (see 2.5), consistent with ADR-022 Lane D.

### 2.3 Where notes live: options, Workshop and GitHub implications

| Option | Pros | Cons |
|---|---|---|
| A. In the mod repo, `.factory/notes/` (recommended default) | Atomic commits with the code ("focus changed + design note updated"); Git blame gives per-line human/agent attribution for free; travels with clone/fork/PR; works in Obsidian, VS Code (Foam), Quartz; mirrors GitHub reviews | Risk of shipping in the Workshop upload (unverified, see below); public if the repo is public; PR noise |
| B. Separate notes repo per project | Zero chance of shipping with the mod; separate privacy | Two repos to create, link, sync and permission; non-atomic with code changes; harder for hobbyists |
| C. Database only (PostgreSQL) | Fast, RLS-isolated, easy FTS | Not usable outside the app, no Git history/blame, contradicts "native files and Git are the source of truth" |
| D. Orphan branch in the same repo (for example `factory/notes`) in a second worktree | Cannot ship on the mod branch; same repo and permissions | Not visible in PR diffs with code; not atomic; confusing for beginners |

Recommendation: A for files, plus a PostgreSQL search projection (rebuildable from the files, tenant column and RLS per the existing data rules). Label it clearly in the UI: "Notes are part of your repository; anyone who can see the repository can read them." If a project needs private notes, they stay out of v1 (do not invent a second store).

Steam Workshop and mod uploads (what is known):
- Verified (HOI4 wiki, Mod structure): the `.mod` file is local only and is "not uploaded when publishing via Steam Workshop"; `descriptor.mod` sits inside the mod folder; `thumbnail.png` is the Workshop image. The HOI4 wiki Modding page has no section on what the launcher uploads or excludes.
- UNVERIFIED and unresolved: whether the Paradox Launcher's Upload mod flow skips dot-folders such as `.git` or any ignore file. A Paradox forum thread asking exactly this exists (title: "is there any way to make launcher ignore certain directories like git when uploading a mod") but both fetch attempts failed (validation page, then HTTP 500), so its answers are unread. Web searches found nothing authoritative. Do not assume exclusion.
- Consequence: the Factory's own publish/package step (deferred stage) must build the Workshop payload from an allow-list of game directories plus `descriptor.mod`, `thumbnail.png` (not "everything except notes"), and a validator must warn users who upload manually through the launcher. Also add `.factory/ export-ignore` to `.gitattributes` so `git archive`-based consumers skip it.
- Proposed experiment (not run; Workshop publishing is deferred): upload a disposable mod containing `.factory/notes/x.md` and a `.git` directory through the Launcher, then download the item and list its files. Record spend/time and the Launcher version.
- GitHub: notes render as Markdown on github.com (wikilinks probably show as raw brackets, unverified). Block references and embeds will not resolve there. Keep a per-project switch to Markdown links for projects whose collaborators read on GitHub.

### 2.5 How notes relate to ADR-022 memory (complement, not duplicate)

| | ADR-022 memory | Notes |
|---|---|---|
| Purpose | Make the agent stop repeating mistakes, personalize it | Shared, human-readable project knowledge: lore, mechanics, conventions, design decisions, plans |
| Writer | Background reflection job, automatic after the verification gate | Humans and agents, explicit, proposal then acceptance |
| Store | PostgreSQL rows with RLS, ledger | Markdown files in the project's Git repo; PostgreSQL index is derived |
| Visibility | No browse or edit page (maintainer choice); Undo and forget | Browsable, editable, diffable, outside-the-app readable |
| Authority | None, always data | None, always data (untrusted input to the model, labelled with status) |
| History | Ledger | Git log and blame |
| Canon | Lane D: never memory | Home of canon: a `proposal` note is a KnowledgeCandidate; a human-accepted `confirmed` note is the file form of an ApprovedCanonVersion (mapping needs maintainer confirmation) |

Rules to avoid duplication:
1. A MemoryItem never copies note text. It may cite a note by path plus blob hash ("project convention documented in note X"), and Lane B "observable in accepted source" can treat an accepted note as an observable source.
2. ADR-022 Lane D "canon changes become design proposals": implement the proposal as a note change proposal (`status: proposal`) accepted through the normal review flow.
3. Both memory and notes enter the context assembler as labelled, attributed data blocks that grant nothing; an `outdated` or `assumption` note is shown with that label.
4. Notes do not reopen the "no page to browse memories" decision: that decision is about the automatic memory store; the notes browser is a different feature.

### 2.6 Proposed note model (frontmatter)

```yaml
---
id: focus-tree-conventions        # stable slug, never reused
title: Focus tree conventions
type: system                      # lore | mechanic | convention | decision | plan | reference
status: confirmed                 # confirmed | proposal | assumption | outdated
tags: [focus, naming]
aliases: [focus naming]
authors: [human:klim, agent:run-0183]   # also derivable from git blame
confirmed_by: human:klim          # required when status is confirmed
refs:                             # mod files and assets, for staleness checks
  - path: common/national_focus/chaos.txt
    anchor: focus:CHAOS_rise      # optional entity key
    blob: 3f2a9c1                 # hash when last verified
links:                            # work items in the app
  job: J-123
  spec: SPEC-005
  pr: 42
supersedes: [old-focus-naming]
---
```

- `status` is set by authors; the server computes a separate derived flag `possibly_stale` when a `refs[].blob` no longer matches the current file (this is the "outdated" signal the agent can act on), so agents never silently rewrite a human's `confirmed`.
- Version history and attribution come from Git (`git log -- path`, `git blame`); agent commits use a distinct author identity or trailer so line-level human/agent attribution works in the UI without a custom table.
- A `lint` operation (the gist's third operation) reports broken links, orphans, missing status, ambiguous wikilinks, case collisions and stale refs, and runs as a validator in the existing validation flow.
- Folders are for humans (the maintainer's Events, Systems, Planning, Agents, Tooling layout works); semantics come from `type`.

### 2.7 Retrieval (ADR-009 compliant)

Verified PostgreSQL facts (v17 docs): `websearch_to_tsquery` (never raises syntax errors), `ts_rank_cd` (cover density, uses proximity), `setweight` A to D, `ts_headline` (output not XSS-safe), `pg_trgm` (contrib, trusted extension, `similarity()`, `%`, `word_similarity()`, GIN/GiST support for LIKE/ILIKE/regex).

Design:
1. Tables (derived, rebuildable, tenant column and RLS like the rest): `note(project_id, path, blob_sha, title, type, status, tags[], aliases[], frontmatter jsonb, updated_at)`, `note_section(note, heading_path, text, tsv)`, `note_link(src, dst_path, dst_anchor, kind wikilink|embed|ref|relation, resolved)`.
2. Query order for the agent tool: exact (id, alias, title, path, tag, entity key such as a focus ID), then full text over sections with weights (title A, headings B, tags/aliases B, body D) using `websearch_to_tsquery` and `ts_rank_cd`, then `pg_trgm` fuzzy on titles, aliases and identifiers (HOI4 IDs like `CHAOS_rise` tokenize badly in FTS, trigrams handle them), then optional one-hop link expansion through `note_link` (a recursive CTE is enough at this size; no graph database), preferring `confirmed` notes and respecting a token budget.
3. Generated map (the gist's `index.md` idea): a compact per-folder listing of title, status, one-line summary, produced by the server, so a small project can hand the whole map to the agent first and then fetch sections.
4. Tool surface (modelled on the Anthropic memory-tool commands and the Obsidian MCP read modes): `notes.map`, `notes.search`, `notes.read(section)`, `notes.backlinks`, `notes.propose(create|patch_section|patch_frontmatter|rename)`; all paths validated against the notes root, writes become change proposals (never direct), size caps.
5. Embeddings: not needed now. Evidence for deferral: the gist claims the index works at hundreds of pages; basic-memory and qmd add vectors for semantic matching, which is a scale and recall question for EXP-05 under ADR-009, not a starting requirement. Trigger to revisit: measured recall gap on real project notes after FTS + trigram + link expansion. (A pgvector service appears in an older research evidence file; the current compose file uses plain postgres:17.6, so a vector extension would be a new image decision.)

### 3.2 In-house option on platform primitives

Verified platform status:
- Popover API: MDN labels it Baseline "Newly available". Provides `popover` (auto, hint, manual), `popovertarget`, `showPopover()`, top-layer rendering; non-modal; focus is not trapped, so focus management is yours.
- CSS anchor positioning: web.dev's January 2026 roundup lists it Baseline "Newly available" with Chrome and Edge 125, Firefox 147, Safari 26. Properties: `anchor-name`, `position-anchor`, `position-area`, `position-try`, `position-visibility`. Anchor positioning changes only visual placement, so keep DOM order logical.
- Testing: jsdom (the project's test environment, jsdom 30.1.3) does not implement the popover attribute; the tracking issue jsdom/jsdom#3721 is open (updated 2026-08-03). Tests must stub `showPopover/hidePopover` or run in a real browser. A plain `role="dialog"` element in a portal with anchor positioning works without the Popover API and is jsdom-friendly; use Popover only for top-layer stacking.
- Fallback for older browsers (Safari < 26, Firefox < 147): a centered, non-anchored card with the same content. Optional dependency if exact placement everywhere matters: `@floating-ui/dom` 1.8.0 (MIT, 21 KB min / 8 KB gzip, @floating-ui/dom @93ea014e03 repo), which Joyride also uses.

Sketch of the in-house engine (an estimate of 250 to 400 lines of TypeScript plus about 100 lines of CSS, not measured):
- A tour is data, not code: `{ id, version, requires: [featureFlag], steps: [{ target: 'data-tour=project-create', titleKey, bodyKey, advanceOn: 'next' | 'click' | { appState: 'project.created' } }] }`.
- Targets use dedicated `data-tour="..."` attributes (never CSS classes), so redesigns do not break tours.
- Focus: move focus to the step heading, restore it on close, Escape closes, no dimming overlay so users can operate the real UI ("learn by doing"), aria-live polite step announcement, `prefers-reduced-motion` respected.
- Persistence: server-side per account, `seen[tourId] = version` plus dismissals, not only localStorage.

### 3.3 Patterns that keep onboarding from rotting

1. Tours are versioned data keyed to feature flags and `version`. Show a tour only when `seen < version` and its feature flag is on; bump `version` only when the underlying UI changes. New features ship a small "what is new" tour, never a replay of old ones.
2. A CI test (Vitest + Testing Library, or a browser test) renders each tour's route and asserts every `data-tour` target exists and every i18n key exists in all locales (the project's i18n lint already exists). A missing target fails the build instead of confusing users.
3. Tasks verified by app state, not clicks: onboarding checklist items are computed from server facts (project created, setup applied, first agent run finished, first proposal accepted, first save point made, GitHub linked) through one endpoint. Verified analogues: GitHub Skills courses are template repositories whose GitHub Actions workflows watch your activity and advance the README to the next step; MediaWiki's Growth team ships a newcomer homepage with suggested tasks and a help panel (its feature summary says the help panel alone does not raise edits, but supports the tasks flow). Lesson: real, in-context tasks beat passive help.
4. Anecdotal warning (one forum report, not a study): Discourse's opt-in tutorial bot in a private message had very low completion in one admin's report (3 of 90 replied, 1 completed). Do not hide the first-run experience in a separate channel; embed it in the real first screens and keep it skippable and replayable.
5. Empty-state guidance: every empty list has one sentence of explanation and one primary action ("Create your first project"). Offer a "Start from a sample mod" project (a tiny repository the maintainer controls; `klimPaskov/hoi4-factory-test-mod` is the existing test repository) so beginners can see the loop before importing their own mod.
6. Docs-as-code help panel: help topics are Markdown files in the repo (same pulldown-cmark pipeline as notes, rendered at build or server time), opened by a `?` button keyed by route or component (`helpKey`). A test asserts every `helpKey` has a file. The same text feeds a public docs page.
7. Always optional and replayable: a "Tour" entry in the help menu replays any tour; "Don't show again" is per tour version.
8. Beginner/advanced split: onboarding explains the default simple path; advanced Git controls are introduced by a tour only after the user opens them.

Recommended conflict flow (no new dependency):
1. Detect: `git merge-tree --write-tree --name-only -z <ours> <theirs>` for a pre-merge conflict list without touching any worktree; this also powers the "will this merge cleanly?" badge on PRs.

5. If CodeMirror 6 is approved for other reasons, use it for the "edit result" pane with `mergeControls` custom buttons.

### 4.6 What makes Git approachable for hobbyists (patterns to adopt)

1. Save points: present a commit as a "save point" with a plain message. The workspace already has restore points under `refs/hoi4factory/restore/<task>/<label>`; extend this idea to automatic save points before every agent run and before every risky operation (jj snapshots the working copy automatically; GitButler has an undo timeline).
2. Plain-language status (no staging vocabulary by default): "3 changes not saved yet in 2 files", "GitHub has 2 newer saves", "1 file needs your decision". Group changes by game concept (focus, event, localisation, gfx) with a "Show raw diff" advanced toggle.
3. Undo everywhere: record each Factory-initiated Git operation with the before and after ref states in the existing ledger, and offer "Undo" that restores refs (jj operation log pattern). Unreferenced objects are kept alive by the restore refs, so undo is safe. lazygit's undo covers only commits and branches, so also capture the working tree in a save point.
4. Branches as "try an idea": agent tasks already get a branch and worktree; present them as "Agent's draft" versus "Your version", with a one-click "Keep this draft" (merge) or "Discard".
5. Selective saving: file, hunk and line checkboxes, using the proven patch path (build patch from selected hunks, `git apply --cached --unidiff-zero`, as GitHub Desktop does); `commit_paths` already refuses surprise staged changes.
6. Progressive disclosure: simple view by default; advanced controls (raw index, branches graph, cherry-pick, rebase) behind an "Advanced" switch, introduced by a tour only after first use.
7. Guardrails: confirm any discard, show what will be lost, never auto-resolve conflicts silently, show validation status next to the save action, and link GitHub check results next to internal validators.
8. Reviews and PRs: mirrored GitHub data uses the same diff component with inline comment rows; the server already has `reqwest` and `jsonwebtoken`; `octocrab` 0.54.7 (MIT OR Apache-2.0) is available but I did not evaluate it against the existing code, so keep typed `reqwest` wrappers unless endpoint count grows.

### 4.7 Topic 3 consolidated recommendation

| Responsibility | Choice |
|---|---|
| Git engine and write path | `git` CLI (existing); no new crate |
| Optional later read acceleration | `gix` 0.90.x, only after measuring a need |
| Hunk and line staging | Server-built patch + `git apply --cached --unidiff-zero` (GitHub Desktop pattern) |
| Conflict detection and merge | `git merge-tree --write-tree` and `git merge-file --diff3`/`zdiff3` (git >= 2.38) |
| Diff model | Server parses `git diff` into structured hunks with stable IDs; `similar` 3.2.1 (Apache-2.0) only if in-memory proposal diffs are needed |
| Diff UI | In-house accessible table component; fallback dependency react-diff-view 3.3.3 |
| Conflict UI | In-house region chooser; CodeMirror 6 merge only for an optional edit pane |
| Structural merge | None now; future entity-keyed merge with the project's own HOI4 parser |
| Image diffs | In-house CSS modes (two-up, swipe, onion skin, difference); server PNG conversion; pixelmatch optional |
| Undo and save points | Ledger of ref snapshots + restore refs (jj and GitButler idea) |

Rejected: git2-rs/libgit2 (second engine), Monaco (weight), diff2html (HTML strings), git-diff-view (0.x, heavy), Mergiraf (GPL-3.0, compiled-in languages, no Paradox grammar), difftastic (CLI), GitButler code (FSL competing-use clause), Sapling ISL (coupled to `sl`), Gitless (MIT, v0.8.8, last commit 2021-02, stale).

## 5. Cross-topic synergies

- One Markdown pipeline (pulldown-cmark + ammonia) serves notes, help panels and PR/issue body rendering.
- One optional web dependency, CodeMirror 6, could serve note source editing, read-only file viewing and the conflict edit pane; if not approved, a textarea works for all three at lower comfort.
- Onboarding checklist items (first save point, first accepted proposal) reuse the Git ledger; the Git tour is versioned like any other.
- Notes make the first-run sample project teachable: the sample ships with three example notes (one per status).
- Generated artifacts (note index/log, help index) are never hand-edited, which avoids merge conflicts in agent worktrees.
