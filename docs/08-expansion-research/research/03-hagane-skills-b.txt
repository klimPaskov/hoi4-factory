Status vocabulary used in the verification ledger:
- CONFIRMED: the installed game (script, data, documentation/, or strings inside hoi4.exe) agrees.
- CONTRADICTED: vanilla data or game documentation disagrees; evidence given.
- UNVERIFIED: cannot be decided offline (engine runtime behaviour, UI geometry); I say what I did find.
- INFERRED: my own reading, not stated in the source.
Verification tooling I used: a small Python 3.9 PDX-script parser (kept in the session scratchpad, not in the repo) run over vanilla events/, common/, history/, interface/ and localisation/; grep over hoi4.exe for engine message strings; the markdown documentation/ folder; and the documentation files the game itself ships inside common/ subfolders (about 40 `_documentation.md` files, see section 7).

## 1. Executive summary

What this half of the repository is. Seven "build card" skills, one human-facing guide and thirty field-reference files that together teach an agent how to drive a closed hosted platform (scharnhorst.hagane.works) through forms: POST fields, GET them back, run the platform validators, then load the zip in the game and read error.log. The cards deliberately do not repeat field tables. They carry (a) a form-field to HOI4-output emission map, (b) a "want experience X, fill fields Y" cookbook, (c) the wiring to other entities, (d) a self-check ("GET back and assert") and (e) a distilled trap list marked with a red-dot icon. The platform mechanics (routes, wrapped lists, int FKs, raw_extras, upload endpoints, auto-suffixing, export gates) are specific to the hosted API and are not reusable. The underlying HOI4 knowledge, the trap catalogue and the verification discipline are reusable.

Highest-value takeaways for us (details in the catalog, section 8):
1. A trap catalogue of "looks valid, silently does nothing or silently breaks something later" items, many of which can be turned into offline lint rules: asymmetric mutually_exclusive, relative_position_id ordering, prerequisite AND/OR shape, decision visibility gates, idea picture sprite existence, TAG length, capital ownership, impassable states needing force_link_ownership_to, duplicate ideology group blocks, loc key charset, missing second language.
2. The malformed-effect cascade: one wrong-shape effect in a focus reward desyncs the parser and the rest of the file's focuses vanish in game while static checks stay green. The diagnosis rule (find the first Unexpected-token line, not the last) is directly usable.
3. A fully game-tested, honestly labelled guide (dynamic-spirit-from-variables) that is an excellent model for our own recipes: it states which sections were run in game on which build and which parts come from the wiki only. Its scope findings (PREV not ROOT in recount loops, prefixed variable names instead of a nested scope block) are real, subtle and cheap to encode as lint rules.
4. Verification ladder design: entity-level assertions after every write, then platform validate, then lint, then in-game error.log as the last gate, plus explicit "false green" warnings (wrapped list reads as empty, silent id suffixing, silently dropped dangling references).
5. Several Hagane statements are wrong or outdated for 1.19.3.0 and must not be copied (list in section 6): continuous-focus recipe, war_with_on_add, wargoal folder name, two attache/lend-lease on_actions that do not exist, script-BOM rule, the "Trial of Allegiance owns MIOs" label, button size crash, and the coincident-node crash claim.
6. Adjacent finding that Hagane did not use: the game ships first-party `_documentation.md` files in about 40 common/ subfolders, a loc_formatter documentation with idea_name/idea_desc/advisor_desc tooltip formatters, and console commands (loc_check, loc_check_events, loc_check_focuses, loc_check_decisions, loc_check_characters, loc_check_national_spirits, loc_check_modifiers, debug_checkportraitssanity) that do what Hagane asks the agent to do by eye. These are generic, free and offline.

## 2. How the half fits together (architecture)

Layers, from most to least reusable:
- Guide (guides/): pure HOI4 script, no platform needed; stated verification level and game build (guides/README.md:6-12; guide :3, :394-400).
- Field reference (field-reference/): map from HOI4 vocabulary to platform fields. Granular by workbench, one file per entity, with a "Common quirks" tail and bold tags on raw-script fields. Linked from the cards in their section 0 and in "Cross-links".
- Build cards (skills/): the emission map and traps. They are thin on purpose: they point to field-reference for shapes, to hoi4-build-api for routes, to hoi4-wiring for cross-entity chains, to hoi4-investigate for root-causing, to hoi4-submod for base-mod references.

Every card repeats the same skeleton: short preamble stating what the card is NOT; section 0 validation sources; emission table; cookbook; wiring; self-check; common traps; cross-links. This uniformity is itself a technique (see H-B66).

Every skill starts with the same auto-update stanza: at session start run a fast-forward-only git pull once, skip silently if offline or not a git checkout (SKILL.md lines 6-9 in all seven cards). I recommend not adopting this (H-B70).

Platform-specific versus generic, one-line map:
- Platform-specific: route names, int-FK vs name-ref idioms, wrapped list GETs, raw_extras, upload endpoints, sentinel values (0 and -1.0 meaning "do not emit"), auto-suffixing, export cross-ref gate that silently drops dangling refs, super-event workbench, translate API, scripted GUI compiler, "scope_kind does not gate visibility".
- Generic HOI4: nearly every item in the trap lists once the platform wording is removed. Sections 3 to 5 mark each.

### 3.1 hoi4-build-events (E)

1. Purpose and activation. Frontmatter (E:2-3): fires whenever filling the Events workbench (country_event, news_event, state_event, namespaces, options, immediate/trigger/after, auto-fire via on_actions) or the super-event workbench. The description advertises three quirks: is_triggered_only vs MTTH exclusivity, per-option effect tooltip, option loc-key collisions, and that scope_kind does not gate visibility. Hand-offs: route table and picture upload to hoi4-build-api (E:20, :155); wiring (focus to event, event to on_actions, THIS/ROOT/FROM scope passing) to hoi4-wiring (E:20-21, :160); leader succession to hoi4-build-characters (E:69, :161); in-game root cause to hoi4-investigate (E:162-163); base-mod references to hoi4-submod (E:134). Hand-offs in: hoi4-wiring chain 1 and 3, hoi4-build-focus section 4, hoi4-build-scenario section 2 (prefer an event's own auto-fire over history script).
2. Workflow. (a) read field-reference/events.md and tokens; (b) validate every raw field (trigger, MTTH, immediate, after, option effects/trigger/hidden effects) for token legality and scope (E:23-33); (c) create the namespace first, with a mod-unique prefix (E:38); (d) fill fields following the emission table (E:36-51); (e) pick a cookbook recipe for the desired experience (E:53-69); (f) wire it to callers (E:122-134); (g) GET back and assert (E:136-140); (h) platform validate; (i) in-game pass. Super-events follow a separate workbench path with their own cookbook (E:71-120).
3. Dependencies. Platform API: nested namespaces route, POST /events, upload-picture, super-events routes, export/validate, lint/tree-validation. Generic: HOI4 event syntax, error.log, on_action names (e.g. on_startup), effect `country_event = { id = X days = N }`.
4. Verification routine. Entity-level: namespace registered, never both is_triggered_only and mean_time_to_happen, no option key ending in .t or .d, both languages of title and desc, every raw token validated (E:136-140). False-positive guards: typo'd country_event references are silently dropped by the export gate so a green export proves nothing about reachability (E:123-125, :152); the list GET for super-events returns a wrapped object so a naive length reads zero (E:118-120); a super-event nobody references is dropped from the export and only the skip log says so (E:95-98); a custom picture without an upload is dropped (E:50).
5. Notable techniques (file:line):
   - Mod-unique namespace string to avoid vanilla collisions, with the engine log symptom (E:38).
   - Fields that look like gates but are only file organisers (scope_kind, country_tag, shared_country_tags): scope events through the trigger instead (E:39, :146-147).
   - Deterministic ai_chance: platform forces a base of 100 when unset; remember base is not factor (E:43, :150).
   - Per-option tooltip for var/flag rewards so the option does not show an empty effect box (E:44, :62-64).
   - Emission order of an event: flags, trigger, MTTH, immediate, options, after (E:47).
   - immediate is for pre-popup setup wrapped in hidden_effect, after for cleanup (E:47).
   - Hidden helper plus self-requeue heartbeat via country_event with a days delay (E:58-59; FR/events.md:49-50).
   - Self-fire without a caller via auto-fire fields that generate on_actions entries with a per-country tag guard (E:49; same idea in hoi4-wiring chain 3).
   - Leader succession via kill_country_leader plus create_country_leader inside an option, no pre-created duplicate leader (E:67-69).
   - Super-event model: generated hidden driver event with an auto id, scripted GUI overlay, loc routers and placeholder art; background upload only; dormant-drop rule; SE-to-SE chains (E:71-120).
   - Base-mod submod gating: which ids are checked at export and which only feed a scan; the per-event lint is not base-mod aware (E:130-134).
6. Version-sensitive or doubtful claims. See ledger V01 to V12 (section 6). Short form: the <ns>.<int> id rule is a platform rule (vanilla has exceptions); the .d/.t collision is a platform key convention, not an engine rule; MTTH modifier ordering is unverified; the hash-collision explanation for the namespace rule is unverified although the log message exists in the engine.

## 4. The guide: guides/dynamic-spirit-from-variables.en.md (G)

1. Purpose and activation. A human walkthrough, not an agent skill (guides/README.md:3-4). Goal: a national-spirit-like entry whose bonus follows the situation (example: bonus per core state under foreign control), built from a dynamic modifier whose values are variable names, a recount scripted effect, an on_action hook, a country-history initialiser and localisation (G:7-36). It states the verification level up front (G:3) and again at the end (G:394-400). Activation by humans reading the index (guides/README.md:10-12).
2. Workflow (G:46-140): (1) define the dynamic modifier with an enable trigger, an icon, a variable-bound value and a custom tooltip key; (2) write a recount effect that zeroes counters, loops, adds to the counter through a scope switch back to the country, folds with one multiplication and a clamp; (3) hook the effect to a per-TAG daily on_action; (4) initialise variables and attach the modifier in a small separate history file; (5) write loc with the variable interpolation. Extensions: second rule with a nested loop (G:142-202); same-day refresh through on_state_control_changed plus force_update_dynamic_modifier (G:204-226); focus/event tooltips via the tooltip argument on add_to_variable (G:338-374); swapping in other rules and built-in variables (G:278-336).
3. Dependencies. All generic. The workbench note (G:19) says the platform can create the modifier and its values but not the custom tooltip, scripted effect or daily hook; pure-script route is described.
4. Verification routine. An in-game checklist table that marks each row as Pass (machine checkable, e.g. error.log has zero hits, files present with correct BOM) or By eye (G:244-253); a way to induce the state change from the console with a throwaway test event (G:255-276); and a closing paragraph listing exactly what was run (build 1.19.2.0, Denmark 1936, date, observed values) and what was not (three diplomacy hooks, spelling of two triggers inside nested scopes) (G:394-400).
5. Notable techniques:
   - Why an idea cannot do it: idea modifiers take numbers only, a variable name there is silently invalid with no log line; dynamic modifiers accept variable names and recalculate daily (G:40-44).
   - Explanation lines do not generate themselves; the engine prints only the total, rule text is hand-written in the tooltip key (G:68, :382).
   - Count into the country by PREV, never ROOT, because ROOT differs by hook type (G:93-95, :222-224, :381).
   - In a nested loop a scope block on PREV.PREV adds to the wrong country; put the scope chain in the variable name instead (G:193).
   - Fold once at the end (multiply, clamp) rather than adding a scaled amount per item (G:89-90, :189).
   - Per-TAG daily hook, not the global daily (performance), and the TAG must be replaced inside the hook name (G:101-113, :383).
   - Initialise the variable before attaching the modifier (G:126).
   - Use a separate small history file per mod instead of editing the vanilla one (G:117-124).
   - Same-day refresh by recounting in the event hook and forcing a modifier update (G:204-226).
   - Built-in country variables before writing loops (G:282-304).
   - Loop-shape table: pick what to walk, write the test, add to the counter in the owning scope (G:306-315); ratio and step folds (G:317-336).
   - tooltip argument on add_to_variable with the two fixed tokens for added and prior value, and the instruction to search vanilla loc for the modifier's display token because naming is irregular (G:338-357).
   - Common mistakes list as symptom and cause (G:376-384); "Want a different approach?" list that states when not to use the pattern (G:386-392).
6. Version-sensitive or doubtful: see V79 to V88. Key results: all eleven built-in variable names exist; tooltip argument usage far above the stated count; the attache and lend-lease hooks do not exist in 1.19.3.0; script files without BOM is not a rule; the colour and format tokens match vanilla loc.

## 5. The field-reference files: how they are organised and what is in them

### 5.1 Organisation for agent use

- Granularity. One file per entity or workbench, 12 to 107 lines each in my half (most 20 to 50). The shortest are pure field tables (division-templates, division-deployments, countries); the longest are the raw-template domains (balance-of-power 102, peace-conference 107, music 85) and the two with failure-mode essays (ideologies 102, states 102). A file never explains HOI4 semantics at length; it maps "what do I put in this field" (field-reference/README.md:3-5, glanced).
- Standard anatomy of a workbench file: a one-paragraph purpose line (often with a DLC gate, e.g. autonomy-states.md:3-4, intelligence-agencies.md:3-4, mios.md:3-4, special-projects.md:3-4); a Field | Meaning table where raw-script fields are tagged in bold as raw trigger or raw effect; a pointer line to _raw-script-fields.md and tokens.md (e.g. events.md:45, focus.md:37); then a "Common quirks" tail with the traps. Entities with sub-routes add a "Sub-resources" list (countries.md:20-23, custom-traits.md:21-24, equipment.md:23-25, sub-units.md:29-32).
- Anatomy of a raw-template domain file (BoP, music, peace conference, modifier definitions): directory and naming rules, one field table per block with Required and Default columns, a minimal working example, platform entry points, and quirks (balance-of-power.md:9-102, music.md:9-85, peace-conference.md:9-107). This is the richest format and the most reusable, because it is almost entirely about HOI4 rather than the platform.
- What goes in: field meaning, whether a field is raw script, int-FK versus string-key references (autonomy-states.md:24, doctrines.md:28-30, equipment.md:11, division-deployments.md:11, oob-units.md:75-77), sentinel values (history-files.md:9, :14-15, :29-30), tri-state booleans (sub-units.md:37-38), measured facts with version (ideas.md:11, states.md:24-26), failure cascades (ideologies.md:58-81), and workflow notes that are really API semantics (states.md:41-72).
- What stays out: the token vocabulary (it lives in tokens.md, which README.md:15-24 calls a filling aid rather than an exhaustive dump, with the platform as the authority) and the cross-entity chains (hoi4-wiring).
- Linking from skills. Each card has a section 0 telling the agent to read the matching file first (E:24-26, F:23-24, D:26-28, M:27-28, S:27-28), and a Cross-links tail listing exact files (E:156-160, F:176-177, M:215-218, S:179-180). The reference files link back to cards for recipes (focus.md:20 to hoi4-build-focus layout; oob-units.md:83 to hoi4-build-scenario). The README groups files into three families (story and politics, military and hardware, UI and validation) plus the raw-template domains (README.md:65-89, glanced).
- Strengths. Very low redundancy of HOI4 teaching, high density of "this passes a shape check and fails in game" items; consistent tagging; versions and sample sizes stated when a number is given; explicit "not recommended right now" blocks with evidence date for known-broken features (technologies.md:6-17, special-projects.md:9-15).
- Weaknesses. The same trap is restated in card and reference and has drifted (see H-B69); several files defer shape discovery to runtime ("GET an existing node and copy") instead of specifying it (doctrines.md:24-25, mios.md:28-29); field names are the platform's renames, so mapping back to HOI4 tokens needs the card tables (unit_types to type, military_visible to visible, categories list versus repeated category lines); most vocabulary correctness is delegated to the platform lint and error.log rather than written down.

### 5.2 Entries with non-obvious pitfalls worth knowing

(Paraphrased. "Platform" marks hosted-API behaviour; unmarked means generic HOI4.)
- events.md: an event can be self-firing only if not triggered-only (:19-24); option key must avoid title/desc derived keys (:38; platform convention, see V07); scope_kind is file organisation only (:51); auto-fire at startup is the way to initialise variable systems (:29, :49-50).
- focus.md: tree-level initial_show_position is a tagged union and the older initial_show_focus is accepted for compatibility (:11); cost is points divided by the 7-day tick, vanilla 10 means 70 days (:19; confirmed by NFocus.FOCUS_POINT_DAYS = 7); prerequisites list-of-lists (:22); mutually_exclusive must list the other entry nodes on each side (:23); research_bonus is not a focus effect (:40-41); primary country does not auto-pick its tree in a multi-tree platform project (:42-43; unverified).
- decisions.md: category_id on a decision is an int FK (:18); allowed is the static country restriction and decisions are global by default (:21, :52-54); target_root_trigger hides rather than greys (:40); ROOT is the taker and FROM the target in a targeted decision (:55-56). Note the tension at :52 with D:44-45 (see H-B69). war_with_on_add at :44 is not a 1.19.3.0 key (V32).
- ideas.md: picture drops the GFX_idea_ prefix, blank gives a question-mark placeholder, undeclared sprite is dropped and reported (:11); auto_attach_on_start defaults to true (:28); a country-specific spirit should carry an original_tag allowed if other countries can receive it via generic effects (:34-35).
- super-events.md: picture is upload-only, a vanilla sprite name is ignored (:10, :23-24); number unique per country, clash is a 409 (:25); auto_fire_after_days alone is enough to delay, auto_fire_on_startup is an OR'd enable (:26-28); a dormant super-event is rejected on MCP (:29).
- characters.md: one person with commander and advisor roles is one character (:3-4); pure advisor traits go in the generic traits field (:16, :40-41); ideology emits a leader block only for the leader role, default role is general (:44); can_be_captured and always_show_on_actions_tooltip are 1.19 additions (:27-28; the first confirmed by the game's own characters documentation).
- custom-traits.md: modifier is a dict like ideas, not raw text (:27); route id is the integer, trait_id is the string token (:28-29); a country leader trait's icon is an advisor sprite index (:23-24, unverified).
- autonomy-states.md: min_freedom_level is stored as freedom times 1000 (:13, :22-23; vanilla stores 0.4 style decimals, so this is a platform quirk); modifier is a dict; ai_weights maps keys to raw inner text (:25).
- balance-of-power.md: the file alone does nothing, set_power_balance activates it (:73-77, :94-95); side ranges have dead zones (:96-98); decision_category moves the category into the BoP view (:99-100); value clamps at plus or minus one (:101-102). All BoP effects, triggers and the weekly modifier exist in the game docs (V72).
- bookmarks.md: minor flag for small rows and no major key (:13, :21-22); label slots limited (:20); default_country shows without its own entry (:23-24). The card also states the effect block runs after history and before selection (S:57).
- countries.md: tag regex allows 2 to 5 characters although the engine needs 3 (:8; S:42); empty color_ui clears an override (:11); changing tag cascades renames (:29-30).
- division-deployments.md and division-templates.md: template referenced by name inside the same OOB group (:21-22 and :11-12); location is a bare province id (:23); country_tag derived from the oob_file prefix (division-templates.md:20).
- doctrines.md: one discriminated table of four kinds nested by string key; bonuses only inside raw_extras (:3-4, :20-25); xor and allow_in_multiple_tracks are 1.19 subdoctrine-only and stop emitting when the type changes (:15-17, :32-33; confirmed by the game's subdoctrine documentation); source_file is relative to common/doctrines/ (:34).
- equipment.md: every stat optional, absent means inherit, zero is a real override (:17, :28-30).
- history-files.md: sentinels (capital 0, stability and war support -1.0 mean "do not emit") (:9, :14-15, :29-30); one history file per country, duplicate tag is a 409 (:31); capital state must be owned (:32).
- ideologies.md: extension is add-only over 4 groups and 22 subtypes (:13-16; confirmed); a second block for an existing group triggers a duplicate-database-id error that discards the whole block, then cascades into an invalid-ideology error and a leaderless country (:58-72; the engine message strings exist); full file plus replace_path is the only legal way to add a subtype (:49-50); the politics screen shows the group name and the subtype appears only on hover of the leader icon (:83-86); set_party_name takes loc keys, not literals (:87-89; confirmed in vanilla usage).
- intelligence-agencies.md: names is a pool and the engine picks one at random (:11, :24); logo must be an upload (:21-22); agency_id doubles as the sole name token when names is empty (:27).
- mios.md: traits are plain dicts in one column with no ids (:28-30); name is an optional loc key (:31).
- modifier-definitions.md: declares only; nothing sets the value (:22-24); categories need at least one entry and the list of legal values is long (:15); explicit_fields is read-only tracking (:16). The field list matches the header comment in vanilla common/modifier_definitions/modifier_definitions.txt (V76).
- music.md: a wrong station header fails silently and every song in that file never plays (:78-79); .ogg must be real Ogg Vorbis (:80-81); chance only matters in weighted shuffle and a factor of zero mutes a song under a trigger (:82-84); no name loc line means the raw id is shown (:85).
- oob-units.md: scalar fields are strings and invalid tokens return 422, empty string omits the line (:72-74, platform); parents are int FKs, opposite of deployments (:75-76, platform); layout/body_ast exist only to preserve imports and should stay empty when authoring (:77-79); export merges everything per group into one OOB file in a fixed order (:80-83).
- opinion-modifiers.md: PUT is a true partial update and null deletes a key (:20-22, platform); defining the modifier is not enough, something must apply it (:25-26).
- peace-conference.md: the four action types are engine-fixed and you tune cost, AI desire and category grouping (:3-7); scope chain ROOT / FROM / FROM.FROM / FROM.FROM.FROM (:20-28); mid-conference world state is stale so use the pc_ trigger family (:98-100); cost modifiers multiply (three halvings give 87.5 percent off) (:101-102); AI desire at or below zero is an off switch (:103-105); categories are pure UX (:106-107).
- special-projects.md: export can fail to parse and the validate endpoint does not cover that (:9-15); DAG edges are string tokens (:36-37); several numeric fields are free-text raw script (:38-39).
- states.md: edit-only, seed from vanilla (:6-8); impassable pairs with wasteland or enclave and force_link_ownership_to (21 of 21 in vanilla, confirmed) (:24-26); display names are loc overrides with a no-version-suffix rule (:86-102; unverified); two delete routes with different rules and a warning that bulk-delete ids are row ids, not HOI4 state ids (:59-72, platform); never write provinces from memory (:74-77); the game reads the state id from contents but overriding requires the exact vanilla filename (:79-84).
- sub-units.md: flags tri-state (:37-38); typed fields cannot hold everything so import preserves extras and re-emits them (:41, :27); an untouched imported file replays verbatim while any edit promotes the group to structured emission (:42-44); loc is not in the unit script (:45-46).
- technologies.md: custom techs do not render without a grid box (:6-17; confirmed in game files); folder spelling armour_folder (:24); position_y is transformed on export (:27); flat modifier dict silently ignored, use the escape key (:40-46); default name is a placeholder bareword (:38); add_tech_bonus category advice (:51-52, partly incomplete).
- ui-panels.md: compiled output is shown by a files endpoint and equals the export (:35-36, :46); buttons: size block omitted deliberately (:39-41; doubtful); empty sprite falls back to a visible default (:43-44); renaming the token re-derives names (:45).
- wargoals.md: scalar keys whitelisted (:12); typed fields cannot be smuggled through the advanced escape hatch (:15); null on PATCH is rejected (:25-27); the directory name given at :3 is wrong for the game (V75).

## 8. Idea catalog

Format per entry: What it is; Source (Hagane file:line); Type (Generic, Hagane-API-dependent, or Mixed); Area; Concrete HOI4 example; Where it belongs (first guess: CR = Chaos Redux, Kit = Agentic HOI4 Modding Kit, Factory = HOI4 Factory product); Evidence (ledger id).

Areas used: investigation, design, scripting, validation, workflow (agent workflow design), safety (existing-mod safety), other.

### A. Events and reference closure

**H-B01. Mod-unique event namespaces.** What: require a mod-specific prefix on every event namespace and flag any namespace equal to a vanilla, DLC or declared base-mod namespace. The source claims the engine derives an id base from the namespace name, so a collision makes your numbered ids alias the base game's and logs an "already exists" error. Source: E:38. Type: Generic. Area: validation. Example: Chaos Redux adds `add_namespace = germany` (vanilla namespaces are named after countries, DLCs and topics; 436 in events/) and its germany.5 shadows a vanilla event. Where: Kit validator rule, Factory import check, CR pre-flight. Evidence: V02 (log message exists in exe, mechanism unverified).

**H-B02. Event firing-mode lint.** What: classify each event as triggered-only, MTTH, trigger-polled or on_action-fired, and flag contradictory combinations (triggered-only plus MTTH; MTTH with no self-fire intent). Note vanilla itself has two events mixing both, so do not make it an error if an on_action calls the event; warn that the timer is inert. Source: E:45, :60-61, :143-144; events.md:19, :24. Type: Generic. Area: validation. Example: an event written with is_triggered_only = yes and a 30-day MTTH that the author expects to appear at random; it never appears. Where: Kit, Factory, CR. Evidence: V03.

Example: desc = my.1.d and a fourth option name = my.1.d; the button shows the description text. Where: Kit, CR. Evidence: V07.

Source: E:123-125, :152; F:141-142; C:96-103; wiring:129-130 (glanced). Type: Generic principle. Area: validation. Example: an event chain whose follow-up id does not exist; an event option calling an undefined scripted effect; a focus whose prerequisite lives in another tree; an idea granted that no file defines. One bad key character is claimed to kill all later lines in the file; vanilla has zero violations in 1.3 million lines. Source: L:24-30, :80-81, :181-182; G:384. Type: Generic. Area: validation. Example: event id with an accented letter in its derived key. Where: Kit, Factory, CR. Evidence: V41.

**H-B25. The engine does not fall back across languages (claim unverified), so a missing key shows the raw key. Source: L:31-35, :63-66, :172-184; documentation/console_commands_documentation.md:1121-1146 (adjacent). Type: Generic. Area: validation. Example: localisation keys present in English but missing in the Russian file. Where: Kit offline script, CR verification checklist, Factory. Evidence: V42, V48.

**H-B26. Markup-preservation guard for translation.** What: before accepting any translated string, compare the multiset of engine markup tokens in source and target: colour codes and their closer, bracketed variable and scripted calls, dollar-quoted references, escapes, icons; refuse and report on mismatch. Source: L:107-109, :161-163, :189-190. Type: Generic. Area: validation/workflow. Example: a translation drops the closing colour code and the rest of the tooltip turns green. Where: Factory translation feature, CR if translating, Kit script. Evidence: V47.

**H-B27. Translation-run semantics.** What: default to dry-run; fill blanks only, never overwrite human text unless asked; auto-detect source language; report per language coverage and the list of missing keys; adding a locale must also add it to the emit set. Persisting by default is the trap that made "successful" runs write nothing. Source: L:121-170, :187-188, :193. Type: Mixed. Area: workflow. Example: bulk-adding Polish to a 500-key mod without overwriting hand-written Russian. Where: Factory product, CR.

**H-B28. Loc override and vanilla-id reuse rule (needs an in-game test).** What: duplicate keys do not resolve by load order; an override must live in a replace folder, and reusing a vanilla entity id means vanilla text may win, so prefer mod-unique ids. Related claim to test: a state-name override line with no version suffix wins while the same line with :0 loses; note vanilla 1.19.3.0 is almost entirely written without version numbers (1,301,395 of 1,303,741 lines). Source: L:37-41, :90-92; S:85; states.md:86-102. Type: Generic. Area: safety. Example: Chaos Redux renames a vanilla state or leader and the old name still shows. Where: CR (write an in-game test case), Kit. Evidence: V43, V46.

**H-B29. Fill every language at creation time.** What: when an agent creates an entity it should write all required languages immediately; retro-filling after a long build is worse and the marginal cost of inline translation is near zero. Source: L:68-70, :77-79. Type: Generic. Area: workflow. Example: building 200 events with English only and leaving the translation step to the end. Where: Kit, Factory, CR.

**H-B30. Tooltip formatters for ideas, advisors, characters and techs (adjacent).** What: custom_effect_tooltip can pull a live name or description with idea_name, idea_desc, advisor_desc, character_name, country_leader_desc and tech_effect, so reward tooltips never duplicate or drift from the source text. Not in Hagane; relevant to H-B10. Source: documentation/loc_formatter_documentation.md. Type: Generic. Area: scripting. Example: a focus that grants a spirit shows the spirit's real description in its tooltip. Where: Kit, CR.

**H-B31. Encoding rules as checked facts.** What: lint loc yml for UTF-8 BOM and language header and file suffix; do not assert that script files must be BOM-free (vanilla has many with a BOM). Source: G:22-23, :130. Type: Generic. Area: validation. Example: a loc file saved without BOM. Where: Kit. Evidence: V44, V45.

**H-B37. ### I. Scope and script patterns from the guide

**H-B55. Lint: ROOT used inside a scripted effect reachable from an on_action whose ROOT is not the intended country. Source: G:93-95, :193, :222-224, :381. Type: Generic. Area: scripting/validation. ## 9. Limits, open questions and cautions

- Not verifiable offline: runtime behaviour such as the loc key charset killing the rest of a file, no cross-language fallback, replace-folder semantics, :0 suffix override behaviour, left-edge UI occluders, allowed-bypass by add_ideas, bookmark effect order, MTTH modifier ordering. Each should become an in-game test before we state it as fact.
- My counts come from a custom parser that ignores some syntax (focus offset blocks, scripted triggers, inline arrays); treat them as accurate to a few percent. Coincident-node counts in particular are approximate.
- Trial of Allegiance and MIO: I show that the data ties the DLC name to South American AI strategy files and that MIO files are generic; I did not find an authoritative statement of which DLC introduced MIOs.
- Inferred overlaps with our own tooling (focus renderer, script validator, impact inspector) come from tool names visible in this session, not from reading those tools.
- I did not read the platform's closed source; everything about hagane.works behaviour is as stated by the skills, not independently checked.

Do not paste cards or reference tables into our projects; re-derive from the game documentation where possible, which is first-party and was the real source of several Hagane files anyway.

## 10. Ten most valuable ideas (shortlist)

1. H-B04 Dangling-reference closure that reports instead of dropping (also H-B05 orphan detection): the single most reusable validation principle.
2. H-B06 Focus-tree structural lint bundle (reciprocal exclusion, anchor order, unique ids, prerequisite targets), backed by engine messages and vanilla data.
3. H-B08 Parser-cascade triage rule: fix the first error; static green plus missing content in game is the signature.
4. H-B25 Per-language loc completeness with the game's own loc_check commands (and H-B24 key charset).
5. H-B18 Sprite-existence validation with did-you-mean (ideas, focus icons, portraits), measured: 29 vanilla ideas have none.
6. H-B20 Modifier key validation from modifiers_documentation with the three-decimal rule.
7. H-B55 Count in the owning scope (PREV, prefixed variable names) with H-B56 on-action scope table.
8. H-B64 plus H-B65 Verification ladder and false-green catalogue as agent and API design rules.
9. H-B67 and H-B68 Evidence-labelled recipes grounded in measured game facts with version.
10. H-B42, H-B40 Existing-mod safety rules for ideologies and states (never reopen a group; never write provinces from memory).
