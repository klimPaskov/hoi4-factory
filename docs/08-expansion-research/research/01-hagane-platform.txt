## 0. Headline findings

1. [V] The hosted platform is closing. The platform's own Updates page (2026.10.28 entry) says online service stops on 2026-11-11, new registrations and purchases are already closed, game preview is already discontinued, and existing projects can still be exported until closure. Pass orders were fully refunded; other purchases refunded by usage. The team says it plans to publish suitable parts of the code and build a local tool. (https://scharnhorst.hagane.works/en/updates; raw HTML re-fetched with curl and the text confirmed.) That is 11 days after today. Nothing that depends on the hosted API, MCP endpoint or tokens will survive.

2. [V] The brief's premise "the org has one public repo and no platform source" is out of date. A second GitHub organization, `hagane-works` (with a hyphen; created 2026-10-30), published `hagane-works/hagane-studio` on 2026-10-30: a local-first Windows desktop edition of Hagane Works, GPL-3.0-only, Go backend plus React/TypeScript frontend, about 233k non-test Go lines and about 106k TS/TSX lines, 149 documented tools, v0.1.2, single squashed commit 1e831623ed162e1a64763c242c55b249376ba20c. I shallow-cloned it to `.work/ext/hagane-studio`.

3. [V]+[I] Authenticity of that repo is very likely but not confirmed by the team's own channels. Evidence for: the brand icon file is byte-identical to the one the live site serves (git blob SHA-1 04ccf82b... equals the SHA-1 of the live file I streamed into a hash without saving it); the repo's tool names match the hosted MCP tool names documented in the skills repo (7 of 7 checked); the commit email domain is hagane.works; the timing matches the 2026-10-28 announcement. Evidence against / gaps: not linked from the official site or the original `haganeworks` org as of my fetches; the account that made it public (`mickvale`) was created 2026-10-30, one minute before the org; the commit is unsigned. Confirm with the team before relying on its license grant.

4. [V] The original hosted platform's own source (Next.js frontend, Python and Go backend, Asset Lab, AI gateway, billing) is NOT public. `hoi4-modmaking-skills` (CC BY-NC-SA 4.0, HEAD ef7028c12cd021216bfb7660f85ad93e5efc93e1, tag v1.5.0 = 927b3660...) is documentation and skills only and its LICENSE grants no rights to the platform or its source.

5. [V] It is a hosted web workbench (Next.js site behind Cloudflare, Stripe checkout, Google OAuth or email login), with a free Windows "Local Assistant" helper and, since 2026-10-30, a separate open-source local desktop edition. It was never primarily a desktop app.

6. [V] Architecture: the platform owns the project (typed rows, IDs, namespaces, derived localisation keys) and regenerates mod files on export. Its own generated coverage table (web/src/generated/exportCoverage.ts) shows what that costs on import round-trips: for example 99 focus files in to 7 out, 115 decision files in to 2 out, 2334 of 2525 state filenames renamed, and about 43 vanilla directories not routed at all (kept only by overlaying onto the original mod). This is the opposite of HOI4 Factory's native-files-as-truth design and is the main reason it is an inspiration, not a base.

7. [V] Best reusable ideas for HOI4 Factory (all classified in section 3): edit-revision tokens that refuse stale agent writes; a write receipt that separates "saved" from "verified"; preview-then-apply with per-item discard; a coverage/fidelity ledger with named statuses; a flags-set-but-never-read lint; the focus graph interaction model; DLC-aware project settings; draw.io sketch import; honest "export never blocks" policy.

8. [V] Licensing: CC BY-NC-SA 4.0 material cannot go into HOI4 Factory (AGPL-3.0, planned paid credits), the Apache-2.0 kit, or Chaos Redux. Creative Commons lists no non-CC license as compatible with BY-NC-SA 4.0 (https://creativecommons.org/share-your-work/licensing-considerations/compatible-licenses/). GPL-3.0-only material from `hagane-studio` CAN be combined into an AGPL-3.0 project (GPLv3 section 13, LICENSE lines 552-560 of the cloned repo), but cannot be relicensed into the Apache-2.0 kit. Facts and ideas remain free to use; expression is not.

9. [V] The studio repo contains a copy of the field reference (42 files; 12 byte-identical to the CC BY-NC-SA copy, 28 reworded, 2 new) under GPL-3.0. Because the same authors hold both copyrights, they may license both ways, but see item 3 before relying on it.

10. [I] Direct integration is not possible in any useful sense. The hosted service ends in 11 days and has no licensed API for us; the local edition is Windows/WebView2-oriented, Go, keeps its own JSON project store, and would duplicate the source of truth.

### 2.2 Import, reimport, preservation, export

[V] from https://scharnhorst.hagane.works/en/docs/platform-features and /advanced-faq:
- Import reads a mod folder (Chromium native picker; other browsers fall back to uploading the folder). It parses descriptor, characters, focus trees, technologies, ideas, events, decisions, bookmarks, country history, states, icons and portraits into editable entities. Background import with progress. Supplemental import into an existing project with per-kind selection and an overwrite/skip policy.
- Known gaps stated by the platform: OOB history, custom GUI, music/sound and other unmodelled directories land in an "unrecognized" bucket and survive only via the overlay export; intelligence upgrade trees and MIO policy subdirectories not imported; super-events share a checkbox with events.
- Export is a job: check (validation) then download. Three modes: Standalone (only modelled kinds; documented as lossy for large imported mods), Overlay onto the original mod (upload the base ZIP; platform output is merged over it; unmodelled files preserved verbatim), and Differential merge (field-by-field conflicts, use mine / use base / manual). "Also pack imported content" is off by default.
- Reimport: the 2026-10-27 update says existing projects are not repaired automatically; users must back up and import the mod again. [V] There is no merge on reimport.
- Write-back to a folder works only in Chromium (File System Access API).
- Provenance model: each entity carries source `imported` or `created`; editing an imported entity flips it to `created`; default export emits created only (a patch/addon), `include_imported: true` re-emits everything. [D] skills `field-reference/_editing-existing-mods.md:6-36`.
- Vanilla edits are done by "overlay": a same-ID override file plus a hidden event fired at game start that applies the trait/portrait/leader change. [V] getting-started doc ("Core philosophy") and narrative-politics doc (Characters). The platform is "append-only" for submods and cannot suppress base-mod content except through the raw-file override escape hatch. [D] skills `hoi4-submod/SKILL.md:18-39`.

### 2.3 Validation

[V] public docs (advanced-faq) and [D] skills docs:
- In-editor lint banners (for example a flag that is set but never checked), a Validate dialog per focus/decision/event with error / warning / info levels, per-line diagnostics in script boxes, pre-export "Check my mod" across all workbenches, an "Edit Target" badge for loaded-existing mods, a map-health light for states.
- Errors never block export (the button becomes "Download anyway"). The docs repeat that a green check is not engine-level validation. [V]
- REST validation endpoints (documented in skills repo): `POST /api/go/projects/{pid}/export/validate` (cross-references closed, localisation complete, assets shipped), `GET /api/go/lint/tree-validation/{pid}` (token legality and structure), `GET .../relations/graph|entity/{kind}/{id}|country/{tag}` (edges carry `resolved:false` for dangling references), `POST/GET .../scripted-symbols` (used-but-undefined and name collisions). [D] `_validation-tools.md:6-39`.
- Silent drops: unresolved cross-references (for example a typoed event id) are dropped on export and reported in `native_warnings` and in log files at the ZIP root (`_CROSS_REF_SKIPPED.log`, `_TOKEN_LINT.log`, `_MODMADE_EXPORT_FINDINGS.json`, `_RAW_OVERRIDE_FILES.log`). [D]/[V] CHANGELOG.md:67-104, `_editing-existing-mods.md:61-63`; constants in `internal/hoi4/exportengine/cross_ref_lint.go`.
- Under-reporting lesson: the skills CHANGELOG (v1.4.0) measured the old route family reporting 283 issues vs 284, and 165 vs 173 event findings (8 unterminated quotes missed). [D] CHANGELOG.md:67-104.
- Is it schema-aware? [I] Only in the entity-field sense. The "schema" in the studio repo is `internal/schema/tables.json` (a relational-style table and column list) used to fill defaults. Script validation is a hand-written Clausewitz parser with trivia, cross-reference closure, loc file structure checks, DLC-conditional lint and token lint (finding codes such as `clausewitz.unterminated_quote`, `localisation.invalid_key`, `politics.*`, `refs.focus_missing.*`). CWTools rules are used only to read the modifier-name catalog (`internal/cwtools/cwtools.go:22`). So there is no full grammar-driven validation of effects and triggers.

## 4. Licensing analysis (Question 4)

This is an engineering reading, not legal advice. A lawyer should review before shipping anything derived.

### 4.1 What each license is

- Skills repo (docs, skills, field reference, guides): CC BY-NC-SA 4.0. Attribution, NonCommercial, ShareAlike. The LICENSE adds that it grants no rights to the platform, its source code or the game, and that mods built with the skills belong to the user. [V] LICENSE:22-48.
- Studio repo (source, docs, original art, original knowledge articles): GPL-3.0-only, with `third_party/` and files with their own licenses staying under those. [V] README.md:165-175; THIRD_PARTY_NOTICES.md. The game's own files are not included. External sources cited by the articles are not relicensed.
- Paradox: command definitions, scopes and descriptions on the Command Wiki come from the game's script documentation and the site says they belong to Paradox. [V] https://scharnhorst.hagane.works/en/wiki. No Hagane license covers them. Likewise the game's text, sprites and vanilla files.

### 4.2 Compatibility matrix

| Target | CC BY-NC-SA 4.0 skills content | GPL-3.0-only studio content |
|---|---|---|
| HOI4 Factory (AGPL-3.0; planned paid credits via Stripe) | Not allowed to copy or adapt. (1) ShareAlike requires adaptations to stay under BY-NC-SA or a CC-designated compatible license; Creative Commons lists no non-CC license as compatible with BY-NC-SA 4.0 [V]. AGPL forbids added restrictions, and NC is one. (2) NonCommercial: material used in a service that sells credits is at least arguably "primarily directed toward commercial advantage"; a free tier does not clearly cure that. | Allowed. GPLv3 section 13 expressly lets a GPLv3 work be combined with an AGPLv3 work into one combined work; the GPL terms continue for that part and AGPL section 13 network terms apply to the combination [V LICENSE:552-560]. Paid credits do not conflict with GPL or AGPL. Obligations: keep notices and the license text, mark changes, offer corresponding source (already needed for AGPL). "GPL-3.0-only" (no "or later") is fine because section 13 handles the AGPL case. |
| Apache-2.0 Agentic HOI4 Modding Kit | Not allowed (same ShareAlike and NC conflicts; Apache would re-permit commercial use). | Not as Apache. GPL material cannot be relicensed under Apache-2.0. Apache code can flow into GPLv3 but not the other way. If a GPL-derived file were included it would have to sit as a separately licensed, clearly labelled component, and anyone who builds a combined work with it is bound by GPL. The simplest rule: keep GPL-derived material out of the kit. |
| Chaos Redux (licence not stated in the brief) | Not allowed unless Chaos Redux itself is released under BY-NC-SA 4.0. The "mods you create are yours" note applies to output the platform generates, not to copied field-reference text. | Only if Chaos Redux's license is GPL-3.0-compatible and its owner accepts that. Same logic as the kit. |

Other points:
- Aggregation: shipping a CC BY-NC-SA file unmodified, separately labelled, inside a larger distribution is not itself adaptation, but the NC clause then limits how that distribution is used commercially. Not recommended for a hosted paid product.
- Facts and ideas: not protected. HOI4 script rules, "decisions are global by default", the shape of a focus node, API endpoint paths and tool names as facts about how a service works, measured counts (4,257 sprites, 0 of 718 techs rendering) are facts. Re-expressing them in our own words and verifying them against the game is fine. Expression is protected: the wording of SKILL.md files, tables laid out as documentation, descriptions in tool schemas, example prompts and templates, and the selection and arrangement of the field reference as a whole. Copying small tables verbatim is risky even if each fact is free. Where the EU applies, a substantial investment database (for example the 40-file field reference or 96-article knowledge base) can also carry a sui generis database right, which makes bulk extraction riskier than copying one fact.
- Workflows: a method (for example "validate before export", "preview then apply", "seed states from vanilla") is an idea. Do not copy their step-by-step prose or recipes.
- Tool and endpoint names: interface names are low risk to reuse for compatibility, but the descriptions and input-schema wording are expression. Our MCP tool names already differ.
- Brand: "Hagane Works", the logo and the hosted site design are trademarks and brand assets, not covered by GPL (the GPL does not by itself grant trademark rights). Do not reuse the icon or imply endorsement. Attribute honestly if any code is adapted.
- The identical copy of the field reference in the GPL repo means the authors have offered that text under GPL-3.0 as well. That would, in principle, let HOI4 Factory adapt the GPL copy. Caution: [U] authority of the publisher (section 1.4), the copy has no explicit copyright line, and 28 of the 40 shared files differ from the CC version, so you must take the GPL repo's version only, never mix versions. Even then, a bulk copy is optional; a rewrite from game files is cleaner.
- Outbound transport: any GPL-derived code in the Rust server or TS client means the AGPL-3.0 source release of HOI4 Factory must carry the GPL notices for those files.
- Paradox content: do not republish command descriptions from the Hagane Command Wiki as ours; rely on game files via the maintainer's reference tools.

### 4.3 Recommended policy (for the maintainer to decide)

1. Treat everything under `haganeworks/hoi4-modmaking-skills` as read-only reference. No copy, no close paraphrase of structure.
2. Treat `hagane-works/hagane-studio` as the only Hagane source we may adapt, subject to authenticity confirmation, and keep any adapted file in a directory with a provenance note (path, commit 1e83162, license GPL-3.0-only) and headers.
3. Prefer clean-room original implementations for anything touching source-preserving edits, since the fit is poor anyway.
4. Record the decision in docs/02-architecture/maintainer-decisions-2026-10-24.md as the instructions require.

## 5. Architecture trade-offs visible from outside (Question 5)

Hagane's choice: the platform owns the project (typed rows in a database; JSON tables in the local edition), owns IDs and namespaces, derives localisation keys, and generates mod files on export. Vanilla and base mods are touched only additively: same-ID overrides, hidden startup events, filename shadowing, and an explicit raw-file override escape hatch. HOI4 Factory's choice: mod files are the source of truth, Git is history, and edits are source-preserving.

| Dimension | Hagane (platform-owned, regenerate) | HOI4 Factory (native files + Git) |
|---|---|---|
| Round-trip fidelity of existing mods | Lossy by design. Modelled kinds are re-emitted canonically, filenames change and files are consolidated (99 to 7 focus files, 115 to 2 decision files in their own measurement), comments probably survive only partly [I] (the parser captures comment trivia, but output is regenerated), about 43 directories not routed at all and kept only by overlaying onto the original ZIP. The platform itself warns that not every file can be edited or preserved. | Byte-for-byte preservation of untouched content is a stated design goal (Setup). Harder engineering (CST with spans, minimal text edits) but the loss class disappears. |
| Reimport | Manual: back up, import again; existing projects not healed. No merge. | Possible via Git history and 3-way merge. |
| Lock-in | High. Project data lives in the platform. The 2026-11-11 shutdown shows the risk: users must export before the date, and what they get is a generated mod, not their project. The local edition now offers JSON files but the project model is still not the mod. | Low: the repository is the mod. |
| Merge-ability with Git | Poor. Exports rewrite files, so a diff against the previous commit shows churn; a real mod repo (bzhant/huore-nianhua README, claimed [D]) describes unzipping each platform export over the repo root then committing. Overlay and differential merge exist because of this. | Native: small, reviewable diffs, PRs, blame. |
| ID safety and cross-reference closure | Strong in the platform: it can enforce uniqueness, prefix IDs, derive loc keys, and know every reference (relations graph). Because it owns the namespace it can auto-suffix. Cost: mods that already own IDs must be adapted; silent dropping of unresolved references. | Weaker by default (we cannot rename a user's IDs). Needs a mod index and impact analysis (we have hoi4_mod_index and hoi4_impact_inspect) and loud reporting rather than silent drops. |
| Concurrency | Simple: row revisions, one writer wins, stale writes refused for trees and bookmarks. | File hashes or revision tokens plus Git conflict handling. Multi-writer (human plus agent) needs the same stale-write protection. |
| Agent ergonomics | Excellent: typed tools with field docs; agent cannot produce invalid syntax in typed fields, but raw script fields still hold unvalidated text. | Agents edit real script; needs strong validation and source-aware edit tools. |
| Vanilla edits | Additive tricks (hidden startup events). Safe for load order, but changes semantics and can diverge from what modders expect. | Honest overrides via files. Needs care with replace_path and load order. |
| Fit with submods | Strongly additive, can never suppress base content. | Can choose either. |
| Hosting economics | They ran server-side rendering, 3D generation and LLM calls and could not cover costs. | Native files and agent calls are cheaper to host but credits must still cover model spend. A cautionary data point for pricing. |

Evidence for the economics claim: the closure notice's stated reason [V]; the cost structure inferred from the products [I].
