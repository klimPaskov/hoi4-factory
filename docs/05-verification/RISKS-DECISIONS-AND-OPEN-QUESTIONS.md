# Risks, decisions and open questions

Status: **Proposed decisions with explicit unresolved implementation evidence**. Revised on 2026-10-24 for the [maintainer decisions](../02-architecture/maintainer-decisions-2026-10-24.md). This is a working risk register, not a list of reasons to stop planning. The planning package is complete when its artifacts pass QA. Product release decisions depend on the future experiments below.

## Critical risks and ownership

| Risk | Evidence and implication | Owner and decision point | Required response or fallback |
|---|---|---|---|
| RISK-01, Setup restoration | SRC-A09 records a failed exact-HEAD Windows recovery CI case reporting that the project was not restored exactly. Cause is unknown, and the hosted product runs Setup on Linux server paths that the failing case did not cover | Onboarding owner, S01 before production apply reliance | Reproduce and diagnose, then verify a corrected or separately selected pin on server paths. Do not assume an older release is safe |
| RISK-02, callable Setup boundary | SRC-A01 through A08 distinguish portable planning from desktop scan/transaction services and actual Tauri commands. The desktop services assume local folders and launcher data | Onboarding owner, EXP-01 | Prove direct embedding or an extracted facade on server workspace paths while preserving provider-analysis and evidence-confirmation gates. Drop launcher integration rather than emulate it |
| RISK-03, source fidelity | Agent Tools has preserving paths, while comparison writers normalize or discard source details. Supported operations still need execution evidence inside the Linux image | Domain owner, EXP-02 | Use a tested writable subset, refuse unsupported edits and keep raw source accessible |
| RISK-04, replay and ownership | The project now owns the agent loop (ADR-011). Pi and OpenCode showed that hook mutation, replay and persistence are easy to get wrong in SRC-B01/B02, and nothing upstream now carries those fixes for us | Runtime owner, EXP-03 | Host validates final arguments after every repair step, records reconstructable intent, fences ownership and reconciles unknown effects. Use the Pi and OpenCode cases as regression fixtures |
| RISK-05, container packaging | No image has been built. Setup, Agent Tools and any validation tool may assume Windows paths or desktop dependencies | Runtime/release owner, EXP-04 | Build and run each required tool inside the Linux image, record digests and dependency closure, and mark any tool that cannot run there unavailable |
| RISK-06, tool containment on shared servers | Agent tools now run on infrastructure shared by many accounts. A plain container shares the host kernel and is not proof of isolation. A same-user process or MCP server can reach resources outside a logical broker | Security owner, S03 and EXP-07, before public launch | Initial trusted bundled adapters only, typed operations without a generic shell, per-account resource roots. Evaluate a stronger runtime boundary for model-directed tools. Reviewed third-party execution needs demonstrated containment |
| RISK-07, game support | SRC-A17 shows a narrowly qualified native Linux runtime, with unavailable native Windows/macOS and mod-QA paths. The server holds the game for reference but does not run it | Domain owner, S07/S08 | Declare build limits, use separately scoped user-operated game observation where available, never relabel a preview |
| RISK-08, map generation | SRC-A13 shows unavailable geography-model synthesis despite useful previews | Map owner, EXP-06 | Build a separately tested bounded importer of structured files or remain read-only. Full world generation stays deferred |
| RISK-09, provider portability | Project-owned Rust adapters must normalize streaming, tool calls and errors for each provider. Credentials and live profiles were unavailable here | Runtime owner, EXP-04 and S08 | Probe two APIs and one reachable self-hosted endpoint, pin actual profiles and preserve unsupported capability outcomes |
| RISK-10, provider cost uncertainty | Interrupted requests can have billing effects even without a final response. Operator-funded allowances make that cost the operator's | Runtime owner, S03 | Keep original unknown outcome and conservative budget reservation per account and task. Retry only under explicit bounded policy |
| RISK-11, configuration drift | Actual Agentic config has 196 scalar leaves and no model-context override. Its manifest selects Tools 4.0.3 while the separate tool audit is 4.3.0 | Developer workflow owner, S01/S08 | Use the full field map, explicit tool migrations, current client checks and disabled optional connections |
| RISK-12, distributed state | Git volumes, PostgreSQL and artifact storage have different commit boundaries, and GitHub adds a remote with its own state | Reliability owner, EXP-03/08 | Journal intent and reconciliation, test hard kills, back up and restore all three stores consistently, reconcile remote refs before retry and preserve unresolved journals |
| RISK-13, stale knowledge | Retrieved or learned suggestions can conflict with approved design, changed source or a new game reference build | Context owner, EXP-05 | Separate canon, memory, engineering guidance and caches, with source/version invalidation, re-verification of stale items and lane-gated activation under ADR-022 |
| RISK-14, concurrency | Text merges miss shared-symbol, binary and cross-file semantic conflicts. Invited collaborators arrive earlier than the original plan | Collaboration owner, EXP-07 | One agent writer first, owned branches for every human and agent, explicit semantic collision fixtures and fresh merged-result evidence |
| RISK-15, license scope | The project is AGPL-3.0 with attribution terms (ADR-017). Permissive code licenses do not cover every asset or game right. Nova is restrictive and comparison only. Mastra template's declared license lacks a root license text | Maintainer, EXP-07 and S08 | Inventory transitive code and assets for AGPL compatibility before release, exclude restricted material, resolve specific uncertainty before bundling |
| RISK-16, performance | No actual focus/map benchmark ran, and browser rendering plus server load are new factors | UI/map owner, EXP-06 | Benchmark fixed fixtures, server hardware and browsers, narrow affected regions and justify revised targets with evidence |
| RISK-17, user comprehension | An attractive preview may be misunderstood as game verification | Product owner, S08 pilot | Observe users interpreting evidence labels and correcting a broken result, revise the surface based on failures |
| RISK-18, instruction authority | Skill metadata, historical instructions or model-written lessons can be mistaken for new permission | Developer/runtime owners, S01 onward | Shared rules and scoped grants remain authoritative, tested learning review cannot silently broaden policy |
| RISK-19, custom loop maintenance | ADR-011 accepts that the project owns stream assembly, malformed calls, error classes, cancellation, usage accounting and recovery for every adapter | Runtime owner, S01 and S03 | Prefer vetted crates, keep adapters narrow, keep a provider fault corpus as regression tests. Reconsider ADR-011 if measured maintenance cost is materially higher than an adapted library |
| RISK-20, tenant isolation | A public service holds many accounts' mods, keys, tokens and tasks. One missing ownership check exposes another user's data | Security owner, S02 and S08 | Resolve every handle through the owning account and project, test cross-account access on every API, keep per-account secrets encrypted and audited |
| RISK-21, outbound requests from custom endpoints | Users may configure any reachable OpenAI-compatible URL, which can target internal services | Security owner, S03 | Block private, loopback and link-local destinations by default, resolve and pin addresses before connecting, allow exceptions only by operator configuration |
| RISK-22, server game copy rights | ADR-015 places a full game copy with all DLC on a public service. The maintainer deferred the rights review | Maintainer, S08 before public domain exposure | Read-only mount, never in images, exports or raw downloads. Record the rights review before exposure. Fall back to mod-files-only checks if the review fails |
| RISK-23, GitHub scope and limits | Broad tokens would expose repositories the user did not select. API rate limits and outages can interrupt import and publication | Collaboration owner, S02 and S04 | GitHub App with selected repositories and short-lived installation tokens, separate push and pull request grants, back-off and reconciliation of uncertain outcomes |
| RISK-24, operating cost and abuse | Free public use with an operator allowance invites automated abuse and unbounded model, storage and compute cost | Maintainer and security owner, S08 | Per-account quotas and rate limits, upload and workspace size limits, allowance caps, a daily cap on operator-paid memory verification replays, abuse monitoring, and a kill switch that stops new dispatch |
| RISK-25, privacy obligations | A hosted service stores personal data, mod content and provider keys | Maintainer, before public launch | Privacy policy, data retention and account deletion that preserves linked GitHub repositories and offers export first |
| RISK-26, memory poisoning | ADR-022 writes memory automatically. The [MINJA paper](https://arxiv.org/abs/2503.03704) reports high injection success against agent memory through queries alone, read from its abstract only. In shared project memory one member, an imported mod or a non-member GitHub comment could plant an item that fires in every later task | Security and context owners, S05 before public launch | Reflection input allowlist that references external and non-member content by ID only, write-time and load-time threat scans with blocked placeholders, attribution and owner bulk pause or delete per contributor, per-account contribution limits, and the C7 red-team fixtures in T-MEM-03 |
| RISK-27, authority laundering through memory | A learned item such as "the user allows force-push" or "skip validation" could be read by the model as permission | Runtime and security owners, S05 | Lane D rejects grants, permissions, tools, endpoints, budgets and secrets by fixed Rust rules. Memory is a labelled data block that states it grants nothing, permission changes appear at most as a settings suggestion, and the broker checks every effect against grants regardless of memory (T-MEM-03) |
| RISK-28, cross-tenant leakage through memory | Personal memory follows a user across projects and a shared retrieval index could mix tenants, so private project data could surface in another project or another user's task | Security owner, S05 and S08 | Row-level security and a scoped data-access layer on every memory, feedback and ledger row, personal items that reject project identifiers, per-project indexes filtered before retrieval, no project memory in public views or copies, audited break-glass for operators, and T-MEM-01 with T-ACCT-01 probes |
| RISK-29, self-reinforcing bad lessons | Automatic lessons can harden a narrow fix into a rule that regresses good work, and the agent can confabulate why an item exists | Context owner, EXP-05 | Verification gate with deterministic check or counterfactual replay plus do-no-harm sample, per-use attribution with automatic pause on repeated harm, expiry on negative tool claims, conflicts never auto-resolved, and ledger-backed explanations (T-MEM-02, T-MEM-04) |
| RISK-30, global-lesson privacy | Global lessons are learned automatically without human review from many users' projects, which could carry private source, identifiers or behavior into product knowledge | Maintainer and security owner, S05 before the first global lesson ships | Only de-identified rule and fix-pattern signals with placeholders, counted once per project, at least five unrelated projects, replays inside each project's scope with only pass or fail leaving it, identifier-index rejection of the generated statement, contribution following each user's learning switch, maintainer pause and removal, and disclosure in the privacy policy (T-MEM-05) |

## Smallest experiments that resolve architecture uncertainty

| Experiment | Bounded method | Required evidence and decision | Stage / checks |
|---|---|---|---|
| EXP-01, onboarding binding and recovery | In an isolated fixture inside the server image, call actual Setup planning and adapted desktop services on server workspace paths. Exercise new/import and interruption boundaries, including the observed CI case | Exact service binding, preserved gates, before/after inventory, root cause or honest non-reproduction, selected pin and supported recovery variants | S01/S02, T-SETUP-01 through 04 |
| EXP-02, source-preserving focus subset | Run no-op, supported node creation/linking, move and scalar edits over original synthetic difficult syntax/encoding cases | Byte oracle, semantic oracle, explicit unsupported operations and a go/no-go decision for each editor gesture | S01/S04, T-VIS-01/03 |
| EXP-03, Rust runtime and authority | Drive the Rust agent loop with deterministic fake streams and effect observers. Inject malformed and mutated final arguments, truncation, cancellation, hard process death, stale ownership and changed roots, then reopen under a new server incarnation. Compare in-process and worker placement | No unsafe duplicate effects, immutable reconstructable intent, settled versus unknown outcomes and a measured placement decision | S01/S03/S05, T-RUN-02/03/04 |
| EXP-04, containers, providers and GitHub | Build a Linux image that performs one native request with no coding CLI present. Compare a third-party provider crate with thin adapters. Probe approved API profiles and one reachable endpoint with a finite budget. Connect a GitHub App to a disposable repository | Image digest and dependency closure, capability receipts, measured adaptation burden and the actual granted GitHub scope | S01/S03, T-RUN-01/05/06, T-DEPLOY-01, T-GH-01 |
| EXP-05, context and verified learning | Use a fixed question/source answer key with approved canon, stale facts, smaller context and cancelled indexing. Compare exact/domain/full-text baseline before optional semantic retrieval. Seed fixture failures with known fixes, known-useless and known-harmful lessons, and poisoning cases, then sweep the ADR-022 starting thresholds: replay sample count and pass rule, do-no-harm sample size, probation promotion count, harm-pause rule, 60-day stale and archive periods, injection caps and the five-project global threshold | Recall misses, stale-answer rate, budget behavior, review race results, verification false accept and false reject rates, replay cost per lesson against the daily cap, scanner false positives, calibrated threshold values and a justified storage/retrieval decision | S05, T-CTX-01 through 04, T-MEM-01 through 05 |
| EXP-06, visual/map feasibility | Benchmark 500/2,000-node focus and synthetic structured map fixtures in the browser, test bounded map edits and dependency closure, keep reference images distinct | Source preservation, named topology checks, measured latency/memory and a supported operation subset | S04/S07, T-PERF-01/02, T-MAP-01/02/03 |
| EXP-07, collaboration and protection | Run owned-branch collisions between invited members and agents, malicious uploads, cross-account access, stale leases, tool containment and dependency/license inventory on disposable artifacts | No unauthorized effect, complete collision report, reviewed containment proof and distributable closure | S06/S08, T-GIT-01/02, T-SEC-01/02, T-ACCT-01, T-RELEASE-03 |
| EXP-08, restore and release evidence | Back up and restore a staged deployment with unresolved journals, interrupt an image upgrade and schema update, delete and restore an account, export native source and record a user-operated game scenario where available | Source/canon/state recovery, no silent loss, clean native continuation, actual support matrix and scoped game result | S05/S08, T-RELEASE-01/02, T-DEPLOY-01, T-HOI-02 |

An experiment that fails should return a narrow proposed correction or an alternative. It should not silently create a full replacement subsystem. Findings update the ADR, affected spec, stage and test oracle through the normal review process.

## Decision record index

They cover Setup reuse, Candidate A preference, host authority, storage, focus-first editing, maps, one-writer sequencing, Claude-first engineering, retrieval and license constraints. [ADR-011 through ADR-023](../02-architecture/maintainer-decisions-2026-10-24.md) are maintainer decisions recorded on 2026-10-24. They cover the native Rust agent runtime, the public hosted web application with accounts and invited collaborators, Docker deployment, GitHub integration and the in-app GitHub collaboration hub, the server-held game reference, free use with user keys and a monthly allowance, Claude and OpenAI adapters with Stripe for later credits, the gVisor tool sandbox, account and project policies, the AGPL-3.0 license with attribution terms, automatic personal, project and global memory with verified lessons and no authority, and automatic engineering learning gated by regression tests. Together with the provisional decisions the index spans ADR-001 through ADR-023. They also record their effect on ADR-001 and ADR-003 through ADR-010.

Each accepted ADR must record the approving owner, date, evidence revision, alternatives, constraints, costs, unresolved conditions and reconsideration trigger. S01 may still return evidence against ADR-011 through its reconsideration trigger. That returns the question to the maintainer rather than switching runtimes silently. A documented implementation defect can justify a small upstream contribution or adapter correction before a fork is considered.

## Unknowns that do not block the planning deliverable

Live client loading, MCP connectivity, runtime execution, container builds, GitHub App behavior, paid model trials, sandbox enforcement, actual game checks and usability outcomes are all explicitly unexecuted here. They are implementation gates with owners and fixtures. A complete plan can contain those unknowns because it explains how to resolve them and what must remain unavailable meanwhile.

No unresolved question authorizes an agent to change approved canon, broaden permissions, run a game, purchase API usage, push to GitHub, expose the service publicly or publish the product. Future stage authorization and existing project policy determine those actions. Within an authorized stage, routine reversible engineering should proceed without repeated permission requests.
