# Requirements traceability

Status: **Complete planning map, proposed product behavior**. This index connects stable requirements to architecture decisions, subsystem ownership, first implementation stage and acceptance. A stage is the earliest accountable owner, not the only stage that touches the requirement. Later hardening and release checks remain mandatory.

The authoritative requirement wording is in [product requirements](product-requirements.md) and [requirements.json](requirements.json). Acceptance oracles and execution limits are in [the acceptance matrix](../05-verification/REQUIREMENTS-ACCEPTANCE-MATRIX.md). Decisions are in [the architecture ADR table](../02-architecture/options-and-decisions.md) and the [2026-10-24 maintainer decision record](../02-architecture/maintainer-decisions-2026-10-24.md).

“MVP” includes essential development, source integrity and release hardening. “Later” identifies expanded collaboration/content/map scope after the focus slice. “Research needed” preserves the deferred broad map-creation aspiration without claiming implementation. Out-of-scope first-slice capabilities are recorded explicitly in [the backlog](../04-implementation-stages/BACKLOG-AND-DEFERRED-SCOPE.md).

## Deliberate verification dependencies

No product implementation or actual model/game trial is implied by this traceability. REQ-037 through REQ-040 and REQ-045 have meaningful planning-artifact checks, while live guidance loading, connected MCP and native behavior remain future tests. REQ-032 is satisfied at planning level by a substantive staged contract. Full map synthesis needs a separately authorized implementation and actual verification before any runtime support claim.

A new requirement or changed acceptance oracle must update this map, the machine-readable matrices, its specification and the owning stage. A justified narrowed release scope records excluded requirements explicitly instead of deleting their history.
