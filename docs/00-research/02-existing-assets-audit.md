# Existing assets audit

Audit date: **2026-10-23**. Source findings are **Verified (source)** only where actual implementation was read. Repository CI observations are labeled separately. No application, test suite, published executable or HOI4 process was run in this audit. Reuse decisions are **Proposed**.

Read first: [candidate comparison](03-candidate-comparison.md), [evidence and research log](04-evidence-and-research-log.md), [onboarding specification](../03-subsystem-specs/001-onboarding-and-mod-setup.md) and [HOI4 tools specification](../03-subsystem-specs/006-hoi4-tools-and-validation.md). Machine-readable evidence is in [evidence-a.json](evidence-a.json).

## Decision supported by the evidence

HOI4-Mod-Setup supplies substantial onboarding machinery and should be integrated through an adapter over its existing services. HOI4 Agent Tools is the leading source inspection, rendering and bounded mutation foundation. CWTools and its separately pinned HOI4 rules provide an independent static validation layer. HOI4 Live Tools is an optional, capability-gated observation integration. Modmaker and HOIIVUtils offer useful interaction and algorithm references, with material preservation and integration gaps. Nova remains comparison only because its published license restricts derivatives and commercial bundling, and its public repository exposes no implementation to audit.

This is not an unconditional adoption decision. The most consequential unresolved item is a failed native recovery acceptance test on the exact Mod Setup commit audited here. Its Windows job reports that the project was not restored exactly. That failure must be reproduced and explained before S02 can accept import preservation and recovery. The many source-level guardrails and passing jobs do not erase this contradictory evidence. [SRC-A09, failing job](https://github.com/klimPaskov/HOI4-Mod-Setup/actions/runs/39281117181/job/118160257466)

## HOI4-Mod-Setup: actual onboarding and reusable boundary

### Architecture and entry points

The desktop combines a React interface, typed Tauri calls and Rust services. `crates/hoi4-setup-core` contains portable manifest, descriptor, adaptation, merge, profile, source-export and related logic. Its adapters include read-only filesystem and bounded source access. The scanner, native transaction, credentials and operating-system checks remain in the desktop layer. The source does not establish a ready-made public HTTP onboarding API or stable external SDK. The proposed C-09 SetupAdapter therefore needs to wrap or extract services rather than pretend an existing endpoint can simply be called. [SRC-A01, portable adapters](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/crates/hoi4-setup-core/src/adapters.rs)

The setup assistant and the installed coding environment are separate decisions. Current setup requires provider analysis, but an API or local provider can fulfill that role. This permits a standalone factory to use its native provider integration without making Claude Code, Codex or another coding CLI a runtime requirement. The assistant supplies bounded structured proposals. The native core owns deterministic scanning, source resolution, approval, preparation and effects. Recovery can be entered without restoring a provider session. [SRC-A04, source guidance](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/AGENTS.md)

### Actual new and existing project flows

The route is controlled by `nextScreen` and `previousScreen` in `src/App.tsx`. Seven progress groups organize the finer steps. The initial paths differ, then join the same optional integrations and reviewed installation route. The table describes source behavior at the audited commit, not a hands-on usability test. [SRC-A02, App routes and controls](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/src/App.tsx)

| Phase | New project | Existing project | Important controls and outputs |
|---|---|---|---|
| Welcome | Choose create and setup assistant | Choose import or manage and setup assistant | Provider, model and reasoning configuration are separate from later coding-client choice |
| Description | Name, brief and optional context | Existing source is inspected before confirmed proposals | Description expansion is an assistant proposal, with approved context inputs |
| Identity | Confirm generated conventions and destination | Select root, then confirm discovered identity | Display name, project ID, script prefix, namespace, tags and initial folders |
| Advanced identity | Optional details | Preserve valid existing details | Author, mod version, supported game version, branch and external launcher descriptor location |
| Scan and findings | Not the same existing-source scan route | Bounded read-only scan then findings | Deterministic facts, evidence, conflicts, coverage and proposed changes remain distinguishable |
| Environments | Choose coding clients | Preserve or revise valid selections | New default primary is Claude Code, legacy managed defaults may preserve Codex |
| Components | Image provider, components and workflows | Same dependency-aware selection | Optional Live Tools and Meshy routes appear only when selected and supported |
| Integration | Conditional MCP setup | Same | Credential references and selected runtime checks, without exposing secrets in state |
| Git | Initialize or skip | Preserve, initialize or skip according to state | Branch, commit choice, remote details and local/push/create-public choices |
| Dry run | Review proposed files and commands | Review conflicts and preservation decisions | Create/update/skip/conflict counts, destinations, commands, working directories and expected writes |
| Apply and ready | Create at apply boundary | Change only approved paths | Twelve transaction stages, readiness evidence and unresolved actions |

For new projects, the identity preview includes `descriptor.mod`, a launcher `<project-id>.mod` and `thumbnail.png`. A selected context image can become the thumbnail, otherwise the current code produces a black 600 by 600 placeholder. The generated set can include a provider-neutral README, approved context copies, coding-client projections, image or live integration configuration, `.hoi4-mod-setup/state.json` and merged ignore rules. Component files depend on the resolved source manifest and selection. These are not a promise to generate a complete gameplay mod. [SRC-A05, plan construction](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/src-tauri/src/commands.rs)

### Import, conflicts and preservation

The import scanner binds the selected filesystem root identity and checks it around phases. It does not infer authority over arbitrary parent paths. External launcher descriptors are discovered through a bounded immediate-parent scan and require approval. The implementation exposes file, depth, directory, byte and time limits. A partial or limited scan must remain visibly partial in the factory. Setup inventory is not a complete semantic validation of every gameplay file. [SRC-A03, scanner](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/src-tauri/src/scanner.rs)

Plans are built from a source revision resolved before selected files are fetched. Expected hashes and dependency closure control the incoming bytes. Current local hashes and prior managed hashes determine whether a destination is absent, unchanged or modified. Modified content remains preserved until the user resolves a conflict. The renderer does not supply trusted installation bytes. The core retains prepared plans and later retrieves them by ID. The plan must be approved and the dry run reviewed before apply.

Three-way merge requires a verified old source and a reproducible adapted base. A generated file without that base cannot be called safely mergeable simply because it is text. Existing user instructions, descriptor content, custom scripts and modified managed skills therefore need explicit handling. A new unrelated gameplay file must survive create/import maintenance and rollback. Inspected lifecycle tests exercise several of these cases, including an explicitly retained `AGENTS.md`. [SRC-A07, lifecycle tests](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/src-tauri/src/commands_lifecycle_tests.rs)

The generated ignore policy currently ignores such items as `.agents/`, `.codex/` and `AGENTS.md`. That policy is a source finding, not automatically the correct factory collaboration policy. The adapter must reconcile local generated projections with the factory's shared guidance and review requirements. Blindly copying the ignore list would hide files that contributors may expect to review. [SRC-A05, project files](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/crates/hoi4-setup-core/src/project_files.rs)

### Transaction, rerun and recovery

The native transaction preflights root and external-parent identity, retains source and staged bytes, writes a durable plan and journal, performs backup and validation, applies reviewed operations, runs approved post-install steps, checks readiness and writes the success lock last. The stage list is preflight, source resolution, download, checksum, dry run, backup, staging, validation, apply, post-install, readiness and rollback record. Filesystem checks named `final_live_verification` are not actual game observations. [SRC-A06, transaction implementation](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/src-tauri/src/transaction.rs)

Recovery must follow the actual journal state. Verified staging can resume before application. A partial apply refuses resume in the current test and requires rollback. Finalization has a separate reconciliation path that verifies the success lock and related durable record. The flow document's broader resume wording must not override these source constraints. The factory should expose only the actions returned by the adapter for that state.

The maintenance lock tracks source and installed versions. An update requires fresh maintenance analysis. The inspected update-only guard returns without demanding that same analysis for every repair operation, so product copy must distinguish the operations. Repair restores a missing managed file while preserving a modified managed file. Managed removal releases or preserves modified content rather than deleting it indiscriminately. An historical upgrade test is ignored unless the required old checkout is supplied. Test existence is not a current execution result.

### Repository CI contradiction and required experiment

The audited HEAD has CI run `39281117181` marked failed. Successful jobs include frontend, repository integrity, portable WASM core, Rust on Windows/macOS/Linux, platform desktop E2E, the web edition, and candidate new/client/Kaiserreich paths. The candidate recovery job failed on Windows at the native candidate exercise step. Its log reached `recovery-without-provider`, then reported unequal inventory hashes and “The project was not restored exactly.” The log identifies a surfaced assertion, not the differing files or root cause. [SRC-A09, run](https://github.com/klimPaskov/HOI4-Mod-Setup/actions/runs/39281117181)

S01 must recover the available failure artifact or reproduce the exact source-bound candidate, compare complete pre/post path inventories and determine whether the mismatch is a product defect, artifact difference or acceptance-fixture issue. Any fix needs a regression that proves the intended preservation invariant. S02 cannot claim accepted recovery while that explanation remains missing. No code was changed during this audit.

### Browser edition and license implications

The browser route uses the portable core to produce a reviewed ZIP. Its export implementation verifies merge-base hashes, adapts the old source, merges supported JSON/TOML/text and validates the result. It reports actions still required. It does not provide the native transaction's in-place installation, OS credential vault or operating-system post-install effects. This is a useful escape hatch and portability reference. [SRC-A08, web export](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/crates/hoi4-setup-web/src/export.rs)

Original source is Apache-2.0. The dependency notices include additional license families, including MPL-2.0 and CC BY 4.0 entries. Packaging therefore requires a selected dependency inventory and license review. The Apache declaration is not blanket clearance for every distributed dependency or imported game asset. [SRC-A01, notices](https://github.com/klimPaskov/HOI4-Mod-Setup/blob/4488a418cad56a158273cb66c4ce7794696b7ed1/THIRD_PARTY_NOTICES.md)

## HOI4 Agent Tools: source and visual foundations

The repository deliberately remains an MCP tool product. Its contributor guidance excludes a bundled editor or dashboard and directs surfaces through shared typed cores. The factory can own a separate native UI while wrapping these tools. Current package version is 4.3.0 and the package declares Node 22.19 or newer in the 22 line, or Node 24. Public local stdio and authenticated HTTP entrypoints are present. Tool capabilities should be discovered and pinned, including negotiated task support. [SRC-A10, package](https://github.com/klimPaskov/hoi4-agent-tools/blob/25f5641bbc07c65a822ef576ac6e92bd12666880/package.json)

The strongest preservation evidence is in the source layer. It retains source bytes and token spans, hashes the source, serializes an unchanged document from the original bytes and applies nonoverlapping replacements while retaining supported original encoding. Unsafe parse diagnostics block rewrites. Inspected tests cover generated no-op round trips, scalar rewrites, comments, duplicate/unknown syntax, UTF-8 BOM, CRLF and Windows-1252 refusal when a replacement cannot be represented. This is stronger than a pretty-printer claim, but the factory still needs host-level crash and concurrency tests. [SRC-A11, rewrite implementation](https://github.com/klimPaskov/hoi4-agent-tools/blob/25f5641bbc07c65a822ef576ac6e92bd12666880/src/hoi4_agent_tools/core/source/rewrite.ts)

Domain rewrites keep planning, validation, application and rollback internal to one tool call. The factory should not invent an external apply-token workflow that the public server does not expose. It can authorize bounded changes in a task worktree, or use an isolated proposal workspace to obtain actual candidate bytes before the host publishes a reviewed proposal. The final normalized arguments, source hashes and grant must remain bound to the same operation. [SRC-A11, transaction executor](https://github.com/klimPaskov/hoi4-agent-tools/blob/25f5641bbc07c65a822ef576ac6e92bd12666880/src/hoi4_agent_tools/core/transaction-execution.ts)

Focus tools inspect, render and rewrite. The renderer returns linked artifacts with source evidence rather than forcing huge inline results. The large-workflow test constructs 1,024 focuses through MCP, compacts them, repeats compaction unchanged and tests SVG/HTML/JSON and PNG outputs. It does not measure performance in this audit. The source-map, artifact hash and final source snapshot need to be carried into the factory's preview model. Event and technology tools are inspect/render surfaces, so comparable graphical editing remains additional work. [SRC-A12, workflow test](https://github.com/klimPaskov/hoi4-agent-tools/blob/25f5641bbc07c65a822ef576ac6e92bd12666880/tests/integration/mcp-large-focus-workflow.test.ts)

Maps already have inspection, geometry lookup, preview, semantic diffs and transactional bounded edit machinery. One limit is especially important: the structured geography model can be validated and previewed, but its synthesis into the full map is currently unavailable. The integration test explicitly expects `MAP_GEOGRAPHY_SYNTHESIS_UNAVAILABLE` and unchanged mod inventory for a model write. Reference-image world generation is a different path, with synthetic output tests. Neither path establishes an arbitrary image as a complete playable world. [SRC-A13, geography tests](https://github.com/klimPaskov/hoi4-agent-tools/blob/25f5641bbc07c65a822ef576ac6e92bd12666880/tests/integration/mcp-map-geography.test.ts)

Mechanic tests interpret declared source steps and retain unresolved effects and unknown write sets. Advancing modeled days does not execute all game on-actions. Package checks confirm declarations and references, while scenario execution is separate. These distinctions directly support layered evidence labels. [SRC-A14, mechanic semantics](https://github.com/klimPaskov/hoi4-agent-tools/blob/25f5641bbc07c65a822ef576ac6e92bd12666880/docs/mechanics.md)

For local use, stdio avoids remote identity configuration. The HTTP adapter has host/origin controls, OAuth/OIDC workspace grants, read/write scopes and credential-bound sessions. Static bearer mode is not a read-only credential. Inspected tests exercise scope refusal and replacement-token session takeover refusal. This targeted inspection does not replace a security review. Repository CI at the audited HEAD reports success. Roboto and offline OCR dependencies have separate notices. [SRC-A15, authorization tests](https://github.com/klimPaskov/hoi4-agent-tools/blob/25f5641bbc07c65a822ef576ac6e92bd12666880/tests/integration/http-authorization.test.ts) [SRC-A16, CI](https://github.com/klimPaskov/hoi4-agent-tools/actions/runs/39292737534)

## HOI4 Live Tools: optional actual-game evidence

The published v1.1.0 Python release and current native Rust source are distinct deliverables. Native platform code supports the verified Linux path and rejects unavailable native Windows/macOS adapters. Linux opens an owned session and checks the actual executable SHA-256 and ELF build ID. The current constants identify one supported build. A user selecting a nominal game version is not enough to bypass that executable identity check. [SRC-A17, Linux adapter](https://github.com/klimPaskov/HOI4-Live-Tools/blob/6b91a2a43edfeab60a415ec2ddd9b71d215b8a56/native/src/platform/linux.rs)

The capability response distinguishes available observations, unverified observations, commands, ownership and unavailable paths. It labels a failed native game-command posting path as quarantined and says native mod QA is unavailable. FAIR owned-campaign policy and direct-call tests must be preserved. A source preview or modeled mechanic result must not be relabeled live evidence just because Live Tools is installed. The README reports no full-campaign acceptance for any runtime. [SRC-A17, capability response](https://github.com/klimPaskov/HOI4-Live-Tools/blob/6b91a2a43edfeab60a415ec2ddd9b71d215b8a56/native/src/protocol.rs)

The ordinary pause/speed action journal is a valuable reliability reference. It writes dispatch intent durably, verifies the observed target, keeps historical receipts stable across restart and quarantines uncertain effects. Changing request ID does not evade uncertainty for the same process. Tests also reject a late observation as current evidence after the deadline. The factory should use these semantics for external effect receipts, while keeping its own run authority separate from upstream action internals. [SRC-A18, action tests](https://github.com/klimPaskov/HOI4-Live-Tools/blob/6b91a2a43edfeab60a415ec2ddd9b71d215b8a56/native/tests/actions.rs)

Original source is Apache-2.0 with MIT-derived Clausewitz provenance and notices for further dependencies. Python and Rust CI workflows report success at this HEAD. These are repository test signals, not an actual game session run by this audit. S01 should establish a capability matrix, and a later owned campaign probe should record exact build, DLC, scenario and observation scope. [SRC-A19, notices](https://github.com/klimPaskov/HOI4-Live-Tools/blob/6b91a2a43edfeab60a415ec2ddd9b71d215b8a56/NOTICE)

## CWTools and the HOI4 rule pack

CWTools is a mature-in-history F# library with HOI4-specific initialization and an `IGame` interface for parse diagnostics, semantic diagnostics, localization, references, completion and scope information. Rules and resources supply province enums and command interpretation. It is a good candidate for an independent static-analysis worker. Benchmark startup, memory and incremental updates before selecting an in-process or process boundary. [SRC-A20, HOI4Game](https://github.com/cwtools/cwtools/blob/b377453dee803f9258be92cfc49896d09039702d/CWTools/Game/HOI4/HOI4Game.fs)

Its printer regenerates tabs, operator spacing and line endings. One inspected roundtrip test on a formatted fixture does not establish arbitrary source preservation. Keep it out of the canonical write path unless a separate preservation adapter proves stronger guarantees. [SRC-A21, printer](https://github.com/cwtools/cwtools/blob/b377453dee803f9258be92cfc49896d09039702d/CWTools/Parser/Printer.fs)

The MIT rule pack has a separate September 2026 revision and encodes focus types, shared focuses, prerequisites, relative positioning, localization and scoped effects/triggers. Its README acknowledges false positives involving variables and arrays. The inspected completeness helper compares effect names against documentation, and the visible workflow dispatches cache generation. Those are useful maintenance signals, not proof of every gameplay rule. Pin the engine, rule pack and game/DLC profile independently. Record a baseline, classify new diagnostics and retain uncertainty. [SRC-A22, rule limitations](https://github.com/cwtools/cwtools-hoi4-config/blob/297dd69c42aabe10078a8b7ab7f2d07ee631d4ef/README.md)

## Modmaker, HOIIVUtils and Nova comparisons

Modmaker is a Python/Tkinter/Pillow desktop with useful focus canvas, map and content workflows. Its data layer overlays mod files on base files and discards obsolete asynchronous results. Tests cover vanilla copying before edits, undo, AND/OR prerequisite groups and preservation of untouched base states in a merged view. Those are valuable acceptance examples. [SRC-A23, focus data layer](https://github.com/Floxizdia/hoi4-modmaker/blob/a5c138ffacf4ed471769558f864cbe55ec5163fa/app/focus_tree_data.py)

Its actual focus and state write paths read `utf-8-sig` with errors ignored, then write UTF-8 using normal text I/O. That can remove a BOM, change line endings and discard invalid bytes. A one-time `.bak` and undo history are not an atomic multi-file transaction or a compare-and-swap precondition. The scanner explicitly calls itself a lightweight partial parser. Adapt interactions and fixtures, with the existing stronger mutation foundation providing final writes. Original code is MIT, and its README excludes game and third-party assets from that license. [SRC-A23, focus surgery](https://github.com/Floxizdia/hoi4-modmaker/blob/a5c138ffacf4ed471769558f864cbe55ec5163fa/app/focus_surgery.py)

HOIIVUtils is an Apache-2.0 Scala/Java/JavaFX desktop. Its inspected POM targets Java 24 and Scala 3.7.3. README labels its tools WIP. The parser and domain classes offer another view of HOI4 structures, but its writer regenerates formatting and removes tabs from trivia. The inspected parser test file is entirely commented out, as is the inspected focus-integration test section. This does not prove the entire repository lacks active tests. It does mean those files cannot support a claim of active parser coverage. [SRC-A24, writer](https://github.com/battleskorpion/HOIIVUtils/blob/0fe06450bf17c506485caf90fb5d52cf8a2e1b33/src/main/scala/com/hoi4utils/script/scripter/NodeScripter.scala) [Parser test](https://github.com/battleskorpion/HOIIVUtils/blob/0fe06450bf17c506485caf90fb5d52cf8a2e1b33/src/test/scala/com/hoi4utils/parser/ParserTest.scala)

Its province generator composes heightmap, seed and distance-based methods into a province image. That is a candidate algorithm experiment, not proof of a complete playable world, consistent IDs, country histories, supply, terrain and runtime behavior. GPU support is qualified by its own README. The extra JVM stack and asset provenance need justification before integration. [SRC-A24, generator](https://github.com/battleskorpion/HOIIVUtils/blob/0fe06450bf17c506485caf90fb5d52cf8a2e1b33/src/main/java/com/hoi4utils/hoi4/map/province/ProvinceGeneration.java)

Claims about focus/research/map editing, load order and atomic backup saves remain documented claims. The license states CC BY-NC-ND 4.0 and explains restrictions on commercial bundling and distributing modified derivatives. No binary was downloaded or executed. Keep this project as a feature comparison and obtain specific permission before any future reuse decision. No local test execution, game launch, model-provider authentication, desktop installer exercise or asset-generation request occurred. No claim in this audit upgrades test source or repository CI to independently reproduced runtime behavior.
