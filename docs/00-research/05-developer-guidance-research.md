## Current documentation corrections

Current Codex uses `.agents/skills` for repository skill discovery. The user explicitly requires `.codex/skills` deliverables, so the package will include both paths and keep their bodies identical with a deterministic drift check. `.codex/skills` is not described as automatically discovered. Optional `agents/openai.yaml` can disable implicit invocation while retaining explicit invocation. [SRC-C12](https://developers.openai.com/codex/skills)

Claude now documents native AGENTS discovery from v2.1.277 under specific conditions. A root `CLAUDE.md` can change which default discovery applies. The requested explicit `@AGENTS.md` import avoids depending on those conditions and requires no user-level switch or symlink. The starter keeps shared policy in AGENTS and concise Claude-specific operations in CLAUDE. [SRC-C16](https://code.claude.com/docs/en/memory)

Codex reference documents `max_threads` as a legacy alias, while the current machine schema exposes `max_concurrent_threads_per_session`. Its `max_depth` is explicitly V1-only and ignored by V2. The starter therefore uses the canonical concurrency key and omits a misleading depth guarantee. Pinned schema commit is `f71c6afc30031011fe0b4d757b981fd0301b2536` from 2026-10-23. [SRC-C10](https://developers.openai.com/codex/config-reference) [SRC-C11](https://github.com/openai/codex/blob/f71c6afc30031011fe0b4d757b981fd0301b2536/codex-rs/core/config.schema.json)

Claude MCP uses `.mcp.json` and does not read Codex TOML. Its server execution timeout is milliseconds, so 600 seconds maps to 600000. Startup timeout has a client-wide environment equivalent, not the same per-server shape. No Claude `cwd` field is invented. Launch from the intended repository and verify the server's resolved root. Keep both inherited connections rejected through `disabledMcpjsonServers` until an owner reviews installation, authentication and permissions. [SRC-C18](https://code.claude.com/docs/en/mcp)

Claude skill `allowed-tools` grants preapproval and is not a general restriction. The starter does not use it. Denying file editing tools in a subagent does not by itself constrain shell or MCP side effects. Root instructions guide behavior while actual permissions and OS sandboxing enforce boundaries. Worktrees isolate Git changes but are not security sandboxes. [SRC-C17](https://code.claude.com/docs/en/skills) [SRC-C21](https://code.claude.com/docs/en/sub-agents) [SRC-C23](https://code.claude.com/docs/en/worktrees) [SRC-C24](https://code.claude.com/docs/en/permissions)

## Starter decisions and limits

The proposed Codex starter keeps the observed instruction byte budget and nonsecret MCP definitions, adapts approval to on-request, adapts sandbox to workspace-write, and lowers concurrency to four using the canonical key. Each MCP entry has `enabled=false`. Claude settings use default permissions, reject both project MCP names and disable blanket approval. The remote endpoint stays dormant until explicitly enabled. No dependency is installed and no global config is edited by this package.

The source registry and every role field remain accounted for in the CSV and inventory, but all 23 domain roles are optional. Product engineering does not need portrait, quote or 3D asset subagents during bootstrap. Their tool dependencies, provider choices and domain instructions need a scoped review before adoption. The new product runtime must own its own versioned policy, credentials, capability registry, durable state and approval grants. Neither developer config file becomes product runtime config.

Both source schemas were fetched and pinned. SchemaStore commit `bf7c6745505ccace5568dc0d7f4ae29647e9b41a` is dated 2026-10-19. Its Claude schema permits additional root properties, so accepting a JSON document against that schema cannot alone establish support for an unfamiliar field. Only explicitly documented keys are shipped. Python JSON and TOML parsing and targeted shape checks are available. A full standards-compliant JSON-schema engine and the actual clients are unavailable, so full schema validation and live client loading remain S01 tasks. [SRC-C20](https://github.com/SchemaStore/schemastore/blob/bf7c6745505ccace5568dc0d7f4ae29647e9b41a/src/schemas/json/claude-code-settings.json)

## Engineering learning

The proposed engineering learning process captures an observation with a reproduction, evidence hash, applicability bounds, counterexample and suggested change. It progresses through candidate, tested, reviewed and accepted states. Only accepted guidance updates shared instructions or canonical skill bodies. Rejected, superseded and expired candidates remain traceable. Human review is required for changed authority, new external effects, safety boundaries, recurring costs and changes to approved product requirements. Routine factual corrections within an already authorized stage remain reviewable normal work, without repetitive permission requests.

Shared skills use outcome, process, scope and efficiency checks. Trigger fixtures include explicit positive invocations, ordinary questions that must not authorize implementation, unavailable tools, stale evidence and requests to continue into the next stage. Static syntax checks do not establish model trigger performance. A future client trial records model, client version, prompt, tool trace, outputs and rubric result. This follows the eval guidance while preserving a clear separation between observed measurements and planned tests. [SRC-C14](https://developers.openai.com/blog/eval-skills)

The stage handoff carries exact completed scope, revision, evidence and unresolved dependencies. Resuming a Claude transcript can help recover conversational context, but the repository handoff and recorded artifact hashes are the authority for completion. No workflow silently starts the next stage. Small bounded phases and explicit outcomes are consistent with the official development workflow guidance. [SRC-C15](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex) [SRC-C22](https://code.claude.com/docs/en/sessions)
